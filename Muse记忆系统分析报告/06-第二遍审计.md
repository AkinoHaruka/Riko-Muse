# 06 · 第二遍审计：交叉验证（按数据流向）

> 方法：按一条记忆的生命周期重走——产生→提取→入库→索引→检索→注入→遗忘，每环节对比 X 与 Y。本遍新发现编号 D1–D8。

## 环节 1：产生（对话中）

X：agent 按"六类+三不记"纪律即时写（[源-提示词] 1.1/1.3）。
Y：模型只产候选，admit_v2 裁决（源码实测）。
差异：写权归属不同。X 是 agent 直写，Y 是"模型提议、内核裁决"。[推理] Y 更严谨（防幻觉），X 更灵活。V2 保留 Y（已有 Z：三级写入在 12 §五"采用主人的"清单）。

## 环节 2：提取→改写

X：claim 表同时存 `claim_text`（改写后）+ `quote`（原文）+ `speaker`（[源-Schema] 2.1）。
**D1**：这是源证据对附录 D rewrite 契约的直接验证——Muse 的生产 schema 就是"改写后命题 + 原文 quote + 说话人"三件套。Riko-Memory 的 memories 表缺 quote/speaker 内联（只有证据链接）。
→ V2 字段补齐（V2 文档 04）。

## 环节 3：入库（条目结构）

X：entries 是 chunk 级（title+body+行范围），claims 是命题级，两层（[源-Schema] 2.2）。
**D2**：`memory.entry_attributes`——每 entry 的 KV 扩展表，Riko-Memory 无对应物。
**D3**：`memory.metadata`——系统 KV 表。
→ 低优先级，V2 记为可选。

## 环节 4：索引

X：embeddings 挂在 **entries（chunk）级**，不是 claims 级（[源-Schema] 2.3）。
**D4**：检索粒度是"带上下文的块"，不是原子命题。Riko-Memory 的 semantic_vectors 粒度需核对——如果它是 claim 级，V2 检索应对齐到 entry/chunk 级（有上下文才敢用）。
→ V2 文档 05。

## 环节 5：检索→注入

X：开场自动语义检索 + standing context 全文注入 + people INDEX 延迟加载（[源-提示词]）。
Y：DSH `agent/pre-step` 注入（Harness 文档 04）。
对齐：机制不同，效果等价。V2 保留 Y（twin-bundle 设计已定）。

## 环节 6：后台任务

X：7 任务官方定义（[源-文档] 03）。
**D5**：Studying 会"建议用户暗示但没明说的目标"——隐式目标检测，第一遍没注意到。
**D6**：Skill review 有退役机制——"measurably don't help are retired"，不是只增不减。
**D7**：bank/ 条目带 `(src: MEMORY.md:行号)`——source_line 机制的实物证据，证明"文件→DB"的双向链接真实存在。
**D8**：self_improvement.md 是[源-文档]级证据——7 任务不是推理，是官方白纸黑字。之前文档把 05 标[实测]是低估了，应为[源-文档]。

已有真 Z（06）：Y 多一道防线。维持。

## 第二遍结论

第一遍按结构看，漏掉了"跨环节"的差异：D1（claim 内联 quote/speaker）、D4（检索粒度）是数据模型层的实质差异，不是简单的"有/无"。D5/D6 是任务定义的细节。D8 纠正了证据分级。

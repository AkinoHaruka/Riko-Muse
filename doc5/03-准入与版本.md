# 03｜`admit_v2` 准入、版本与旧作业

## 1. 先解决版本冲突

当前 schema 3 的 `extraction_jobs.prompt_version` 由 0002 增加，旧行默认 `extract_v1`；新行目前写 `extract_v2`。`memory-extract::admit` 与 `jobs.rs::save_candidate` 的规则对两代作业共用，故仅把 Prompt 改名不能使新准入可审计。新增 `agent-memory/migrations/0004_admission_version.sql`：

```sql
ALTER TABLE extraction_jobs
  ADD COLUMN admission_version TEXT NOT NULL DEFAULT 'admit_v1';
```

迁移执行器同步 `SCHEMA_VERSION=4`。历史行全部回填 `admit_v1`，原 ID、attempts、status、prompt_version、候选、记忆均不变。**分阶段施工期间继续创建 `extract_v2/admit_v1` 作业；直到 v3 Prompt、v2 准入与 worker 分派全部存在并通过必要检查，才在同一提交中切换新作业默认值**。切换后新建作业固定写 `prompt_version='extract_v3'`、`admission_version='admit_v2'`，包括服务端分窗创建的普通 job 与 checkpoint/dead job；后两种虽不调模型也保留生成时版本。领取与详情读取两列，worker 按两列分别分派。`extract_v1/v2` 和 `admit_v1` 文本及行为冻结；任何未知版本不退回最新版本，应立即 dead 并记录 `UNKNOWN_PROMPT_VERSION` 或 `UNKNOWN_ADMISSION_VERSION`。`doc-handoff/08` 所指出的“确定性错误先重试两次”偏差应在此之前修复，避免新版本错误又空转。

已发布的 `0002_prompt_version.sql` 注释曾把 Prompt 和准入统称“规则版本”；该文件不能回改。实施时在 `doc/13` 和新迁移注释中明确分工：`prompt_version` 只选模型提示词，`admission_version` 选 Rust 准入及查库提交规则。

候选已有 `job_id`，可经作业行查准入版本。新 active 的 revision/audit reason 必须表明 `extract_v3/admit_v2`，不把老作业的结果标为新策略。若实施发现旧数据无法可靠追溯候选到 job，先记录缺口并设计增量字段，不能以“当前代码规则”倒推历史准入。

## 2. `admit_v2` 固定顺序

返回仅有 `Active`、`Held(reason)`、`Rejected(reason)`；第一项失败决定状态。规则按如下优先级执行：

| 顺序 | 判定 | 结果 |
|---|---|---|
| 1 | 来源不属于当前 scope/窗口或非 user/user | `rejected:BAD_SOURCE` |
| 2 | quote 不是同一来源正文的连续原文 | `rejected:QUOTE_MISMATCH` |
| 3 | 规范化为空或超过 512 Unicode 标量字符 | `rejected:INVALID_QUOTE` |
| 4 | 假设、转述、引用、一次性语境 | `held:CONTEXT_UNCERTAIN`；明确加入旧文档已有但现码遗漏的“今天先” |
| 5 | 两个独立命题或可剥离的口语前缀 | `held:MULTI_CLAIM` 或 `held:NON_MINIMAL_QUOTE` |
| 6 | 引用缺明确归属主体 | `held:UNCLEAR_SUBJECT` |
| 7 | 密码、API key、token 等凭据内容 | `held:SECRET`；任何路径不得 active |
| 8 | 健康/过敏/诊断/病历等敏感个人信息 | `held:SENSITIVE` |
| 9 | 第三人事实、家庭成员信息 | `held:THIRD_PARTY` |
| 10 | 未来节点、相对时间或明显短期状态 | `held:TEMPORAL` |
| 11 | 与 kind 不符，或未命中允许的明确自述/指令/偏好句式 | `held:NOT_EXPLICIT` 或 `held:KIND_MISMATCH` |
| 12 | 同 scope 旧证据已 suppressed | `rejected:SUPPRESSED_SOURCE` |
| 13 | 完全相同的 active | 仅加证据，不新建记忆 |
| 14 | 已知属性键冲突 | `held:POSSIBLE_CONFLICT` |
| 15 | 其余 | 单事务建 active、来源、revision、audit，索引 dirty/reindex 沿用现行规则 |

规则 1—11 在 `memory-extract`；12—15 在 `memory-store-sqlite`。每次先判无权/无效来源，再看正文内容，避免从跨 scope 行泄露判断结果。`claim` 仍等于 quote 的空白折叠，不生成改写文本。reason 字面值须写进新增契约文档与诊断说明；不能只存在日志里。凭据候选若保留在 `memory_candidates`，现有 schema 会保存 quote 原文，因 L0 本已保存该用户事件，不能宣称“系统不持久化凭据”；候选默认列表、日志及错误不得打印它，`candidates show` 仍是本地管理员主动查看入口。

## 3. 可自动 active 的窄句式

以下只对**单一命题、完整第一人称、没有 §2 排除项**的候选有效。实现者可以用有限字符串模式，不得用模型自报 `kind` 取代 Rust 判断。

| kind | 可识别形式 | 边界 |
|---|---|---|
| instruction | 原有“以后/总是/从现在起/记住”及英文等价词，且是用户对 Agent 的长期要求 | 引用里提到“记住”一词、要求记住第三人/健康/时间事实，不直接放行；先过 §2 的敏感等闸门 |
| preference | “我喜欢…/我不喜欢…/I like…/I dislike…” | 稳定偏好；“今天先…”等一次性语境 held |
| fact: identity/residence | “我叫…/我是…/我住在…/my name is…/I live…” | 值不能为空，不能包含另一独立命题；`我是` 的角色不明时 held |
| fact: occupation | 原有“我在…工作”，新增“我在…做…开发/工程/设计/教学/研究”等**有职业尾词**的有限形式 | “我在家做饭”不得作为职业 active；不从“做后端”自行补公司/地名 |
| fact: primary practice | “我主要写…/我平时主要写…” | 引用自身必须含“我”；“平时主要写…”独立片段 held；对象不能为空，不从对象猜技术类别 |
| episode | 本版无自动 active 新规则 | 保留 held 或由现有用户显式保存路径处理 |

实现时把有限职业尾词表、长度上下限和标点边界放到同一常量/函数并给出正反例；不得在不同层复制不一致的名单。句式之外默认 held；不试图用规则填补所有语言。用户之后明确纠错/遗忘优先于自动提取。

## 4. 时间与敏感语义

模型的 `occurred_at/valid_until` 仍只留候选诊断，不能自动写入规范记忆。包含“今年九月/明年/下周/即将/准备”等未来节点，或“今天/最近/坏了/暂时”等短期状态，因没有可靠有效期与状态更新机制而 held/TEMPORAL；明确的过去经历也不自动转为永久当前事实。第三人标记至少覆盖“我姐/我哥/我妈/我爸/孩子/小孩/家人/同事”等可核查样本；不能把“我们家小孩”误识别成用户本人。健康至少覆盖“过敏/诊断/病历/疾病/吃药”等样本。关键词只能作为保守拦截，不能宣称穷尽敏感类别；不确定时 held。

## 5. 旧作业与活跃旧记忆

`extract_v1|v2 + admit_v1` 的未完成作业继续按旧规则处理，包括手动 retry；不得在新代码里借同名函数静默切换到 `admit_v2`。旧 active 不自动降级、拆分或补期限。升级后新写入的 v2 作业只用新版本。若产品后来要求追溯清理旧 active，须另列带用户可见影响的迁移决策，不能把它藏在 schema 0004 中。

## 6. 首版有限识别器的精确定义

这张表是 `admit_v2` 的**最小受支持集合**，不是“可自由扩展的提示”。后续要增词或放宽句式，另升准入版本并增加正反例。判定时可对工作副本执行 trim、大小写折叠和 NFKC；原 `quote`、`claim` 的保存方式沿既有契约，不能以规范化文本替换证据。每个 `X` 须非空、长度 1—64 个 Unicode 标量字符，且不含 `，,；;。.!?！？\n\r`。每项在去除句末一个标点后匹配；不要删除中间词或否定词。

| kind | 完整 quote 的允许形状 | 额外限制 |
|---|---|---|
| instruction | 以 `以后`、`从现在起`、`请总是`、`记住`、`请记住`、`always`、`from now on`、`remember` 起始 | 后面必须有非空要求；先过 SECRET/SENSITIVE/THIRD_PARTY/TEMPORAL 门；`我以后...` 不因内部含“以后”被当作指令 |
| preference | 以 `我喜欢X`、`我不喜欢X`、`I like X`、`I dislike X` 起始 | `X` 不可再形成第二独立句；一次性词先 held |
| fact/name | `我叫X`、`my name is X` | 现有 name 属性冲突逻辑继续有效 |
| fact/residence | `我住在X`、`I live in X` | “我在杭州做后端开发”**不**说明住在杭州 |
| fact/occupation-old | `我在X工作`、`I am a X`、`I am an X` | `我在家里休息` 不符合；中文 `X` 中不得有另一分句 |
| fact/occupation-new | `我在X做Y`，且 `Y` **以** `开发`、`工程师`、`设计师`、`教师`、`老师`、`研究员`、`产品经理`、`数据分析` 之一结尾 | `X`、`Y` 各为非空受限片段；`我在家做饭` 不符合，`我在杭州做后端开发` 符合 |
| fact/primary-practice | `我主要写X`、`我平时主要写X` | “平时主要写X”无主语，held/UNCLEAR_SUBJECT；不根据 X 猜职业或居住地 |

旧版 `我是X` 过宽。`admit_v2` 只在 `X` 以职业尾词之一结束时当作 fact 自动 active；例如“我是软件工程师”可通过，“我是刚吃完饭”held/NOT_EXPLICIT。英文 `I am a/an X` 沿用旧形状，但临时、健康、第三人和多命题门仍优先。事实 kind 不接受仅含“以后”的句子；偏好 kind 不接受职业句式；kind 与形状明显冲突时记 `KIND_MISMATCH`，不要自动改 kind。

## 7. 阻断词与冲突键的实施下限

以下是本版本必须覆盖的有限词表；它只负责**阻止自动 active**，不能解释成完整自然语言理解。匹配前先看 source/quote 有效性，匹配优先级依 §2；一个 quote 命中多项时记录先遇到的 reason。大小写折叠用于英文，中文按字面包含；保存的 quote 不变。

| 类别 | 至少覆盖的文本信号 | 说明 |
|---|---|---|
| 一次性/假设 | `如果`、`假如`、`比如`、`这次`、`本次`、`今天先`、`if `、`for example`、`this time`、`just today` | `今天先` 是旧文档有而旧码漏的规则，只加入 v2 |
| 宽 quote | 两个完整子句由 `，,；;。` 分隔，且后句以 `我`、`平时主要写`、`还`、`也` 开始；或 quote 内出现两个完整第一人称起点 | 不把姓名地址中的普通逗号直接判为两个命题；不确信可独立维护时 held |
| 可剥离口语前缀 | `提醒一下，`、`顺便说一句，`、`对了，`、`by the way, ` | quote 含该前缀则 held；模型可重新提出不含前缀的逐字 span |
| 凭据 | 继承现有 `sensitive()` 的密码/token/API key/sk- 模式，并覆盖 `api key`、`API key` 等同义拼写 | 命中 `SECRET`，自动和直写均不得 active；不要把值打印到日志 |
| 健康 | `过敏`、`诊断`、`病历`、`疾病`、`吃药`、`服药` | 命中 `SENSITIVE`；不能把所有健康表达识别能力写成“已覆盖” |
| 第三人 | `我姐`、`我哥`、`我妈`、`我爸`、`我们家小孩`、`小孩`、`孩子`、`家人`、`同事` | 命中 `THIRD_PARTY`；“我们家小孩”不能算第一人称用户事实 |
| 未来/短期 | `今年`、`明年`、`下周`、`下个月`、`即将`、`准备`、`今天`、`最近`、`暂时`、`坏了` | 命中 `TEMPORAL`；不从模型时间字段生成自动过期日 |

`UNCLEAR_SUBJECT` 适用于没有完整用户自述主语、也没有明确第三人主语的 fact/preference 片段，如“平时主要写 Rust”“老笔记本电池坏了”；已识别第三人主语应按 §2 继续到 `THIRD_PARTY`。对额外未知口语或复杂从句，先进入 held，不按“看起来像事实”放行。

Store 的现有属性冲突键至少扩展为 `occupation`（同时识别“我在X工作”和“我在X做Y职业尾词”）及 `primary_practice`（“我主要写X/我平时主要写X”）。同一 scope 同键不同值进入 held/POSSIBLE_CONFLICT；不得借新的职业句式绕开旧冲突检测。职业句中的 `X` 只是工作地点/单位文本，不写入 residence 键。没有明确属性键的复杂冲突继续如实列为未解决，用户可通过 correct 显式处理。

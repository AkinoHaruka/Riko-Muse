# 05｜召回契约与可区分的离线评价

## 1. 本版不改 compose 的理由和具体边界

`memory-store-sqlite/src/memories.rs::compose_context` 先取查询命中，再给最多两个 active instruction 独立名额；其余 fact/preference/episode 只从查询相关 hit 中填充，总预算仍为至多 5 条/2000 字符，超长单条跳过。doc5 保留此行为。新增的 fact 只有通过已有词法搜索命中才进入自动上下文；不承诺零词法措辞能召回。“我喜欢暗色主题”在“推荐护眼颜色”中未注入，但回答可能碰巧也是深色，这是 `doc-handoff/06` 已确认的行为归因问题。

不添加“最近两条偏好常驻”“所有重要事实常驻”或按模型 confidence 排序。这样做会挤占指令/查询命中名额，并可能把已经变化但未纠错的事实带进无关问题。也不把 `index_degraded` 时的降级命中宣称为正常检索质量。

## 2. 离线探针格式

每个探针记录：`probe_id`、同一 scope 的 active 记忆集、另一 scope 的干扰记忆、查询、预期相关 memory_id、预期不注入的 ID、预算、是否有词法机会（包含直接词、同义改写、零相关三档）、search 命中、compose items、实际 text 与 `index_degraded`。从规范表构造临时库，不调用外部模型。用 memory_id 比较实际注入，不能只看回答措辞。

至少包括：

- **该生效**：同用户 Agent A 存“我喜欢暗色主题写代码”，Agent B 问“VSCode 暗色主题怎么配”，应由词法命中注入；另一个用户的同句不参与。
- **正确沉默**：同样记忆下问“如何焯西兰花”，该偏好不注入；长期“以后回答请用中文”仍在指令名额内。
- **已知盲区**：问“给我推荐护眼配色”，偏好零词法命中时当前可能不注入；记录为召回覆盖缺口，不能把模型可能给出的深色回答记为记忆效果。
- **互相冲突**：同一属性两条不同 active 或一条 superseded，检查只把规范 active 候选用于普通 compose；若两条仍 active，不能声称系统自动消歧。
- **失效/遗忘**：`valid_until<=now`、forgotten、suppressed 旧证据不得在 search/compose 出现；历史查询按现行授权开关。
- **预算**：超过两条指令、超过 5 条或 2000 字符、单条过长，明确记录哪些 ID 被跳过；不能截断否定词。

## 3. 未来改召回的门槛

如果离线探针显示稳定的“明确该生效却未命中”，先写一个可复现的查询集和预期 ID，再比较词法扩展、受限同义词、语义检索或独立名额。每个方案同时量化：该注入时覆盖、正确沉默、错误注入、跨 scope 泄露（必须 0）、预算挤占、索引退化、查询开销。真实模型回答是否使用记忆是**另一层**；在用户恢复模型试验之前不报告利用率或回答质量提升。

任何新检索索引只作为规范 `memories` 的可重建派生物，过滤必须先按 token scope、active 与有效期，遗忘/纠错下一读立即生效。若需要改 `compose`，另开文档与验收卡，不藏在 `extract_v3` 实施中。

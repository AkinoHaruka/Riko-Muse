## 1. 上一轮闸门的结论与新闸门

第 10 份记录没有观察到三项既定阻止情形：错误自动激活、active claim 改写、跨用户泄露。跨用户一项本轮仅单 principal，沿用先前离线隔离证据，不能写成“D5 真实模型跨用户复验通过”。因此**可以开始由开发者逐条核对写入凭据的受控日常试用**。

真实会话另出现两次“未调保存工具却告诉用户已记住”（含一次明确“请记住”）。这直接损害用户判断记忆是否已经持久化的能力。新增第四条日常产品闸门：**凡向用户确认“已保存／已记住为长期记忆”，必须能对应本次会话由内核返回的成功 receipt（memory_id/status），或已完成的提取作业及 active ID；模型自行陈述不是凭据。** 在可信宿主状态提示或同等机制完成前，不把受控试用扩大成无需核对的日常上线。单纯加强工具描述/提示词只能作为辅助，不能当作此闸门的验收。

当前 `memory_remember` 成功返回可给 receipt；异步提取尚未成功时只能表示“已捕获、待处理”，不能说“已记住”。若模型没有调用工具、也无完成的 active 记忆，宿主应给用户明确的“未确认保存”状态；具体 UI/宿主事件接线要先核官方 DSH 源码，不凭空假定存在回复拦截 Hook。受控试用期间，每条重要保存请求都以实际 memory ID 或 `memory_search/get` 复核，记录假阳性与漏写。

## 2. 决策 A：409 `STATE_CONFLICT` 的工具返回形状

**决定：`memory_remember` 的 409 `STATE_CONFLICT` 返回结构化 `{ok:false,error:{code,message}}`。** 它是用户可理解的保存规则拒绝，符合工具已声明的输出形状。适配器现有 `USER_FIXABLE` 是全工具共享集合；不要直接把 `STATE_CONFLICT` 全局塞进去，因为其他工具/协议中的该码也可能表示作业或状态错误。应在 `memory_remember` 调用 `toToolResult` 时按**端点 + HTTP 409 + error.code** 做窄映射，其余状态仍沿现有 throw/记录 request_id 语义。401、网络故障、坏 JSON 与内部错误绝不可伪装成用户可修复的拒绝。

验收：本地固定响应与真实 DSH 宿主均应看到同一 JSON 信封；三种直写窄门（SECRET/TEMPORAL/需保存指令）分别保留原 code/message，不回显正文；对另一工具的人为 `STATE_CONFLICT` 仍保持基础设施/协议错误路径。**此修复不能解决“模型完全不调工具却谎报成功”**，两项必须分开报告。

## 3. 决策 B：直写复合命题

**决定：`memory_remember` 的一次调用只能保存一个可独立纠错和遗忘的命题，所有 kind 都适用。** `doc-handoff/10` 中“我对芒果过敏，以后别再推荐含芒果的甜品”同时含健康事实与长期指令；将整句以 preference active 后，查询“推荐笔记工具”也召回了过敏内容，已观察到无关注入。新直写粒度门在 quote/span 校验及高风险类别校验之后、创建或去重之前执行；命中复合命题返回 409 `STATE_CONFLICT`，提示用户分开陈述和保存，不自动拆分或重写 quote，也不创建部分记忆。

当前 `admit_v2` 的 `multi_claim` 只识别部分第二分句起点，**不识别“，以后…”**。直写可新增自己的保守判定，至少覆盖 `，/；/。` 后的“以后”“从现在起”“我”“平时主要写”“还”“也”，并对样本里的“过敏 + 别再推荐”给出确定性拒绝。不要直接扩大既有 `admit_v2` 函数：其规则版本已被作业行引用，静默变更会改变未完成旧作业的准入结果。复杂句无法可靠拆分时拒绝一次性直写，让用户发出两条分别明确的保存请求；未来若要同一消息保存多项，另设计带多个独立 quote/span 的原子协议。

验收：第 10 份记录的复合 quote 用 fact/preference/instruction 任意 kind 均 409；两条分别发送的完整用户保存请求可以各自得到独立 memory ID；原有单命题健康窄门与普通偏好保持可用；拒绝时不写 active、不变更候选、不泄露正文。若已有复合 active，**不在迁移中静默改写、拆分或删除**，由用户纠错/遗忘或一次独立清理决策处理。

## 4. 仍属观察项

- 模型把“我平时主要写 TypeScript…”标成 preference，Rust 给 `KIND_MISMATCH`。这是已观察到的漏收；不让 Rust 根据文本偷偷改 kind。先保留原候选与 reason，下一次 Prompt 修改必须新建版本，并用非示例句检验。
- “有哪些食物需要忌口”没有词法命中过敏记忆。现行 compose 契约并未提供语义召回；不要因一例就让全部健康记忆常驻。用“该注入／正确沉默／错误注入”成组探针设计受限召回，再决定是否加规则或索引。
- 第 10 份记录共 15 个提取作业、16 条候选；粒度表现良好，但样本小且单一模型。长窗口、多轮、并发和其他模型的质量仍未验证。

## 5. 建议实施顺序与发布口径

1. 先做决策 A 的端点限定结构化错误，再做决策 B 的直写粒度门；两项各自独立提交与验收。它们都不能被包装成真实模型质量提升。
2. 单独设计“保存成功凭据”宿主展示/确认机制；先核官方 DSH 可用事件与回复通道，再定最小实现。验收必须复现“模型不调工具却声称已记住”，让用户看到的权威状态仍是“未确认保存”。
3. 继续在独立 schema 4 环境做受控日常试用，记录候选、准入、memory ID、注入 ID、工具 receipt 与用户可见保存状态。不要自动升级 dana/realtest；真实原库升级仍需先只读一致性快照，`index_dirty=1` 独立处理。

完成 A/B 前可以继续**有人核对的受控试用**；完成保存凭据闸门及其 DSH 复验前，不宣称“用户可以可靠地凭 Agent 的口头承诺判断是否已保存”，也不把当前小样本写成全面上线验收。

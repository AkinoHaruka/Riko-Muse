# 02｜候选粒度、`extract_v3` 与失败归因

## 1. 输入与输出冻结

模型输入继续使用 `serialize_window_events` 的同一 JSON builder；服务端 32 KiB 分窗预算不能因新 Prompt 另造一套输入序列化。`extract_v1`、`extract_v2` 字符串原样保留。新作业才写 `prompt_version='extract_v3'`。响应保持现行 `{ "candidates": [...] }`；每项仍为 `source_event_id,quote,kind,occurred_at?,valid_until?,confidence?`，最多 20 条。不得增加模型生成的 `evidence_id` 或自由文本 `claim`。额外字段继续按现行严格 schema 报 BAD_JSON；同步把 `doc/13 §5` 关于“独立 claim held”的旧表述修成真实协议，不能让文档与解析器并存两套说法。

## 2. 一候选一命题

新 Prompt 明示：每个候选只含一个可独立维护的用户命题；同一条用户消息若有两个合格事实，输出两项，二者可以共用 `source_event_id`，但各 quote 必须为原文中的独立连续 span。不得为了保全主语跨越另一命题并生成宽 quote，也不得把“平时主要写 Rust”改写成“我主要写 Rust”。宽 quote 应留作 held，而不是以错粒度激活。

逐字不等于可准入。Rust 先核 `source_event_id` 属本窗口 user/user，再核 quote 原文连续、长度，再检查命题粒度与语境。以下明确边界可以确定性处理：

- quote 含两个由 `，/；/。/;/,` 分隔的独立个人陈述，或出现两个自述起点（如“我在…，我主要…”）时，`held:MULTI_CLAIM`。实现须避免把小数、英文专有名词中的标点误判；无法可靠切分时 held。
- 引用口语前缀（“提醒一下，”“顺便说一句，”“对了，”）且前缀与命题可分时，`held:NON_MINIMAL_QUOTE`；不要在 Rust 中改写 quote 后自动 active。模型可返回不含前缀的另一条原文连续 span。
- 嵌在完整句中的无主语片段（如“平时主要写 Rust”）即使逐字，也只能 `held:UNCLEAR_SUBJECT`；不能用同事件别处的“我”补 claim。独立的“我主要写 Rust”可进入准入。
- 单一命题内部的必要修饰词不能随意剥除；“不喜欢”“主要”“以前”影响含义。判为过宽时保留整条候选，不截断成可能反义的新 claim。

这些是**保守的自动 active 门槛**，不是对所有自然语言的完备句法解析。无法识别的复杂句保持 held；不要发明语义分割器把用户没说过的话变为规范记忆。

## 3. 空候选与输出错误

`{"candidates":[]}` 是合法响应，不应由规则层臆造记忆。记录该窗口候选 0 的可观察状态；有真实模型授权后再观察新 Prompt 是否改善漏提。单项来源或 quote 错误应按既有 candidate rejected 规则处理；整个 JSON schema 错误仍使 job 按 BAD_JSON 失败，不以宽松解析偷偷丢字段。模型 `confidence` 只留诊断，绝不映射为可信度阈值。

## 4. 必须成对保留的例子

正例：“我在杭州做后端开发。我主要写 Rust。” → 两项，quote 各自逐字、两项分别接受准入。反例：“我在杭州做后端开发，平时主要写 Rust。” → 模型若只给整句，held/MULTI_CLAIM；若给两项，首项可 active，第二项因缺主语 held/UNCLEAR_SUBJECT。反例：“提醒一下，我对花生过敏，我姐在成都教书” → 不可生成一条 active；即使拆对，也分别进入健康/第三人 held。

## 1. 接手时的现场

上一个 Harness 在写 V2-S1（doc7/04）时被中断，工作区处于**机械重构做到一半**的状态：

- 已落盘：迁移 `0015_memory_domains.sql`、`memory-domain/src/domains.rs`（`DomainScope` 类型）、
  存储层大量签名加 `dom: &DomainScope` 与读域过滤 SQL、`doc7/04` 规范本身。
- **`cargo check --workspace --all-targets`：208 个错误**，工作区无法构建。
- 根因有两类：
  1. 一个一次性脚本 `agent-memory/_fix_callsites.py` 用**字节插入**改调用点，且只在
     「`.` 前一字符不是字母数字」时命中（即只处理链式调用），既漏掉大量
     `store.xxx(...)` 调用点，又在多行调用末尾插出**游离逗号行**
     （`        , &memory_domain::DomainScope::user_main())`），共 52 行语法错误。
  2. `memory-domain/src/lib.rs` 只加了 `pub mod domains;`，**没有 re-export**，
     于是所有 `use memory_domain::DomainScope;` 全部失败。

该脚本已删除（它会再次破坏代码）。恢复过程见 §4。

## 3. 本轮修出的真实缺陷

这些不是重构噪声，是会导致**跨域泄漏或功能错误**的实现缺陷：

| # | 位置 | 现象 | 修复 |
|---|---|---|---|
| 1 | `pages.rs` `publish_page_inner` | 找既有页面时**未按域过滤**，side 域发布会原地升级主域那一页（同 key 两域共用一行） | 查找加 `domain_id=dom.write` |
| 2 | `jobs.rs` `JOB_ROW_COLUMNS` | 列清单漏 `domain_id`，而 mapper 读 `r.get(15)` → worker 全部 `InvalidColumnIndex(15)` | 补列 |
| 3 | `memories.rs` `search_memories` FTS 支路 | 给 FTS 表起别名后 `WHERE f MATCH ?1` 被当成列名 → `no such column: f`，拉丁 token 查询整条支路失败 | 不给 FTS 表起别名，用 `memory_fts MATCH` |
| 4 | `pages.rs` `page_fts_search` | `?N` 与无名 `?` 混用导致编号错位（`InvalidParameterCount`），页面检索失败 | 全部改无名占位符，绑定序与 SQL 文本严格一致 |
| 5 | `lib.rs` `insert_principal` | 无条件写 `memory_domains`，使「只应用到 0010/0014 的迁移演练」无法建 principal | 先查 `sqlite_master`，旧 schema 快照跳过 |

同时按迁移纪律把 `d69_tests` 的冻结历史断言 `applied == 14` 同步为 `15`。

## 4. 一次事故与恢复（如实记录）

用 cargo 的机器建议批量补参数时，我把 `worker.rs` 与 `dream_worker.rs` 的**字节偏移混在同一个
文件上**应用（`endsWith('worker.rs')` 同时命中 `dream_worker.rs`），导致
`dream_worker.rs` 被写到错误位置而损坏（花括号 223/226 不平衡）。

恢复方式与验证：`dream_worker.rs` 在 HEAD 上是干净版本，上一个 Harness 对它的改动只有
2 处 `/*DOM*/` 标记（`git diff --stat` 当时为 `4 +-`）。因此
`git show HEAD:…dream_worker.rs` 还原后补回这 2 处，再跑 `cargo check`，
得到 `dream_worker.rs` 的 E0061 列表为 `499,508,518,522,697,723,734,736,816,1050,1064`
——与损坏前记录的基线**逐行一致**，确认恢复完整。
`worker.rs` 未被写入（花括号 316/316 平衡），无损失。

## 1. 测量方法与边界

- `doc-handoff/p3-bundle-audit.py` 以当前 `memoryd principal add` 初始化 schema 23 新库；向该临时库写入 **120 条 synthetic active**：事实/偏好/指令/经历各 30 条，其中 12 条为关系句式。每条有独立 user evidence、逐字 UTF-8 span、SHA-256；通过真实 memoryd HTTP 调用 derived/relationships refresh 与 bundle。SQL 造数仅用于预算压力，不构成 Rust 准入或模型抽取质量证据。
- 12 个查询：5 个单话题、5 个复合话题、`P3` 广义查询、1 个无关查询。每个各跑默认请求（旧 8 条/2400 字符）和放宽请求（100 条/24000 字符）。服务无 embedding/reranker，检索为真实词法通道；计时为本机 HTTP 往返，单次样本不是性能基准。
- 关系句式在此次语料的 `relationships/refresh` 结果为 0；因此关系段预算与 8 条上限**没有数据支持调整**。四段中实际测到 compact、alignment、retrieved。`alignment` 来自确定性 synthesis，非模型新生成。
- 旧代码事实：`riko-memory/crates/memory-server/src/main.rs` 原 `BUNDLE_TOTAL_CHARS=4000`，retrieved 装配只检查 `q_items/q_chars`，未扣总预算；`riko-dsh/src/recall.ts` 按段创建独立 user-role 消息并前插。

## 3. 同语料对照与相关性抽样

对放宽请求的**相同排序结果**执行整条优先装配模拟（扣除已用前三段字符，换行按 1 字符计；compact 不拆条）。单话题放宽候选为 12–21 条；广义查询去重后 82 条。

| 模拟方案 | 12 请求因总预算新增省略 | `complete=false` 次数 | 广义查询保留/丢弃 | 观察 |
|---|---:|---:|---:|---|
| 严格 4000；compact 1200 / alignment 600 / relationships 8 | 45 | 1 | 37/45 | 旧代码未实际执行此总上限 |

| 8000；compact 上限改 600、alignment 上限改 300 | compact 少 3/24 条；retrieved 无新增收益 | — | — | 实测 compact 为 675、alignment 为 187，压 compact 只丢内容 |
| 8000；compact 上限改 1800 | 0 | 0 | 82/0 | 实测 compact 仅 675，扩此段无收益 |

**token 量级**：用固定代理指标 `CJK 字符数 + 1.3×拉丁数字连续组数 + 0.5×其余字符数` 估算注入文本，不宣称是模型 tokenizer 的精确值。旧默认 travel 约 930、新默认 travel 约 1434；新默认广义约 1531、放宽广义约 3751。真实 DSH 模型回合的完整输入为 **10,233 tokens**、输出 46 tokens（含 DSH 其他提示，不等于记忆注入 token）；见 §6。

**线上渲染开销**：`budget.used_chars` 采用内核既有的正文计数，不包含 compact 的 `stable_refs`、各段标签与 XML 转义。真实 DSH 的一轮 rust 模型输入中，内核段计数为 compact/alignment/retrieved `675/187/1571`，代理捕获的对应包裹文本长度为 `2712/235/1619` 字符，合计 **4566**，高于服务端计数 **2433**。本卡的 8000 是**内核记账硬上限**，不宣称模型线上包裹文本也被硬限到 8000。这个差异主要来自逐条稳定引用；若以后要对线上 token 做硬限额，必须另立适配器与内核共同的渲染计数契约，不能把本卡的正文计数说成实际 prompt 大小。

**人工相关性判定**：从旧默认请求省略列表按查询顺序取前 20 条，判据为是否直接描述该查询话题，未把形式相同但无话题的关系句算相关。下表的编号对应脚本生成的 `P3-xxx`，无私密正文。

## 4. 规范与实现

规范卡 [doc7/15](../doc7/15-P3-注入预算与形态施工规范.md) 已先于代码提交：总硬上限 **8000**（来自 7742 与三档对照）、默认 retrieved **24 条**（五个单话题放宽后最多 21 条；旧 8 条显式省略 80 条）；候选深度使用既有 `SEARCH_PER_CHANNEL_LIMIT=100`，避免默认 24 条时第 25 条起无声消失并误报 `complete=true`（广义请求实测 82 条）。compact ≤1200、alignment ≤600、relationships ≤8、retrieved 默认 2400 字符、段内排序、独立 user-role 前插均维持现状；各项没有更改证据。

内核 `main.rs` 的 memory/page 装配共用 `retrieved_omission_reason`，在每条入选前检查总上限，超出记 `TOTAL_CHAR_LIMIT`，计入 omitted 并使 `complete=false`；继续考虑后续较短条目。`budget.used_chars` 不超过总量。未动适配器、迁移或历史 extract/admit 版本。

## 6. 真实 DSH + 真实模型复验

P0.6 交接未留下可执行闭环脚本，故按其临时库方法重建：同一 schema 23 临时库、官方 DSH `0.2.1-rc.2` HEAD `687f282e…`、`riko-dsh` 当前构建，隔离的 headless profile + root 插件 patch；memoryd 127.0.0.1:8899。DSH 的 DeepSeek Messages 连接经 `/tmp` 内的临时协议代理转到真实 SiliconFlow `Qwen/Qwen3.5-4B`；代理只转换协议并记录模型输入结构，不生成回复。代理配置初次路径错误返回 502、第二次缺 SSE `message_stop` 返回 `STREAM_CLOSED`，修正后正式两轮返回 completed。凭据只从本机权限受限的环境文件读取，未入库/提交。**此处是真实 DSH + 真实聊天模型回合，但不是 P0.6 的 riko preset、多轮写入/纠错/Dream 全链重跑；embedding 未配置。**

- HTTP bundle 对 `travel`：四段 `675/187/0/1781`，`budget.used_chars=2643/8000`，四段 `complete=true`，去重 3。相同语料旧默认为 `675/187/0/669`，省略 9 条。适配器 `recall.ts:267-303` 为每个非空段创建独立 user-role 消息；真实模型代理捕获到的 DeepSeek Messages 请求将连续 user 内容合并为一个 user payload，但内部标记按 `compact → alignment → retrieved` 排列，空 relationships 没有占位。system 内容里没有这些 `agent_memory` 标记。该线上的形态与单测一致，模型确实收到内容。
- 第一轮新 DSH Session `session-501c6bd4-…` 问 travel 偏好，真实模型回答“先看简短摘要，再看证据编号”；该步完整模型输入 10,233 tokens、输出 46 tokens。新 Session `session-8c585825-…` 的模糊 rust 问法得到冗长但含正确偏好的回复；再用明确问法在 `session-56be7f80-…` 回忆，正确回答“先看简短摘要，再看证据编号”。这些 Session 共享同一临时用户 scope，证明新预算下的跨会话读取与注入，不证明泛化回答质量。

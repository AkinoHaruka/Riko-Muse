## 1. 最后一步的失败现象（最重要）

**背景**：V2-3 注入首版按 `doc2/04 §4` 写 `source:{kind:'plugin',plugin:'@agent-memory/dsh-adapter',form:'agent-memory'}`。真实宿主运行时报：

```
dsh: format v4 message requires a producer-owned source kind
```

定位：`packages/session/session-format-v3-to-v4/src/message-sources.ts` 第 9 行明确拒绝 `kind === 'plugin'`（注释：refuses retired plugin wrappers）。已按一方惯例改为 `{kind:'agent-memory', form:'recall'}`（`agent-instructions`、`time-context` 都是 producer 自有 kind），提交 `d7c863b`，`tsc` 通过并重新产出 `dist/`。

**复验时出现的现象**：改完后用同一条命令跑「用中文回答我」，得到

```
dsh: TRANSPORT: DeepSeek Messages transport failed
```

此时 `mock-state.json` 的 `requests` 从 10 变 11（说明请求到了 mock），但 DSH 侧报传输失败；首次跑之前（改 source kind 前）同类型请求是成功的（`ok 无记忆注入 tools=29`）。尚未定位，候选假设按排查成本排序：

1. **mock 自身的 SSE 帧问题**：`requests=11` 说明进了 mock，但可能响应在 `content_block_stop` 之后没正确结束，或 DSH 的 `parseSse` 要求 `event:` 默认值/`data:` 之外的字段。先单独用 curl 打一次带记忆上下文的请求比对。
2. **注入消息进入待发送的历史后触发序列化分支失败**（`serialize()` 对未知 source kind 的处理），错误在 transport 层被包成 TRANSPORT 抛出。
3. **顺序假象**：两次运行的差别其实来自 mock 状态文件里 `firstMemoryId` 未记录导致走了不同分支；先用干净 state 各跑一次对照。

**建议的下一步命令序列**（每项单独跑、单独看日志，不要串成一条）：

```bash

#    → 期望 ok 无记忆注入
# 2) 跑一次 remember 场景，确认内核 memories 有一行 active
# 3) 跑「用中文回答我」注入场景 → 断言 mock-state.json 的 sawPluginMemory 为 true
#    若仍 TRANSPORT：先 curl 直接打 mock 复现，再看 /tmp/mock.log
# 4) 注入通过后依次跑：纠错流程 → 遗忘流程 → 取记忆 <id>
```

## 4. 交接禁区与注意

1. 官方 clone、三个上游仓库只读；根仓库不要递归 `git add .`。
2. mock 模型的任何成功都不等于「真实模型连通」；真实端点在无凭据时必须写「未验证」。
3. `migrations/0001_init.sql` 禁止回改；新增持久字段一律新迁移文件 + 同步 `SCHEMA_VERSION`。
4. Windows 下编译前先确认 8791 端口无监听（`memoryd` 会锁 `target/debug/memoryd.exe`）。
5. `helpers`：本机 `rm` 会触发 safe-delete 钩子（批量/特定路径会失败），删文件失败时改用 python `os.replace` 或 `os.remove`。

## 3. Prompt 组装与注入事实（D6-4 依据）

### 3.1 preStep 顺序

`packages/core/agent-loop/src/agent.ts`：

- `preStep()` `:267-286`：先 `this.loopCtx.systemPrompt.assemble(assembleContextFor(this, signal))`（`:272`），再 `dispatch.waterfall('agent/pre-step', { messages: claimed, ...position, signal }, ...)`（`:276-282`）。与 doc6/11 §3.1 一致。
- **默认** enter decision 是 `messages: context === undefined ? claimed : [...claimed, context]`（`:278-281`）：loop 自带的 runtime-context 快照追加在 claimed **之后**。doc6/11 要求的「记忆上下文在原始用户正文之前」不能靠注册式 `systemPrompt.context()` 实现，必须在 `agent/pre-step` 监听里重写 decision.messages（见 3.4）。

### 3.2 AssembleContext 与 dispatch

- `packages/core/agent/src/dispatch.ts:174-176`：`assembleContextFor(agent, signal)` 返回 `{ agent, scope: agent, ...signal }`。与 doc6/06 §3 一致。

### 3.3 system-prompt 注册表

`packages/core/system-prompt/src/index.ts`：

- `AssembleContext` `:42-50` = `{ scope?: ScopeKey; signal?: AbortSignal }`；`agent` 字段由 `assembleContextFor` 通过模块扩展带入。
- `PromptSection` `:52-76`：`text: string | ((context) => string)`——**同步 provider**（`:66`）；`complete?: boolean` `:75`。
- `PromptContext` `:78-86`：「Dynamic model context materialized as a durable user-role snapshot」——注册式 context 就是 user-role 快照，与 doc6/11 的角色分层假设一致。
- `complete:true` 语义 `:597-634`：装配后恢复该 section 为**唯一** system prompt section；多于一个 complete section 直接抛错（`:598-600`）；waterfall 后被强制恢复（`:629-634`），监听者不能借 assemble waterfall 替换 complete prompt。官方组合中当前仅 `packages/bundle/web-app/presets/minimal.patch.yml:15` 使用 complete；headless/CLI 组合无 complete section，Soul section 可正常追加（D6-4 仍须在真实 profile 复测）。
- assemble waterfall 是异步的 `:625-628`（`'system-prompt/assemble'` 事件声明 `:31`，返回 `Promise<PromptAssembly>`，返回值 authoritative）——**异步获取 Soul 的正确挂点**。注册式 section 的 text provider 是同步的，不能在里面做 HTTP。
- effect 注销：`SystemPrompt.section()/context()/tools()/variable()` 全部经 `this.layers.effect(...)` 返回「the exact Cordis effect disposer」（`:454-463` 等）；注销触发 `system-prompt/change`（`:417`）。满足 D6-4 的 HMR/卸载销毁要求。
- `joinContextSections` `:303-307`：拼接时加固定边界文本「Current runtime context. This snapshot supersedes earlier runtime-context snapshots.」——loop 自有 runtime context 的模型可见边界。

### 3.4 user-role 注入消息的持久化与来源

`packages/core/agent-loop/src/runtime-context.ts`：

- `RuntimeContextProjection.project` `:152-163`：runtime context 以 `createUserMessage({ source: { kind: 'runtime-context', form: 'snapshot', sections } })` 生成——**带来源的 user message**，会被持久化为 `user/message` 事件（满足官方「Model-visible ⟺ logged」不变量）。
- `MessageSourceMap` 通过 declaration merging 扩展（`:13-17` 先例）——插件可声明自有 source kind。本项目适配器已经这样做了（见 §8）。

- wire 边界：`packages/llm/llm-deepseek/src/serialize.ts:123-127` 只传 `role`/`content`（tool→user 折叠、同 role 合并），`source` 不上线路。与 doc6/11 §3.4 一致。

## 4. compact 事件真实 emitter（D6-7 依据）

- 类型：`SessionStartSource = 'startup' | 'resume' | 'clear' | 'compact'`（`packages/core/agent/src/runtime-types.ts:125`）；`agent/created` payload 声明 `source`（`:261`）。
- **运行时 emitter 只有两个**：`packages/core/agent-loop/src/index.ts:744` 传 `'startup'`（createAgent）、`:879` 传 `'resume'`（resume 路径，`setupAndPublish` `:754-780` → `prepared.publish(source)` `:624` → `agents.announce`）。全仓搜索无任何 `'compact'`/`'clear'` 作为 source 的调用点。**`agent/created` source='compact' 不可用**——doc6/10 §8「类型存在不能证明运行时真的发出」的预判成立。
- 真实 compact 信号（持久、可监听）：
  - `packages/compaction/compaction-basic/src/region.ts:210` `session.append('compaction/start', lifecycle)`、`:237`/`:245` `compaction/end`、`:491` `compaction/summary`——均为持久 session 事件，事件类型声明在 `packages/compaction/compaction/src/types.ts:24/34/72`。
  - 自动触发器：`packages/compaction/compaction-basic/src/index.ts:148-176` `_registerAutomaticCompaction` 在 `agent/pre-step` 上做压力检查（`compactIfNeeded(agent, 'pressure', signal)`，默认阈值比 0.8，`config.ts:19-23`），`:190-210` 在 `agent/request-error`（CONTEXT_WINDOW_EXCEEDED）上做 overflow 恢复。**运行时确实会自动 compaction**。
  - 手动触发：`/compact` 命令（`packages/compaction/command-compact/src/index.ts:103`）。
- **D6-4/D6-7 结论**：compact trigger 应监听 `session/event` 的 `compaction/start`（或 `end`）事件，不能依赖 `agent/created` source。

## 5. 持久定时调度与后台执行（D6-7 依据）

### 5.1 schedule（持久定时）

`packages/schedule/schedule`：

- 定位「Host-wide durable reminders and shared human/model management」（`src/index.ts:1`）；任务存 durable storage domain（`scheduleDomain`，`src/storage.ts`），「only explicit deletion removes a task」（包 AGENTS.md）。
- 运行时 `src/runtime.ts:20-70`：宿主单 timer（`MAX_TIMER_DELAY_MS` 分片），`requestDrive()` 重算最近到期任务；启动时扫描 active tasks 并排定下一次目标（包 AGENTS.md：「One Host runtime scans active tasks at startup」）；到期经由既有 Session controller resume 会话投递（producer kind `schedule`，`runtime.ts:6` 自有 source kind）。
- web bundle 默认禁用 shipped schedule（`f9564a0d48`，仅 `packages/bundle/web-app/cordis.patch.yml`）；CLI profile 需在组合中显式装载 `@deepseek-ai/dsh-schedule` 才有该能力。
- **结论**：Auto Dream 定时器可以走 schedule 域（durable、重启恢复），也可由适配器自持 timer + spool 持久化兜底；两条路都不需要新宿主能力。D6-7 设计卡二选一并记录。

### 5.2 jobs / jobs-local（后台作业）

- `ctx.jobs` 是抽象 seam（`packages/jobs/jobs/src/index.ts:85-110`）；**唯一实现 jobs-local 全内存**：「keeps every job — lifecycle state, the bounded output ring, and the model cursor — in memory」（`packages/jobs/jobs-local/src/index.ts:3-5`），不跨重启持久。
- **结论**：Dream job 的持久状态必须存 memoryd（`0008_dream_jobs.sql`，本来就是设计）；DSH jobs 只能当进程内执行句柄，不能当账本。与 doc6/10 §5 一致，无冲突。

### 5.3 subagent（后台子 Agent）

- `ctx.subagents` seam（`packages/subagent/subagent/src/index.ts:1-30`）：`start`（one-shot run）+ `startContinuable`（durable continuable child）；多 provider（spawn-in-process / fork / acp / claude-code / codex）。
- continuable child：`ContinuableStartSpec`（`src/types.ts:31-43`）带可选预留 `childId`；「durable continuable child」由 continuation manager 持有 handle，有自己的 inbox（`src/index.ts:15-22`）。
- 生命周期恢复：missing direct child 冷恢复走常规 continuation 生命周期（`src/continuation.ts:194-197`），`coldResume` `:406`；`SubagentRunInfo` 注明「a persisted Activation cold-resumes」（`src/types.ts:86-87`）。恢复是**父侧消息投递驱动**（sendMessage/queuePrompt），child 不是独立 daemon。
- **结论**：存在可用后台 dispatch seam，**不需要停在 D6-0 征询 runner 部署方式**。D6-7 可选：(a) continuable Dream child（由 schedule/timer 投递驱动）；(b) memoryd 自驱受控 worker（不依赖宿主进程存活）。两条都在 doc6/10 §8 预设范围内；选定前按卡要求向用户报告选择点。**不得把普通 extraction worker 改名为 subagent** 的红线不变。

1. **Soul section 的挂点是 assemble waterfall，不是注册式 section**。注册式 `systemPrompt.section()` 的 text provider 是同步的（`system-prompt/src/index.ts:66`），无法在其中 `await GET /v1/soul`。D6-4 须在 `system-prompt/assemble` 异步监听中取 Soul 并 push `{name:'agent-memory:soul', ...}` section（waterfall 返回值 authoritative，`index.ts:625-628`）。doc6/06 §3 接线建议第 1 条「system-prompt/assemble」正是此意，本文将其钉死为唯一可行实现。
2. **`agent/created` source='compact' 无 emitter**（§4）。doc6/10 §8 的怀疑成立：compact trigger 只能挂 `session/event` 的 `compaction/*` 持久事件。doc6/10 §8 原文是「沿 driver 到实际 emitter 核实」，与本文结论一致，规范文本无需修改。
3. **prepend 语义必须由 pre-step 重排实现**（§3.1、§3.4）。loop 默认把 runtime context 追加在 claimed 之后；注册式 `systemPrompt.context()` 得不到「在原始用户正文之前」。`PreStepDecision.enter.messages` 可任意重排（`runtime-types.ts:112-119`），注入消息用适配器自有 source kind（现有 `"agent-memory"` kind 已按 v4 会话格式扩展，见 §8），持久化天然满足 Model-visible ⟺ logged。适配器 L0 管线必须继续排除 `source.kind==='agent-memory'` 的事件（现有 events.ts 已按 `source.kind==='user'` 采集，注入不回流）。

另记：`complete:true` 若未来部署组合引入（如替换 web minimal preset），Soul section 会被静默丢弃——D6-4 验收项「官方 DSH 进程 + mock 确认 outbound system/user role」覆盖此点；若命中即在 D6-4 报不兼容并停止宣称人格注入（doc6/08 D6-4 卡原文要求）。

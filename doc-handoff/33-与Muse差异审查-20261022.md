# 33 · 与 Muse 差异审查（2026-10-22）

审查对象：分支 `Riko-Muse`、HEAD `bbabe12`（现场核对）。方法：三路只读审查（内核 `riko-memory/`、宿主 `riko-dsh/`、仓库文档自述），与 Muse 侧可观察行为对照。标注约定：**事实**＝代码或文档可直接核对；**判断**＝璃的评估，不是代码结论。

配套更新：本机官方 DSH clone 已于同日由 0.2.1-alpha.1 升至 **0.2.1-rc.2**（`~/workspace/src/deepseek-harness`，HEAD `687f282e86`），适配器基线问题见 §3.2。

## 0. 总判断（判断）

双生目前高保真克隆的是 Muse 的**记忆数据库**：claim 原子、逐字 span 证据、哈希冻结、supersede 版本链、forget/purge 闭包、可见性谓词——这一层甚至比 Muse 更严格，是风格优势，应保留。

达不到「Muse 那种感觉」的差距不在这层，在它上面的三层：**没有模型做跨记忆提炼、后台只有判定没有执行体、常驻注入的形态与预算装不下一个人格**。外加一笔总账：真实闭环从未验证过。

## 1. 第一档：感觉的直接来源

### 1.1 没有任何代码路径在做「跨记忆提炼」（事实）

- `alignment synthesis` 是 Rust 确定性模板渲染：窗口、纠正轮次/用户轮次/无纠正率三指标、open 修复线程清单、一句固定指导语。代码注释自述「确定性渲染……非模型生成」（`crates/memory-store-sqlite/src/alignment.rs::render_synthesis_body`）。且 compose 接口 `include_alignment` 缺省 `false`。
- `compact_v1` / `facet_v1` / `context entries` 全部是 claim **逐字摘录或逐字拼接**，模块注释明示「不做概括、不拼接；模型生成的多源综述属 V2-B1」，而 V2-B1 同样不调用模型——该能力在树内不存在（`crates/memory-store-sqlite/src/derived.rs:1-5`）。
- 树内仅有的模型文本生成：单条候选的抽取、rewrite、裁决（`dream_worker.rs` / `worker.rs`）。
- Muse 对照：对齐综合由后台 LLM 读近期事实后写成带立场的相处指南，每日更新并常驻注入；dreaming 作业把复盘提炼成行为指南。**判断**：用户体感里的「她理解我」主要由这一层产生；双生这一层是空的。

### 1.2 后台闭环只判定、不执行（事实）

- 内核 `schedule` 是纯函数判定（upkeep/relationships/quiet/nightly 四开关），`background_due` 由 Rust 查库算信号；`/v1/tasks/due` 注释明示「只回答该不该跑，不入队、不调用模型」，`/v1/tasks/run` 只落回执。执行体在内核之外，而之外没有人接。
- 宿主侧 `riko-dsh/src/schedule.ts` 实现了 cron 式调度器，但 `src/` 内无人 import（仅测试直测），文件头自述任务纯内存、不跨重启；`client.ts` 对 `tasks|refresh` grep 零命中——适配器从不调用 tasks，也从不主动触发 derived/relationships refresh。
- Dream 唯一自动入口是事件寄生：宿主 compaction 后入队 trigger，`DreamRunner` 靠顶层 Agent `agent/pre-step` 在线期间轮询 claim；**无父 Agent 在线时，作业只滞留在 memoryd 队列**（`riko-dsh/src/dream-runner.ts`、`src/events.ts`）。仓库记录一致：DSH seam「足以改消息＋加工具，不足以新增调度 child」（doc-handoff/31）；「谁来按 /v1/tasks/due 入队仍未定」（doc-handoff/30 §6.4）。
- Muse 对照：7 个专用后台任务（dreaming/relationships/studying/skill review/quiet 等）在用户不说话时各自运行，是连续性的主要来源。**判断**：「离线也在活着」这件事双生目前为零。

### 1.3 常驻注入的形态与预算（事实）

- 双生 bundle 总预算 `BUNDLE_TOTAL_CHARS=4000`（compact ≤1200 / alignment ≤600 / relationships ≤8 条 / retrieved 取剩余），以**独立 user-role 消息**前插在用户消息之前（`riko-dsh/src/recall.ts::makeBundleHook`），适配器端不做二次裁剪。
- Muse 对照：SOUL、IDENTITY、USER、MEMORY 全文 + people/groups 索引 + 对齐综合以常驻文件形态每轮在场，量级是数万字符，且人格部分位于 system 层。**判断**：4000 字符的用户消息前插装不下「一个人」；这是预算与形态的双重差距，不只是调大数字的问题。

## 2. 第二档：能力缺口

### 2.1 语义召回半成品（事实）

- memory/page 向量真算真用（独立 semantic 支路并入 bundle，词法支路 FTS5＋CJK 二元字＋RRF k=60）。但 entry 向量只完成绑定/入队，worker 对 memory/page 以外 kind 一律判 `dead`/`BAD_KIND`，永远不计算（`crates/memory-server/src/dream_worker.rs:1116-1181`）。
- 整条语义支路以 embedding 端点已配置为前提；未配置即整体关闭，且裁决作业要求 chat 与 embedding 同时可用，否则停在队列。
- 质量：语义门槛 0.3 落地后重跑，无关 query 仍误召回（E12 继续失败，README/doc-handoff/19 §8）；真实语义召回质量未验证（doc-handoff/32 冒烟 `semantic=unavailable`）。向量检索是 ready 集有界余弦全扫，无近似索引。

### 2.2 抽取质量证据单薄（事实）

- `extract_v4`/`admit_v4` 已实现（两阶段，held 候选才进 rewrite，准入 11 道确定性门）。全部质量证据：同语料、同模型（Gemini 3.5 Flash Lite）、15 条样本，v3 基线 0/14 active → v4 7/15 active（doc-handoff/25 §9）；黄金测试夹具仅 6 条规则级样本。仓库明示不做大规模基准。
- **判断**：47% 的 active 率意味着一半的用户事实进不了记忆，这会直接被体感为「她记不住」。

### 2.3 人格层双轨（事实）

- 文件版 twin-soul：`riko-dsh/soul.md` 经 `ctx.systemPrompt.section` 以 order=100 进 system，全进程一份、**无任何隔离**，热重载（`riko-dsh/src/soul.ts`）。内核版 Soul：按 `agent_id` 隔离、order=10300（`makeSoulAssembleHook`）。发货 preset 下两者会同时进入 system prompt。
- `riko-dsh/alignment.md` 是手写静态文件＋热重载，以 user-role 注入；与内核 alignment synthesis **同名异物、零数据通路**（`alignment.ts` 无任何 HTTP 调用）。仓库 AGENTS.md 的 D6 边界写的是「只有 Soul 进入 system、Soul 按用户+Agent 隔离」，与文件版的实际形态不一致。

### 2.4 关系图谱覆盖窄（事实）

- `entity_v1` 确定性投影只识别两种句式（`<REL>叫<NAME>`、`<NAME>是我的<REL>`），代词/多候选一律不建实体（doc-handoff/29）。THIRD_PARTY 门使第三人候选大面积 held，完整人物事实覆盖受限，仓库自述为「政策结果」、政策本身未决定（Muse-V2/00「与 Muse 的明确偏离」）。
- Muse 对照：people/groups 是 LLM 维护的完整人物档案 + 索引先行纪律，关系事实不依赖句式命中。

## 4. 建议的迭代顺序（判断，待用户拍板）

- **P0 · 真实闭环验证卡（不写新功能）**：以 DSH 0.2.1-rc.2 为新基线做正式源码核对 → 真实模型 + 真实对话跑通「写入 → 抽取 → 裁决 → 注入 → 纠正」全链，产出验证记录。理由：§3.1 的总账不清，后续所有迭代都建在未验证的地基上。
- **P1 · 模型提炼生成器（新版本作业，不动冻结版本）**：给 alignment synthesis 与 dream reflection 增加 LLM 生成路径（带来源引用、版本链、授权门沿用现有骨架），目标是产出带立场的相处指南而非指标模板。理由：§1.1 是「感觉」的核心缺口。
- **P2 · 宿主调度驱动**：解决「谁执行 tasks/due」——先核 rc.2 的 jobs seam 是否仍全内存，再决定自建持久调度还是等上游。理由：§1.2 决定离线连续性，是 P1 产出能自动运转的前提（也可与 P1 并行做核对部分）。
- **P3 · 注入预算与形态**：在 P0 的真实数据上评估 4000 字符预算的实际截断情况，再决定扩容与分段形态，避免无数据调参。
- **P4 · 抽取质量扩样**：把质量语料从 15 条扩到可回归的规模，再谈阈值与 prompt 调整；entry 向量判死问题随手修或明确废弃该支路。

## 5. 不是差距的部分（事实）

- 证据与审计链（逐字 span、content_sha256 冻结、读时逐条复核来源、purge 真闭包、forget 需最新用户证据定位）比 Muse 的可观察实现更严格。这是本项目的既定风格（可信度由 Rust 准入决定），不算缺陷，迭代时应保留，不为追「感觉」放宽。

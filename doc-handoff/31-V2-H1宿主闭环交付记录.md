## 2. 服务端：bundle 分段（加法式，不改旧键）

`POST /v1/context/bundle` 新增 `segments` 数组与 `budget`，**原有 `resident`/`retrieved` 顶层键逐字节不变**：

```
segments = [ compact, alignment, relationships, retrieved ]   ← 顺序固定，空段也出现
budget   = { total_chars: 4000, used_chars: N }
```

- **统一预算** `BUNDLE_TOTAL_CHARS = 4000`，按 compact(≤1200) → alignment(≤600) →
  relationships(≤8 条 / 剩余预算) → retrieved(剩余) 顺序分配；超限段置 `complete=false` 并计 `omitted`。
- **真去重**：compact 段在检索**之前**算好，其 memory_id 并入检索的 covered 集，
  因此 retrieved 从候选道阶段就不再包含 compact 已覆盖的原子来源；`deduped` 计数来自候选合并处。
- **可见性同源**：四段都用 V2-P1 的统一可见性判定与 V2-S1 读域集，不另写口径。
- 空段仍出现（`char_count=0`、`complete=true`），调用方不必猜键是否存在。

## 3. 适配器：分段消费 + 工具

`recall.ts`：有 `segments` 时按序为每个**非空**段前插一条独立 user-role 消息，
`source.form` 依次为 `compact`/`alignment`/`relationships`/`retrieved`，正文仍走 `wrapData` 数据边界；
**没有 `segments` 时回退**到 resident/retrieved 两段（旧服务端行为与 D6 完全一致）。
预算与去重由服务端负责（唯一真相），适配器不再二次裁剪，避免两边口径不一致。

新增工具（都走统一可见性判定）：

| 工具 | 语义 |
|---|---|
| `memory_relationships` | `action=index\|resolve\|get`：索引 → 名称解析（歧义返回候选、不猜）→ 按 entity_id + `expected_version` 读详情（版本不符 409） |
| `memory_facets` | 按需读四分面（缺省四段），非常驻注入 |

`memory_explain` 已在 V2-P1 交付；原有 `memory_search/get/remember/correct/forget` 协议未改。
使用纪律写进工具说明：重要变化即时保存且成功才说保存；相关人物先 get 详情；片段不足先精读；问来源用 explain；歧义不猜。

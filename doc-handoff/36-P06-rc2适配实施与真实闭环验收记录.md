## 2. Embeddings 解码器 index 线索核查与修复

### 2.1 现场复现与根因定位
前任实测 Gemini Embedding 端点（`gemini-embedding-001`）时发现响应首条缺失 `index`。
我们直接向 Google 官方 OpenAI 兼容端点（`https://generativelanguage.googleapis.com/v1beta/openai/embeddings`）发送多条输入测试：
```json
{"input": ["hello world", "second item", "third item"], "model": "gemini-embedding-001"}
```
返回响应结构：
```json
{
  "object": "list",
  "data": [
    { "object": "embedding", "embedding": [...] },
    { "object": "embedding", "index": 1, "embedding": [...] },
    { "object": "embedding", "index": 2, "embedding": [...] }
  ]
}
```
**根因分析**：
这不是代理怪癖，而是 **Google 端点背后的 Protobuf (proto3) JSON 映射规范** 导致的真实行为：
- 在 proto3 JSON 映射中，数值字段如果为默认值（`0`），序列化时会被省略以节约带宽。
- 因此，批次中的第 0 个元素其 `index: 0` 被省略；而后续元素索引为 1、2... 时，非零值被正常输出。
- 在 `riko-memory/crates/memory-server/src/embedding.rs` 的 `decode_embeddings_response` 中，原先的判断逻辑为：
  ```rust
  let indexed_count = parsed.data.iter().filter(|item| matches!(item.index, EmbeddingIndex::Present(_))).count();
  if indexed_count != 0 && indexed_count != parsed.data.len() {
      return Err(EmbeddingError::BadJson);
  }
  ```
  在 batch > 1 的情况下，`indexed_count` 恰好是 `len - 1`，既不等于 0 也不等于 `len`，被直接判定为 `BadJson` 报错拒收！

### 2.2 修复与测试
在 `riko-memory/crates/memory-server/src/embedding.rs` 中增加了对 proto3 零值省略的明确支持：
- 判定 `is_proto3_zero_omitted`: 当 `indexed_count == len - 1` 且没有任何 item 拥有 `index == 0` 时，判定第 0 项为被省略的 `index: 0`。
- 补充单元测试 `accepts_google_proto3_default_zero_omitted_batch`。
- 同时在 `Cargo.toml` 中为 `reqwest` 启用了 `"rustls-tls-native-roots"`，解决 Linux 容器环境下对官方根 CA 的信任加载问题。
- `cargo test --workspace` 全绿（160 passed in store tests, 6 passed in embedding tests, 0 failed）。

### 4.1 多轮对话验收过程
1. **Turn 1（事实与身份）**：
   - 输入："你好，我叫林晚，是一名在杭州工作的Rust开发工程师。"
   - 模型响应："你好呀，林晚！很高兴认识你喵~ 原来你是在杭州工作的Rust开发工程师呀，听起来好厉害！..."（遵循 Soul 人格设定）。
   - L0 事件捕获：`session_events` 正确入库，flush receipt 正常。
2. **Turn 2（偏好）**：
   - 输入："我平时喜欢喝无糖乌龙茶，不要加奶。"
   - 模型响应确认，偏好事实进入 L0。
3. **Turn 3（明确记忆指令）**：
   - 输入："请记住：以后回答请始终用中文，并保持简洁，先给结论再给理由。"
   - 模型主动调用工具：`memory_remember`。
   - 准入结果：memoryd 准入成功，生成 active 状态记忆 `01a1643b-6cfc-73d5-ade0-558f5e804c42`（kind: `instruction`）。
4. **Turn 4（记忆纠正与 Supersede）**：
   - 首先记录原住址："请记住：我现在住在上海。" -> 模型调用 `memory_remember` 生成 active 记忆 `01a16440-35e5-72bc-bafd-7c63cecdbb67`。
   - 发起纠错："纠正一下：我现在住在上海浦东新区，之前说的上海不准确。请调用 memory_correct 将原先的住址记忆更正为现在的住址。"
   - 模型行为：模型调用 `memory_search` 确认旧记忆 ID 及版本，随后调用 `memory_correct`。
   - SQLite 真实状态：
     - 原记忆 `01a16440-...`：status 转为 `superseded`，version=2。
     - 新记忆 `01a16441-...`：创建为 `active`，body 为 `"我现在住在上海浦东新区"`。
     - 关系表 `memory_relations`：记录 `source_id: 01a16441-...`, `target_id: 01a16440-...`, `kind: 'supersedes'`。

### 4.2 检索与四段注入验收

# 03 官方 DSH 事件映射与本地可靠性

本文件替代 [v1 DSH 接入手册](../doc/14-DSH适配器实施.md) 中依赖旧 checkout 的事件形状假设。HTTP 请求结构仍以 [v1 协议](../doc/12-HTTP协议v1.md) 为准。

## 1. 输入和映射

官方类型在 [session/types.ts](../deepseek-harness/packages/core/session/src/types.ts)：`event.seq` 是会话内连续的非负整数，`event.time` 是 Unix 毫秒数；`session.id` 是会话 ID。`user/message` 的 `event.data` 是完整 `UserMessage`，`assistant/message` 与 `tool/result` 的 `event.data.message` 才是消息。正文只取 `content[]` 中 `type='text'` 的 `text`，按原顺序用换行连接；纯非文本事件不臆造正文。

| DSH 事件 | 文本路径 | 送内核的 `role/source_kind` | 额外条件 |
|---|---|---|---|
| `user/message` | `event.data.content` | `user/user` | 仅 `event.data.source.kind === 'user'`；来源缺失或其他来源绝不可默认成 user |
| `assistant/message` | `event.data.message.content` | `assistant/assistant` | 仅记录可用文本；不作自动 active 的来源 |
| `tool/result` | `event.data.message.content` | `tool/tool` | 仅记录可用文本；不作自动 active 的来源 |
| `turn/end` | 无正文 | 不送 L0 | 只产生一次窗口 flush，经过同会话发送链 |
| 其他事件 | — | 不送 | 本轮没有映射；不可把工具参数、系统 Prompt 当用户消息 |

插件或系统上下文产生的 `user/message` 必须跳过自动用户证据。注入时用 `createUserMessage({source:{kind:'plugin',plugin:'@agent-memory/dsh-adapter',form:'agent-memory'},...})`；事件处理必须要求来源精确为 `user`，不能仅排除一个已知插件名。对于来源字段无效的事件，记录不含正文的 `UNSUPPORTED_SOURCE` 诊断，明确说明该 seq 未接收。若未来要审计这些事件，应扩展协议允许的 source 类别并单独设计，不许静默提升。

时间转换固定为 `new Date(event.time).toISOString()`，事先验证 `Number.isSafeInteger(event.time)`、非负和转换后的 Date 有效。发送 RFC3339 UTC 字符串。`event.seq` 验证安全整数且非负，不自增生成。`host_id` 是稳定安装 ID，`agent_id` 是该 session 对应的官方 `agent.id`；若当前回调只有 session，基于官方 `agent.id===agent.session.id` 用 `session.id` 作来源标记即可，不影响用户 scope。

### 原文证据回填

对每条 `user/user` 事件维护 `(host_id, session_id, event_seq, message.id) → evidence_id`。`evidence_id` 只取内核 200/201 响应；`message.id` 来自 DSH 已提交消息，可帮助工具识别“当前最新原始用户消息”。不得通过文本相等、最后一条正文事件或模型声称找 ID。已 ack 的映射要写入本地 receipt；进程重启后的未 ack 请求仍用原幂等键重放并回填相同 ID。

## 2. 顺序模型

DSH 的 `session/event` 通知发生在事件提交后，回调是同步受保护通知；监听器异常只写 DSH 日志，不撤销原事件。官方 `Session.append` 明确要求热路径不阻塞 I/O，因此插件也不应在回调里执行 `appendFileSync/fsyncSync`。适配器的顺序如下：

1. 同步验证真实形状和来源，确定 `op_id=(host,session,seq)`；把不可变、无令牌 envelope 放入有上限的内存队列，然后立即返回。队列已接收不等于落盘或内核接收。
2. 单一异步写入者按入队顺序把 envelope 写入 spool 并完成文件刷新；仅在确认落盘后才放入发送链。写入者不应在重试网络请求期间占住队列。
3. 一个 session 内按 seq 发送；不同 session 可并发。`turn/end` 也先入队并持久化，必须等待该 session 前序事件完成落盘和 ack 才能发送 flush。
4. 内核 200/201 返回 `evidence_id` 后，先把 receipt 持久化，再认为该 op ack。若 receipt 写失败，保留为待重放；下次由内核幂等处理。
5. `turn/end` 的 `through_event_seq` 取该 session 此前已排队的最后一条正文证据 seq；只有这些事件均已落盘并获 ack，才发送 flush。

现有 [events.ts](../agent-memory/adapters/dsh/src/events.ts) 在 Promise 链里调用 `spool.append`，但没有独立的有界接收队列、落盘完成状态或持续重试；需要把这些状态分开。现有 `Spool.append` 只 `appendFileSync`，没有 `fsyncSync`；异步写入者要明确文件刷新策略，且只能在确认后发送。`acked.jsonl` 只有 opId，不含 `evidence_id`，需要 v2 receipt 格式及旧文件兼容读取策略。旧 ack 格式仅表示“已确认过”，不能伪造 evidence ID；必要时用保存的原请求重发给内核取 200 幂等响应。

**恢复边界：** 回调返回到异步写入完成之间有进程崩溃窗口，不能宣称零丢失。持久化每个已观察 session 的最高落盘 seq；重启后仅针对这些已知 session，通过官方 `ctx.sessionQuery.readEvent({sessionId,seq})` 或 `observeSession` 的异步观察逐 seq 对账，从上次落盘位置补到当前可用日志末尾。先确认该服务已在独立 profile 装载；若未装载、DSH 自身持久层没有保存该事件、session 已不可读或本地光标也未落盘，记录 `CAPTURE_GAP` 并要求人工处理，不伪造证据。不得在热路径调用同步历史读取。恢复读取只用于找缺口，仍须按本文件的 source.kind 和文本规则重验，使用原 op_id 幂等提交。

**落盘顺序与上限：** 内存队列先以 1024 条或 8 MiB 为上限，任一达到即拒绝新捕获并记缺口；磁盘上限仍为 100 MiB。写入者对每条 envelope 先追加并刷新 spool 文件，成功后才更新该 session 的已落盘 seq 光标；光标写到临时文件并刷新后原子替换。若崩溃发生在 spool 写完而光标更新前，对账可能再次加入同一 op，必须按 op_id 去重；若光标已前进，该 op 必须已经可从 spool 恢复。`turn/end` envelope 和用户正文一样受此顺序约束。启动时先扫描既有 spool 与 receipt，重建发送队列，再对已知 session 做限量补录。首次捕获的 session 如果还没形成任何持久记录便崩溃，适配器无法枚举这类未知 session；该风险要在运行状态中列为未覆盖窗口，不能写成自动恢复。

## 3. 失败状态与重试

| 情况 | 状态与动作 |
|---|---|
| daemon 暂时离线、超时、429、5xx | op 保留未 ack；指数/有限延迟重试并节流日志；不需要重启 DSH 才会再次发送 |
| 401 | 暂停该令牌所有出站发送并报告配置问题；不删 spool，换令牌后可继续 |
| 400/409 | 标记明确的永久异常及 opId/requestId；停止该 session 后续 flush，等待修复映射或冲突，不循环重试 |
| 本地 spool 写失败或队列/文件超过上限 | 明确记录捕获缺口与 seq，停止记忆捕获并启动上述异步对账；保留已写文件，不向 DSH 宣称该事件已经被 memoryd 接收 |
| receipt 写失败 | 内核可能已提交；保持 op 未 ack，下次重发；绝不删除原请求 |
| 进程退出/HMR 卸载 | 停止新操作，最多等待 5 秒，未 ack 留盘；释放定时器、文件句柄与注册 effect |

同一 session 的前项失败时，不得发送后项 flush；否则内核可用不完整 L0 窗口建立 `succeeded` 作业，以后补到的事件不会被该窗口重算。不同 session 不应因一个坏 op 全局停顿。自动重试只处理可恢复网络/服务错误；如果一个 op 是固定 400/409，改进模型或增加重试次数不会修复它。

**原子性限制。** DSH 日志提交、适配器本地 spool 落盘、Rust SQLite 提交属于三个不同持久边界，无法由一个事务覆盖。DSH 捕获失败时不能声称“零丢失”；v2 必须有可见缺口日志和状态。官方 [Session 事件读取决定](../deepseek-harness/.agents/notes/implemented/architecture/2026-09-09-deprecate-synchronous-session-event-reads.md)禁止新代码用 `snapshotEvents/ownEvents/eventAt` 同步扫描历史；官方 [session-query](../deepseek-harness/packages/session-query/session-query/src/index.ts) 提供异步 `readEvent/observeSession`，用于上面的定点对账。对账必须有数量与时间上限，不能悄悄扫描全部历史。

## 4. 边界和最小检查

- 文件上限默认 100 MiB，计算 `events` 与 receipt 总保留量；压缩要先确认未 ack 操作及已 ack 的近期证据映射仍能恢复，使用临时文件/替换流程并在 Windows 验证。达到上限时不静默删除唯一副本。
- spool 目录只允许当前操作系统用户读取；请求与日志不含 token，但事件正文属于敏感数据。按用户/安装分目录，不能共享一个 spool 给不同 token。
- 只验证短路径：构造一条官方形状的 `time:number` 用户事件；断开内核后异步写入者确认落盘；重新连接不重启适配器得到 201；再次发送得到 200 和相同 `evidence_id`；先前 event 未 ack 时 `turn/end` 不能抢先 flush；插件来源事件不能得到 `user/user`。进程在落盘前退出的场景只在 DSH 日志确实可读时验证定点对账，不把无法恢复的缺口算成成功。

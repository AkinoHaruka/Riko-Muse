# 03｜人格与常驻记忆

## 1. `soul.md` 的具体语义

一个 soul 是 `(tenant,user,agent_id)` 下的一份用户编辑 Markdown。它描述该 Agent 在与该用户交流时的身份、表达风格、长期工作原则；不自动搬运用户事实或对话摘录。可写中文标题、段落、列表；导入时把正文作为整体保存，不解析 Markdown 指令为新的数据库事实。用户可完全清空它。

首次配置示例（示意文本，无私密信息）：

```markdown
# 角色
你是我长期使用的编程助手。解释方案时先给结论，再说明关键取舍。

# 边界
对不确定的事实明确说不确定；保存记忆后给出可核对的回执。
```

导入流程：用户编辑本机 `soul.md` → `memoryd soul import --config ... --tenant ... --user ... --agent ... --file ... --expected-version N` → Rust 校验大小/UTF-8/版本 → 保存当前版和用户历史版本 → 返回 version/hash。成功更新既有 Soul 后，按 [14](14-记忆修改审计方案决策.md) best-effort 写一条 L3 `memory_audit` 元数据行；审计失败告警，不回滚 Soul 更新。CLI 必须要求既有文件的 expected-version，初次创建用 `0`；没有 `--force` 隐式覆盖。HTTP 写接口如需为 UI 提供，也必须 Bearer scope + CAS，不向 DSH 模型暴露默认写工具。`export` 生成可再导入的正文，版本另写 sidecar 或命令输出，不能把内部 YAML frontmatter 偷塞进用户原文。

DSH 在 `system-prompt/assemble` 读取对应 agent 的 soul；只添加一个具名 section `agent-memory:soul`，不是 `complete:true`，不覆盖 Harness 已有身份、工具指引或用户设置的 persona。section 正文带清楚的边界与版本标记；注册/销毁遵循 Cordis effect。主体必须来自本进程配置的 user token 和宿主 Agent ID，不能信任模型说“现在我是另一个用户”。

**静态/动态顺序事实**：官方 `deepseek-harness/packages/core/agent-loop/src/agent.ts:267-285` 先 `systemPrompt.assemble()` 后 `agent/pre-step`。因此 pre-step 请求得到的 soul 不能补入同一步 system prompt。实现应在 `system-prompt/assemble` waterfall 异步读取 soul；先按 `08 D6-0` 核对 `AssembleContext` 的 agent/scope 类型及 hook 注册生命周期，再落代码。若该 API 不能提供可信的 agent ID，停止 DSH soul 接线并记录冲突，不能把另一个 Agent 的 soul 当默认值。

## 2. `memory.md` 的具体语义

`memory.md` 是服务端 resident selection 的**人可读导出**，每轮注入用同一选择函数按当前状态实时构造。它不是一份会被后台覆盖的人手编辑文件。用户改变它的方法是 pin/unpin、remember/correct/forget、调整预算；导出让人能审阅“Agent 每轮看到哪些长期信息”。

格式示意：

```markdown
# 长期记忆

- [memory: <id>] 我喜欢先看结论，再看原因。
  来源: <evidence-id>；状态: active；选择: pinned
- [memory: <id>] 以后回答请先给结论。
  来源: <evidence-id>；状态: active；选择: active_instruction
```

真实导出必须 escape 会改变 Markdown 结构的用户正文，不把 L0 整篇消息导出。可选头部列出生成时间、scope 指纹、预算、`included_ids/omitted_ids`；绝不写 token/hash/密钥。文件名可为 `memory.md`，路径由用户传给 CLI。直接编辑导出的文件不会自动写回；CLI 应在输出中清楚提示编辑入口，避免两个权威来源。

## 3. resident 选择算法 v1（Rust 纯函数）

输入：认证 scope、当前 UTC 时间、`max_items`、`max_chars`。从同一 SQLite 读事务中读取全部 enabled pin 和有界 active 候选，查规范表最新 claim、版本、valid_until 与证据引用。候选排序固定：

1. 当前仍 active、未退休且未过期的 **pinned** 项，按 `position ASC, memory_id ASC`。
2. 用户明确 pin 的已发布派生文档（问题画像或主题页），按 `position ASC, page_id ASC`，仅在所有来源版本仍有效时显示，正文标明文档类型及 source IDs。
3. 尚未选中的 active `instruction`，按 `updated_at DESC, id ASC`；**没有固定“最多两条”**。未 pin 指令也受总预算限制，省略 ID 可见。

未 pin 的 `fact/preference/episode` 默认只在动态检索中出现，不能按最近更新时间自动塞进 resident。`resident suggestions` 从 active fact/preference 按 `updated_at DESC,id ASC` 给出有界列表及来源，让用户审阅后 pin；建议本身不改变上下文。这样不会把一次直写的短期事实仅凭“最新”变成每轮常驻。

对每条完整渲染后计数。若加上会超出条数/字符预算，则跳过该条并追加 `{memory_id, reason:'ITEM_LIMIT'|'CHAR_LIMIT'}` 到 `omitted`，继续看后续短条；不截断半句话。即使 pinned 也可能超预算，必须显式在响应与诊断中说明。注入中每条携带 ID/来源；**不把裸记忆正文升级为 system 指令**。`kind=instruction` 仍是用户指令类记忆，出现在 sourced context 中，和用户编辑 soul 分层。

已知 `memory_relations.kind='contradicts'` 的两个当前 active ID 若都进入候选，bundle 不擅自选一个赢家：返回 `conflict_ids`，正文标示“待纠错，不能据此断言唯一当前状态”；默认两条都不进入 resident 正文，以免每轮重复错误指示。其他尚未建 relation 的语义冲突不能被算法假装已识别。冲突本身不会更改 L1。

## 4. 每轮必须重新检查的条件

`memories.status='active'`、不存在 `memory_retirements` 覆盖、`valid_until IS NULL OR valid_until>now`、同 scope；已 forgotten/superseded/expired/retired 或跨 scope 的 pin 仍可作为历史记录存在，但不可展示给模型。correct 产生新 ID 时旧 pin 不自动迁移，返回 `pin_needs_review` 诊断，由用户决定是否 pin 新 ID。forget/retire 后即便 `resident_pins` 行还在，也不得通过导出/API/注入读到旧 claim；retire 只能经显式 restore 恢复，purge 则移除目标及相关依赖，见 [12](12-遗忘、过期与时间衰减方案决策.md)。

派生文档只在用户明确 pin 后进入 resident，使用独立 `resident_page_pins`，不以 `resident_pins.memory_id` 假装支持 page。每次渲染重新核文档当前版本与全部来源，失效时从正文省略并返回 `omitted:{page_id,reason:'STALE_SOURCE'}`；模型生成内容标记为派生资料，用户可据 ID 查看原子来源。

## 5. 本机管理动作

建议 CLI 子命令：

```text
memoryd soul show/import/export/history --config ... --tenant ... --user ... --agent ...
memoryd resident pin/unpin/move/list/export --config ... --tenant ... --user ...
memoryd resident page-pin/page-unpin --config ... --tenant ... --user ... --page ...
memoryd resident suggestions --config ... --tenant ... --user ...
```

HTTP 只读与写接口见 [06](06-协议与DSH接线.md)。CLI 在连接数据库前警告 `Store::open` 会触发迁移；迁移版本与二进制不匹配时拒绝旧版命令直接打开。`resident list` 输出 ID、顺序、当前可用/省略原因，不打印被忘记的正文。`memory_audit` 只写 layer、action、目标 ID、认证 scope、可用的宿主 Agent/task 关联、版本、时间和 request ID；不写 actor 类型或旧/新正文。Resident pin 操作不属于该审计表范围。

## 6. 故障语义

- memoryd 离线：DSH 本轮不使用上轮缓存的 resident/soul，记录一次结构化降级，继续会话；不能把已经忘记的记忆从进程缓存带回模型。
- resident、Soul 与用户 pin 的页面不接受年龄衰减；pin 表示用户显式要求常驻，直到 unpin、状态失效或 purge。episode 的时间排序规则只作用于 Retrieved，见 [04](04-召回与上下文.md) 与 [12](12-遗忘、过期与时间衰减方案决策.md)。
- Soul 导入冲突：原版保持，返回 409 + 当前 version，不自动覆盖。
- resident 预算溢出：业务请求 200，`truncated=true`、`omitted_ids` 非空；不是“全部注入成功”。
- memory 索引损坏：resident 从规范表读，仍可用；动态检索标 `index_degraded`，两者分开报告。
- 派生知识整理模型不可用：已保存的 L1 与 resident 正常，画像/主题文档作业按 [05](05-后台整理.md) 退避；不空掉人格/常驻层。

## 7. Soul 与生成画像的边界

Soul 是用户编辑的人格指令；问题画像（mental model）是 Dream 根据已登记问题和冻结 L1 来源生成的派生知识。二者不可互换：画像不进入 system section，不自动改变 Soul，也不能因“看起来像用户特征”而成为用户事实。画像只可按需召回，或经用户审阅 pin 后进入 sourced user-role resident；编辑画像背后的事实应走 remember/correct，编辑人格应走 Soul 的显式导入。完整融合决策见 [15](15-人格与派生知识融合方案决策.md)。

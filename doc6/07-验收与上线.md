# 07｜验收、观察与部署

## 1. 验收分档

每张任务卡分别报告：**代码存在**、**构建通过**、**确定性本机检查**、**HTTP 实测**、**官方 DSH 进程 + mock**、**真实模型连通与行为**、**已安装部署**。前一档不能代替后一档。不能用“source.kind 已写进内存消息”证明真正上线 wire；需观察模型调用端实际接收的 system/user 内容或官方请求日志。

本页原始 E01—E25 是验收契约。实施状态在 2026-09-28 更新：D6-11—D6-15 已有 Rust/DSH 代码并通过本机固定响应验收；官方 DSH Dream child 的提取、裁决、主题页创建/更新已在合成库执行。当前检查结果、档位边界和未验证项见 [doc-handoff/20](../doc-handoff/20-D6-11-15交付记录.md)。本轮没有真实模型调用、用户库升级或部署。

## 2. 能区分正确与错误的固定情景

先准备两个用户 Alice/Bob、同用户 Agent A/B、两份不同 soul（其中 A 先用“回答先结论”，B 用“先列步骤”），空库起步。所有样本使用虚构身份，不放真密钥/私密正文入 repo。

| 编号 | 操作 | 必须断言 |
|---|---|---|
| E01 | Alice 为 A 导入 soul v1，B 无 soul | A 的 system 有 v1，B 不含 A soul，Bob 不可读取 Alice soul |
| E02 | A 改 soul v2 并以旧版本再次更新 | 下一模型 step 只见 v2；旧 CAS 409；可查 v1 revision |
| E03 | Alice pin 一条居住地事实，B 问无关 SQL | B resident 含该 ID；检索段为空或仅相关项；未 pin 无关 episode 不进入 |
| E04 | Alice pin 超过预算的多条记忆 | 返回 included/omitted IDs 与 `truncated=true`；正文每条完整、无半句 |
| E05 | A 创建与页相关的两条 active L1，整理作业成功 | 一页 published，source 两个 ID+version、可查 revision；L1 原文/状态不被整理修改 |
| E06 | 在整理模型调用期间 correct 源 ID | 旧执行者无权发布；job `stale_input`；新页只能引用新版本 |
| E07 | 使用现有 v1 forget 处理已 pin 且被页/向量引用的记忆 | 下一个 resident/retrieved、页面 API、embedding 搜索都不返回旧 ID 或旧摘要；L0/revision 保持原有保留语义，证据重放不复活 |
| E08 | Bob 用自己的 token 猜 Alice 的 memory/page/soul ID | 全部 404 或空；日志不泄漏正文；Bob 也不能从向量库命中 Alice |
| E09 | 词法零重叠的相关问句 | 开启 embedding 时正确 ID 进入 retrieved；关闭/超时返回明确状态，不伪称语义成功 |
| E10 | 同时有词法、向量，以及已单独定义并启用的图/时间来源候选 | 各启用通道 ID/rank 可追踪；只做一次全局 RRF；若配置 reranker，精排结果可查且不改变状态/scope |
| E11 | embedding 关闭、超时、维度错或 reranker 不可用 | 其余召回通道继续工作；返回具体 degraded status；不把降级称作完整向量召回/成功精排 |
| E12 | 与任何记忆无关的问句 | retrieved 空；resident 仅有本就常驻项；不按最新更新凑满 8 条 |
| E13 | 工具继续执行的 step 无新 user 消息 | soul/resident 仍可见；动态检索不误用 tool/system 或上轮无关 query |
| E14 | L1 来源生成问题画像与主题页，并在来源纠错/失效后再次查询 | 文档可追到来源版本；相关 query 才注入 user-role；绝不进入 system；失效后下一 bundle/检索立即不可见 |
| E15 | 进程重启、spool 重放、重复整理调度 | 无重复 active/derived document/pin；各版本和 job attempts 不被重置 |
| E16 | retire 一条 pinned、已建派生文档且已有向量的 active memory | 下一读立即从 resident、各 recall lane、Dream 输入和派生文档排除；重放与 rebuild 不复活；显式 restore 只在 scope/version/evidence/valid_until 均有效时成功，旧文档/向量不恢复 |
| E17 | purge preview 后目标来源或版本改变，再提交 confirm | preview 只新增短期 token 哈希、不改记忆；stale fingerprint/version 返回 409 且不删任何新数据；重新 preview + 二次确认后按依赖闭包删除，跨用户始终 404 |
| E18 | purge 期间 kill/restart，随后重放旧 spool event | purge job 可续作；目标保持不可读；content-free tombstone 阻止 L0 复活；DB 正文、旧/新候选 quote/claim、revision、derived document、FTS/grams/vector/cache 均不可读 |
| E19 | 关闭 retention 默认配置；再由可信用户/管理员设置小范围正值策略并执行确定性清理 | 默认无自动物理删除；正值策略持久化版本/生效时间后无需逐批 preview/confirm，按 recorded_at/valid_until、共享证据依赖和每轮上限生成可查结果；配置收窄后未开始提交的旧 job 停止，不能误删仍有其他有效证据的 Active memory |
| E20 | 同 query 下近期/陈旧 episode 与 stable fact/preference/instruction 对照 | 近期 episode 仅获得 [12 §6](12-遗忘、过期与时间衰减方案决策.md) 所述有限因子；低相关新记忆不越级，稳定类/Soul/pinned 项无 age penalty，`none` 恢复 base 排序 |
| E21 | 对已有 L1、L2、L3 分别执行 update/delete，并另做 create、L0 写入、pin 和后台 job | 每个已有记录修改只追加对应 `layer/action/scope/agent_id?/task_id?/version/time/request_id` 元数据行；无正文、前后值、actor 或 reason；create/L0/pin/job 不产生 audit 行。模拟 audit 写失败时业务修改仍成功且告警可观察 |
| E22 | purge 带有历史 audit 行、旧候选、新 Dream 候选的 L1 及其派生 L2 页面，然后检查审计与执行账本 | purge 闭包的 `memory_audit`、旧 `audit_events` 中可关联行、候选 quote/claim 与 revisions 一并清除；完成后 confirmation/job 不保留可反查目标的 ID，tombstone 无正文且能阻止旧 spool 复活 |
| E23 | 自动 Dream 定时器及 Held/provider 故障恢复 | 默认 24 小时/15 分钟空闲且有新 user event 才入队；未配置模型/runner 时只保留待处理 L0。成功 Held 在相关新证据到来时用新指纹重裁，同指纹不重复；provider 故障不推进 `processed`，端点恢复后续作冻结输入 |
| E24 | Agent 根据最新用户指令调用 retire/restore | 有效 user event ID 与精确 byte span、目标 scope/version/状态通过；旧事件、伪造 quote、跨用户 ID 被拒；工具回执可核，Dream 无此工具 |
| E25 | 已有用户迁移与新用户创建、问题目录编辑和 Dream 整理 | 每 scope 的问题目录默认空，未显式登记时 Dream 画像结果为 0、主题页可独立生成；用户登记问题后可审阅、改写、归档，版本变化使旧画像下一读立即 stale；Dream 只用当前 active 问题和有效 L1，不能自行创建问题 |

E03/E09 的答案层对照应让“有记忆”和“无记忆”的正确输出不同，例如用户独有的虚构饮食禁忌与特定菜品，而非靠通用知识碰巧猜对。记录 `candidate → active → resident/retrieved ID → wire → answer` 每一段；不同回答不自动算记忆收益。

## 3. 性能与故障预算

本机基线至少量 100、1000、10000 条 active 记忆/用户：resident 读取耗时、词法检索、向量候选、RRF、rerank、bundle 总耗时与内存占用。固定数据集与机器环境，报告 P50/P95，不预先宣称达标。首版保留 Soul 读取 300 ms 失败保护、后台模型调用不阻塞 HTTP、单用户向量候选最多覆盖 10000 ready 对象；**bundle 不设固定延迟预算或 SLA**，只记录实际 P50/P95。query embedding 的 provider 请求超时沿用 `embedding_timeout_secs`（默认 30 秒），不是端到端延迟目标。对象数量超过范围或 provider 请求失败时必须给可诊断降级；耗时偏高时先记录、定位和优化，不因超出未设定的 bundle 目标而提前丢弃语义结果。

故障注入：memoryd 离线、soul 版本冲突、embedding 429/timeout/dimension mismatch、整理 JSON 错、整理过程中 correct/retire/forget/purge、purge job 中断、页面索引 dirty、worker 失租、Windows 二进制被占用。每项核适用的数据保留/擦除语义、`不使用旧 soul/resident/page`、`错误状态可查`。

## 4. 模型使用范围

- 人格/固定/失效可以全用确定性样本与官方 DSH mock 验证。
- 整理 Prompt 和语义召回只需要**一个**用户配置的真实 chat/embedding 端点做小样本验证；不安排模型海试。
- 实际模型的摘要幻觉、错误合并、零词法召回命中率属于质量观察。每例保留 source IDs、job ID、query、injected IDs、模型输出结论（私密正文脱敏），不能从 n=1 宣称整体有效。
- 真实端点不可用时明确记“模型质量未验证”；可先交付不依赖模型的 soul/resident 功能。

## 5. 实际升级顺序

1. 停止将升级的旧 memoryd；只读快照原 DB，记录 `schema_migrations`、L0/候选/active/作业数量、dana 的 `index_dirty` 状态。原有 dana/realtest 库目前仍需独立决定 0003+0004 升级，不把 D6 的部署捆进去。
2. 在文件副本从其实际 schema 版本逐迁移至当前 `0013`，核旧行逐字段不变、历史 forget/replay 抑制语义不变、scope 隔离不变、`rebuild-index` 可恢复，并检查 `0010` 生命周期闭包、`0011` Dream trigger 关联、`0012` child 读取快照和 `0013` page FTS 重建。
3. 新建 schema 13 空库跑 E01—E25 确定性/HTTP；官方 DSH + mock 继续验证 Soul/Resident、retire/restore、受限 Dream child、页面创建与更新、purge 工具不可用；真实模型行为和整体质量另行标注，不能从固定响应推断。
4. 先发布服务端新端点、保持旧 DSH 在旧 compose；再发布支持 capability 握手的新适配器，以独立 profile 开启 v6。发生问题把适配器切回旧 profile，服务端仍可承接旧协议；不要用旧二进制打开新库。
5. 真实用户库升级要单独操作：确认只读快照可恢复、迁移副本通过、端口空闲、worker 已停、索引状态处理方案确定；升级后核服务版本、scope 隔离、旧作业和一条新 bundle。

## 6. 发布用语

“人格已实现”需要 E01/E02/E13 的官方 DSH 实际 system 内容证据。“常驻记忆已实现”需要 E03/E04/E07/E13 的注入 ID 证据。“语义召回改善”需要 E09/E10/E11 的命中、正确沉默和故障降级对照以及真实端点行为。“主题整理可用”需要 E05/E06/E07 的来源、版本和撤销证据；本轮固定响应覆盖了页面来源保存与同页更新，未覆盖真实模型质量、所有撤销故障和部署。只在独立 profile 运行则称“试用”，不能称全局已部署。

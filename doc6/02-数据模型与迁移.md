# 02｜数据模型与迁移

## 1. 当前基线与文件所有权

当前实现 `SCHEMA_VERSION=13`，迁移执行器在 `Store::open` 时自动升级并校验 SQL 文件 SHA-256：`agent-memory/crates/memory-store-sqlite/src/lib.rs:147-245`。`0001`—`0010` 是先前阶段的冻结迁移，D6-11—D6-14 继续新增 `0011`—`0013`。不得让“先运行新版 backup/doctor”意外升级原库；升级前先对关停后的原库做**只读一致性快照**，再对副本运行新二进制并备份。

以下是逻辑 schema 契约和已追加迁移。已写入的迁移文件均按 checksum 冻结；`0011`—`0013` 的实施扩展见本文 §10—§12。

## 2. `0005_soul_resident.sql`

### `memory_audit`

采用 [14](14-记忆修改审计方案决策.md) 选定的 TencentDB 元数据审计方案；在 `0005_soul_resident.sql` 建表，供后续 D6 写入路径使用。

| 列 | 约束/含义 |
|---|---|
| `audit_id` | TEXT 主键 |
| `record_id` | 被修改记录的 ID |
| `layer` | `L1|L2|L3`；分别映射原子记忆、派生知识文档（问题画像/主题页）、用户编辑的 Soul profile |
| `action` | `update|delete`；不提供 create 或自定义动作 |
| `tenant_id,user_id` | 必填认证 scope |
| `agent_id` | 可空关联字段；不可作为认证依据 |
| `task_id` | 可空宿主任务关联；不可作为认证依据 |
| `version` | 更新后的版本；删除时记录删除前已知版本 |
| `updated_at_ms` | 修改时间，UTC 毫秒 |
| `request_id` | 可空请求关联 ID |

为 `(record_id,updated_at_ms)`、`(tenant_id,user_id,agent_id)`、`(tenant_id,user_id,task_id)` 和 `updated_at_ms` 建查询索引。表不存正文、前后值、`reason_code`、操作者类型或完整请求/响应。L0、create、Resident pin 与后台 job 不写此表。审计写失败只告警，不回滚成功的记忆修改；purge 按 [14](14-记忆修改审计方案决策.md) 在擦除流程中清除闭包目标对应的审计行。

`record_id` 的表示固定：L1 用 `memory_id`，L2 用 `page_id`，L3 用本 scope 的 `agent_id`；读取/清理总是同时带 `layer,tenant_id,user_id`，不可把同名 Agent ID 当成跨用户全局 ID。

### `soul_profiles`

| 列 | 约束/含义 |
|---|---|
| `tenant_id,user_id,agent_id` | 复合主键；user scope 外键指向 `principals`；agent_id 为宿主稳定 ID，1—256 字符 |
| `body_md` | UTF-8 Markdown，0—2000 Unicode 标量；空正文代表禁用 |
| `version` | 正整数；每次实际变更 +1；相同内容幂等不增 |
| `body_sha256` | 正文 UTF-8 SHA-256；对账/ETag，不是授权凭据 |
| `created_at,updated_at` | UTC RFC3339 |

`CHECK(version>0)`；正文字符数在 Rust 校验，不用 SQLite `length` 代替 Unicode 标量规则。禁止用全局 `agent_id` 唯一键，会跨用户混淆。`soul_revisions(tenant_id,user_id,agent_id,version,body_md,body_sha256,actor_kind,changed_at)` 是用户查看/恢复历史的内容版本能力；它不替代 `memory_audit`，其正文不复制到审计表。profile 与版本快照按各自写入语义提交；profile update 成功后 best-effort 追加一条 L3 audit。`actor_kind` 只允许 `user_cli|user_api|admin_cli`；无 `model`。

### `resident_pins`

`(tenant_id,user_id,memory_id)` 复合主键；FK 指向对应 scope 的 `memories`；`enabled IN (0,1)`、`position INTEGER >=0`、`pinned_at`、`version INTEGER>0`。同 scope 中 **enabled=1** 的 `position` 唯一（部分唯一索引）；unpin 不删行，置 `enabled=0` 并增 version，重复 unpin 可返回幂等结果，重新 pin 仍沿原行增 version。重排在同事务赋予新 position，若 SQLite 唯一检查妨碍交换，先使用临时偏移或重建该 scope 的位置，不能半更新。pin/unpin 是 Resident 选择配置，不记入 L1/L2/L3 `memory_audit`。pin 可保留在 forgotten/expired/retired 记录上作历史，但 bundle **绝不可使用**；purge 会清理对应 pin，重新激活新 ID 不自动继承旧 pin。

### `mutation_receipts`

`(tenant_id,user_id,operation,idempotency_key)` 复合主键；保存规范化请求正文 SHA-256、结果状态与最小响应 JSON、创建时间。key 为 1—128 个 ASCII `[A-Za-z0-9._-]`，请求在 Rust 解析为强类型后按固定字段顺序规范序列化再哈希。相同键同请求返回原结果；相同键异请求返回 409 新码 `IDEMPOTENCY_CONFLICT`，不产生第二次版本变化。该码在 `memory-contract` 加入；覆盖 soul/pin/page-pin 与本阶段其他新增可重试管理操作，不回改旧 remember 幂等语义。receipts 必须与目标修改在同事务提交；响应中不得包含令牌、原始 L0 正文。

### 不新建权威 `memory.md` 表

`memory.md` 每次由 `resident_pins + memories + memory_evidence + resident_page_pins + memory_pages + page_sources` 按同一读取事务渲染；导出文件只是一份带生成时间/ID 的快照。避免持久副本在 correct/retire/forget/purge/到期后变旧。索引是否 dirty 不影响 resident 对规范表的直接读取。

## 3. `0006_derived_knowledge.sql`

### `memory_pages`

统一保存两种可重建的派生知识文档，避免画像和主题页形成两套来源/撤销权威。字段：`id` UUID 主键；`tenant_id,user_id` scope 外键；`document_kind IN ('mental_model','topic_page')`；`document_key`（同 scope、同 kind 稳定键；画像为已登记问题键，主题页为规范化主题键）；画像另存 `question_version/question_text` 快照，主题页二者为空；`title` ≤80 字；`description` 最多 240 Unicode 标量（`0013` 起用于主题页搜索）；`body_md` ≤1200 字；`status IN ('published','stale','archived')`；`version>0`；`generator_version`、`input_fingerprint`、`created_at,updated_at`。同 scope/kind/key 最多一条 published（部分唯一索引）。模型不能提供 ID、kind/key、question 定义、status/version 或 scope。画像读取时除 L1 来源外，还须核目录中该问题当前 `active` 且 `version` 等于页面快照；问题更新/归档同事务置页 stale 并移除索引，读时复核兜底。

### `mental_model_questions` 与 `mental_model_question_revisions`

画像允许使用的问题键必须来自 Rust 管理的**同 scope 版本化问题目录**，模型不能创建或修改。`mental_model_questions` 以 `(tenant_id,user_id,question_key)` 为主键，保存 question text（1—200 Unicode 标量）、`version>0`、`status IN ('active','archived')` 与时间；key 为 1—64 个 ASCII `[a-z0-9_]+`。`mental_model_question_revisions` 以 scope/key/version 为键保存历次问题正文与状态，供用户审阅；它不是 `memory_audit` 的 L1/L2/L3 对象。CLI 通过 expected version/CAS 执行 add/update/archive/reactivate，归档就是用户“删除问题”的首版行为，不物理删除历史。问题正文/状态改动使原问题画像立即 stale；再次启用按新版本和当前有效 L1 重新生成，旧页面正文不直接恢复。

首版每个 scope 的问题目录**默认为空**。`0006` 迁移和后续 principal 创建都不插入任何问题定义；仅在可信用户/管理员通过 CLI 显式 `add` 后才有 active 问题。没有 active 问题时，Dream 跳过问题画像阶段且结果计数为 0，不生成空画像；主题页阶段独立运行。每份画像仍需 1—20 条同 scope、active、未过期 L1 作为冻结输入。目录写接口不注册 DSH Agent 工具。

### `page_sources`

`(tenant_id,user_id,page_id,memory_id)` 复合主键，双边复合 FK 指向同 scope；`memory_version` 为发布时 L1 版本，`claim_sha256` 为发布时内容摘要。来源必须是当时 active、未过期的独立记忆：mental model 为 1—20 条，topic page 为 2—20 条。读取文档时再验证每个源 **当前** active、版本/哈希一致、未过期；任何不符立即不可见，后台修复只改善可用性，不承担撤销正确性。

### `resident_page_pins`

`(tenant_id,user_id,page_id)` 复合主键及同 scope FK 指向 `memory_pages`；`enabled IN (0,1)`、`position>=0`、`version>0`、`pinned_at`，同 scope 的 enabled position 唯一。只有当前 published 且全部来源有效的页可 pin/渲染；页 stale/archived 时 pin 历史仍在但立即不可见。页面重建后若沿同一 page ID 产生新版本，用户的 pin 保留，但读时必须显示当前 version 与最新 source IDs；若页被归档，不自动迁移 pin 到别的 topic。

### `page_revisions`

`(tenant_id,user_id,page_id,version)` 主键；保存 kind/key、问题定义快照（适用时）、前后文本、source ID/version 列表、生成器版本、actor、时间。旧版只供查看/审计，不能召回；恢复必须按当前有效来源重新生成，不能直接发布历史正文。它是独立内容版本能力；`memory_audit` 只记录已有 L2 文档的 update/delete 元数据，不复制正文。purge 文档时按 purge 闭包清除其 revisions 与关联 audit 行。

### `consolidation_jobs` 与 `consolidation_job_inputs`

作业列至少有 `id/scope/document_kind/document_key/question_version/input_fingerprint/generator_version/status/attempts/run_after/lease_until/claim_generation/error_code/model_name/input_tokens/output_tokens/created_at/updated_at`；question version 对 topic job 为空。状态 `queued|running|succeeded|retryable_failed|dead|stale_input`。幂等使用两个部分唯一索引：`mental_model` 索引包含非空 `question_version`，`topic_page` 索引不包含该空列；两者都包含 scope、kind、key、input fingerprint、generator version。**不得**依赖含 `NULL question_version` 的普通 SQLite `UNIQUE`，因为多个 NULL 不相等，无法阻止重复 topic job。输入表固化 `(job_id,memory_id,memory_version,claim_sha256)`；不得运行时改为“当前所有记忆”，避免重试时输入漂移。claim、续租、过期恢复、代际隔离沿用 doc4 的 job 契约，但不能借用 `extraction_jobs` 的 `(session,window)` 唯一键。

### 页面检索索引

增加 `page_fts`（FTS5）与 `page_grams`，只索引 published 且来源校验有效的问题画像和主题页。索引是派生数据；`rebuild-index` 同时重建原记忆与知识文档索引。更新/忘记源记忆的同一事务将受影响文档置 stale 并删除对应索引行；读取时仍执行源版本校验，防止漏掉某个失效路径。

## 4. `0008_semantic_index.sql`

`semantic_vectors`：`(tenant_id,user_id,object_kind,object_id,model_id)` 主键；kind 仅 `memory|page`；`source_version`、`content_sha256`、`dimensions`、`vector_blob`、`status IN ('ready','stale')`、时间戳。BLOB 为有限非 NaN 的 `f32` 小端数组，长度恰好 `dimensions*4`，所有向量按同一 `model_id + dimensions` 比较；模型切换不能混算。跨表 `object_id` 无法由单一 FK 表达，Rust 写入/查询需校验对象同 scope 和有效状态。

`semantic_jobs` 可复用独立队列，至少持久化对象种类/ID/版本/hash/model_id、状态、重试与 lease generation。correct/retire/forget/purge/页 stale 同事务把关联向量 stale 或删除；查询前仍核规范对象版本与生命周期状态。索引任务失败不会影响 L1 与 resident 的使用。

## 5. `0007_dream_jobs.sql`

Dream 触发和后台执行语义见 [10](10-写入触发与Dream执行模型.md)。本迁移只增加触发、冻结输入和处理账本；不回改 `evidence_events`/`extraction_jobs`。

### `dream_jobs`

至少保存 `id/scope/trigger_kind/trigger_key/agent_id?/host_id?/session_id?/trigger_event_id?/pipeline_version/extract_version/status/attempts/run_after/lease_until/claim_generation/input_fingerprint/model_name/token_counts/error_code/created_at/updated_at`；新 job 的 `extract_version=dream_extract_v1`，旧 `extract_v1/v2/v3` 不用于 Dream。状态至少有 `queued|running|succeeded|retryable_failed|provider_wait|dead|stale_input`。trigger key 幂等；同一 user scope 默认最多一个 running job，多个待处理 trigger 可合并但不能改变已经 running 的输入集合。

### `dream_job_inputs` 与 `dream_evidence_state`

`dream_job_inputs` 固化一个 job 实际读取的 event IDs、role、host/session/event_seq、content hash 和顺序。assistant/tool events 可作为语境输入，但用户记忆证据仍须指向 user-role event。`dream_evidence_state` 以 `(tenant_id,user_id,evidence_id,pipeline_version)` 为键，记录 `pending|assigned|processed` 和当前 job；同一证据不能同时分配给多个 job。`processed` 表示证据已被成功裁决（也包括模型明确给出 not_memory/defer），不代表一定建成 Active。provider 故障期间保持 `assigned`。retry 保留原冻结列表；快照后新入库的 evidence 留给后续 job。

### `dream_candidates` 与 `dream_candidate_evidence`

新 Dream 路径的候选归属 `dream_job_id`，不得把它们写进旧 `memory_candidates`：后者的 `job_id` 有指向 `extraction_jobs` 的复合 FK，不能引用 Dream job。`dream_candidates` 至少保存服务端生成的 candidate ID、scope、dream_job_id、kind、claim、逐字 quote/hash、`candidate|held|rejected|committed` 状态、reason/policy version 与时间；`dream_candidate_evidence` 保存候选到冻结 user event 的 ID 与 UTF-8 byte span，使用同 scope FK。candidate ID 由 Rust 生成，模型只引用该批给定 ID。成功的 defer/conflict 留 Held 及来源版本；新相关证据或用户显式重裁时，新 Dream job 的输入清单可引用同 scope 的旧 Held candidate ID 及其冻结来源，同时加入新 evidence，建立新的 adjudication 输入指纹；旧候选正文/来源不被原地改写，也不把原 L0 再标为 pending。同一候选、相同证据集合与策略版本不得重复裁决。

入队、输入快照与 assigned 状态在一个事务中完成；失败不得推进处理水位。若使用游标替代逐条账本，必须先证明其跨 host/session 单调且不会漏 event；当前每 session 独立 `event_seq` 不能充当全用户 cursor。事件 ID、输入集和结果幂等，主 Agent 直写与 Dream 并发时由同一 scope/claim hash/CAS 规则防止重复。

## 6. `0009_semantic_adjudication.sql`

语义准入与 L1 合并细则见 [09](09-语义准入与记忆合并设计.md)。本迁移为新增语义裁决持久层；不得修改 `0001`—`0008`，不得复用或改写历史 `admit_v1/v2` 作业语义。

### `adjudication_jobs`

独立于旧 `extraction_jobs` 和主题页 `consolidation_jobs`。至少保存 `id/scope/dream_job_id/input_fingerprint/admission_version/adjudication_version/embedding_model_id/status/attempts/run_after/lease_until/claim_generation/model_name/token_counts/error_code/created_at/updated_at`；`dream_job_id` 指向同 scope 的 `dream_jobs`，**没有** `extraction_job_id`。状态至少含 `queued|running|succeeded|retryable_failed|provider_wait|dead|stale_input`。同 scope、同输入指纹和策略版本幂等；独立 `adjudication_job_inputs` 固定本次 `dream_candidates` IDs（可含同 scope 的旧 Held ID）、evidence IDs/byte spans、召回 target memory IDs/versions；重试不能换输入。`provider_wait` 保留输入与 evidence 分配，按 [10 §5](10-写入触发与Dream执行模型.md) 的端点恢复条件自动续作；成功的 Held/defer 另以新输入指纹重裁。

### `adjudication_results`

按 `(tenant_id,user_id,job_id,candidate_id)` 唯一。只持久化规范结果，不持久化完整 prompt 或原始模型响应。至少保存 `durability/action/reason_code/target_memory_id/expected_target_version/applied_result_memory_id/application_status` 与时间。`target_memory_id` 的跨表 FK 无法单独证明 scope，Rust 每次读取和写入都需同 scope 核验；模型只能从 job 固化候选集合引用 ID。

唯一有效结果与 L1/evidence/relations 及 adjudication 结果必须在一个 SQLite 事务内应用；输入失效时整批 `stale_input`，不部分提交。提交成功后按 [14](14-记忆修改审计方案决策.md) best-effort 追加对应 L1 audit；审计失败告警，不回滚主结果。不得把同一 D6 修改双写到另一套通用审计表。旧候选/作业按其原版本解释，新增版本只用于新作业。

## 7. `0010_lifecycle_governance.sql`

遗忘、过期与时间衰减的产品语义见 [12](12-遗忘、过期与时间衰减方案决策.md)。本迁移只增加生命周期记录，不回改 `0001`—`0009`，特别是不能扩展 `memories.status` CHECK 或重解释现有 v1 `/forget`。

- `memory_retirements`：以 scope + `memory_id` 为键的可逆退休覆盖，记录 `memory_version/actor_kind/reason_code/retired_at`；restore 通过同事务移除当前覆盖。被覆盖记忆不能进入任一 read/query path；retire/restore 成功后按 `memory_audit` 规则尝试记录 L1 update。
- 生命周期状态保存在 `memory_retirements` 与 `purge_jobs`；不另建一套通用 lifecycle audit ledger。已有 L1 的状态变更按 [14](14-记忆修改审计方案决策.md) 记为 `memory_audit.action=update`；普通物理删除记为 `delete`。purge 请求/进度由 confirmation/job 状态表示；purge 闭包目标的 audit rows 在擦除流程中一并删除。
- `purge_confirmations`：preview 创建一次性短期记录，只存随机 confirmation token 的哈希、scope、目标 ID/version、依赖 fingerprint、过期时间与消费状态；明文 token 只返回给可信调用者一次，不写数据库或普通日志。confirm 原子消费，重复请求仅可凭同一幂等键取回无正文结果。执行完成或过期后清除目标关联与 token 哈希。preview 因此**只读业务记忆，但会写确认元数据**。
- `purge_jobs`：执行期间保存依赖闭包 fingerprint、状态、attempts、lease/generation、执行进度与无正文结果计数。若超出单事务安全范围，先将依赖标为不可读的 `purge_pending`，重启后可继续；不得留下可读的半删除对象。终态清除可反查目标的 ID/fingerprint，只保留无正文状态与计数。
- `purge_tombstones`：按 scope + evidence/source ID 建唯一键，只存无正文的 replay suppression 标识、operation ID 与时间；不设指向已删除 evidence/memory 的 FK，不存 quote、claim、embedding 或原始 JSON。
- `retention_policies`：按 scope 保存可信用户/管理员确认的 `policy_version/effective_at/raw_evidence_retention_days/expired_memory_purge_after_days/enabled`，各保留期默认 0。版本每次变更递增，历史版本只保留无正文策略值以便解释已执行清理；Agent/Dream 无权写入。
- `retention_jobs`：按 scope、policy version、计算批次 fingerprint 幂等，保存 status/lease/generation、预览计数、失败码和无正文结果计数。提交删除前再次读取当前 policy version；策略取消或收窄时旧 job 终止而不继续清理。正值策略已构成持续授权，此 job 不使用手工 `purge_confirmations` token，但共享 purge 的依赖闭包、不可读覆盖、tombstone 与恢复流程。

purge preview 只计算依赖闭包且不修改 L0/L1/页面/索引；它唯一的写入是上述确认元数据。confirmation 只能一次执行匹配的 target/version/fingerprint。purge 闭包还须处理现有 `memory_candidates` 的 quote/claim、`candidate_evidence` 的 FK 与旧 `audit_events` 中的 target ID/关联字段，以及新增 Dream 候选、裁决输入/结果和 `mutation_receipts` 中可反查闭包目标的响应；不能只清 `memory_audit` 和 L1 revision。retire/restore、purge 状态提交与页面/向量/FTS 失效须在同一规范事务中完成。v1 forgotten 的 `suppressed_sources` 保留原语义；它与 purge tombstone 不互相替代。

## 8. 写事务不变量

1. 任一 L1 状态/claim/version 更改：按对应业务不变量更新内容与派生状态；同事务失效相关页面及向量，并维护 FTS/grams 索引，不能提交后再异步撤销。Dream adjudication 创建或更新 Active L1 也必须进入记忆词法索引。
2. 对同一 mutation，业务数据和必要的 evidence/relations/job result 按所属不变量提交；已有 L1/L2/L3 记录发生 update/delete 后 best-effort 写一条 `memory_audit`。旧 v1 `correct/forget` 已写 `audit_events` 的历史行为保留，同时补记新 `memory_audit` 的旧 ID update；新 D6 mutation 不额外写旧 `audit_events`。审计失败告警且不回滚；purge 按 [14](14-记忆修改审计方案决策.md) 清除闭包目标在两张审计表中的可关联行。
3. pin/unpin：只改变 resident 选择，不改变 L1 truth/status；故忘记重放抑制与 pin 无关。
4. Soul 更新：CAS `expected_version`；冲突返回 `VERSION_CONFLICT`；同正文同版本请求按明确幂等键返回原版本。
5. 模型整理结果：核 job generation、输入 fingerprint、所有源的版本/状态；任一变化整批不发布，作业 `stale_input` 并允许新批重建。
6. 导出 `.md`：先写临时文件、flush、原子替换；路径由 CLI 显式指定，禁止从 user/agent 原值拼路径；导出中不用令牌和原始 L0 全文。
7. 所有新表 SQL 及 Rust 查询绑定 `(tenant_id,user_id)`；跨用户 ID 请求返回 404，不暴露存在性。

## 9. 升级与回滚

- `0005` 只增加表，旧 L1 不改、不批量 pin；旧 soul 默认为空。`0006` 增加派生知识文档能力；`0007` 增加 Dream 触发与输入账本；`0008` 增加向量索引；`0009` 增加版本化语义裁决流水；`0010` 增加可逆退休、purge、保留清理账本。既有 extraction job 仍按历史策略处理。`raw_evidence_retention_days` 与 `expired_memory_purge_after_days` 默认为 `0`（关闭），具体运行策略见 [12 §5](12-遗忘、过期与时间衰减方案决策.md)。
- 每阶段升级前关停 memoryd，对原库做只读一致性快照（包含 WAL/SHM 或用 SQLite 只读 backup API）；**不要先用新 `Store::open` 的 backup/doctor 指向原库**，它会先迁移。
- 先在 `dana/realtest` 的文件副本演练；核对原作业数量、`prompt_version/admission_version`、held/active/forgotten、L0 行数逐字段不变。
- SQLite schema 迁移本身不承诺自动回滚。发生部署问题时停新服务，用迁移前快照整体恢复；保留新版运行期间产生的新数据的独立导出，不能把旧二进制直接指向新 schema 冒险运行。

## 10. `0011_dream_runner_and_redecision.sql`

`0011` 保持 `0001`—`0010` 字节不变，补齐 Dream runner、重裁来源和派生整理触发关联：

- `dream_jobs.runner_id/purpose` 区分当前 runner 与 `extract|redecision|consolidation` 任务用途；`dream_runners` 保存 scope 内 runner 能力与 lease。
- `dream_candidate_redecisions` 记录 Held candidate 与新证据/显式用户重裁、Dream job、策略 fingerprint 的关系。同一候选、证据和策略只允许一次。
- `dream_consolidation_links` 将每个派生整理作业绑定到已持久化 Dream job，并区分 `derived|manual`。迁移会把旧的、无 trigger 关联的 queued/running/retryable consolidation job 标记为 `stale_input / DREAM_TRIGGER_REQUIRED`，增加 claim generation，防止绕过新 trigger 契约被继续领取。

## 11. `0012_dream_read_snapshots.sql`

- Dream job 保存 `read_calls` 与 `read_budget`（缺省 32，范围 1—64）。每次受限读取先校验 Bearer scope、runner、job 状态和 generation，并消费持久预算。
- `dream_read_search_receipts` 仅记搜索操作、query SHA-256、semantic 是否完整、结果数与时间；不持久化原始 query。
- `dream_read_memory_targets` 和 `dream_read_page_targets` 将模型可进一步读取的对象 ID、版本和 fingerprint 固定到当前 job generation。外键保证目标 purge 时同步清理读取关系；后续详情读取必须命中此前冻结的 target。

## 12. `0013_topic_page_description.sql`

`memory_pages.description` 成为可搜索的主题页描述，`page_revisions` 同时保留修改前后 description。由于 FTS5 虚表不能原地加列，迁移重建 `page_fts`，只为仍 published 且所有来源版本及生命周期均有效的页面恢复索引。历史页面 description 为空，不改写其旧正文；后续 `consolidate_v2` 可提供新描述并与标题、正文一起检索。

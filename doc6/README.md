# doc6｜下一阶段开发规范：人格、常驻记忆、召回与整理

状态：**D6-0—D6-15 代码已实施；当前验收状态以交接记录为准**（2026-09-28）。当前 schema 13；D6-11—D6-15 已通过 Rust/TypeScript 检查和官方 DSH 固定响应 Dream child 流程验收。真实模型质量、全面 E01—E25、性能、用户库升级与部署仍分别按未验证/未执行状态记录，详见 [doc-handoff/20](../doc-handoff/20-D6-11-15交付记录.md)。本文最初的设计基线和施工卡状态属于历史，不能覆盖当前代码状态。

## 上游方案选择（2026-09-26）

整体召回以 **Hindsight 为主要设计参考**；向量召回支路、Prompt 注入和记忆修改审计分别采用 **TencentDB 对应机制**。人格与知识层采用融合方案：用户主写、显式导入的 `soul.md` 是唯一人格指令来源；从有证据 L1 派生问题画像（mental model）和主题知识页；借鉴 EverOS 的 Markdown 可读/交换体验，但不制造多份事实源。仅 Soul 进入 system；Resident、原子记忆和按需召回的派生文档作为带来源的 user-role 数据。各项选择不等于采用任一上游的整套生命周期或数据模型。详见 [11 Prompt 注入方案决策](11-Prompt注入方案决策.md)、[14 记忆修改审计方案决策](14-记忆修改审计方案决策.md) 和 [15 人格与派生知识融合方案](15-人格与派生知识融合方案决策.md)。

**评分方案选择（2026-09-26）**：普通记忆不设统一的可信度/重要性总分。Hindsight 旧版 `confidence_score` 只用于 opinion，当前源码已移除；TencentDB `priority` 表达重要性，不代表真实性；EverOS 普通记忆无统一分数，但 Agent 专用对象有质量/成熟度指标。只有出现明确的排序或预算需求时，才考虑独立的 `importance`；观点置信度只限观点类且先验证校准效果。详细选择与上游优缺点见 [13 记忆评分与重要性方案决策](13-记忆评分与重要性方案决策.md)。

## 原始 D6 设计基线（历史）

本节后续的“已有能力”段和目标能力表记录的是 D6 文档起草时的 schema 4 基线与计划，不代表当前工作区状态。当前 schema 常量为 13；当前实现与验收档位以 [doc-handoff/README.md](../doc-handoff/README.md) 及各交付记录为准。新增的 Auto Dream 子 Agent 方案见 [17](17-Claude AutoDream子Agent与记忆整理借鉴方案.md)，不把历史目标描述当作现状。

已有：Rust `memoryd`、SQLite schema 4、L0 证据、原子记忆、`extract_v3/admit_v2`、手工 remember/correct/forget、词法搜索、DSH pre-step 注入与可靠 spool。当前 `compose_context` 只给指令最多 2 个独立名额，总上限 5 条/2000 字；无 Soul、resident 选择、问题画像/主题页、语义检索、语义准入裁决/记忆合并。

本阶段交付七条**可独立证明**的能力：

| 能力 | 必须达到的可观察结果 |
|---|---|
| 人格 `soul.md` | 用户为某 Agent 编辑后，每次模型调用在 system prompt 中得到对应版本；别的用户/Agent 不可见。 |
| 常驻 `memory.md` | 与问句无关的有效核心记忆每轮可见；可固定、解除固定、查看因预算被省略的 ID；纠错/退休/遗忘/到期即时不再出现。 |
| 画像与主题整理 | Dream 从 active 原子记忆生成问题画像和主题知识页，均带来源/版本且可重建；来源变化时立即停止使用旧文档。 |
| 语义召回 | Hindsight 主体召回结构 + TencentDB 向量支路；零词法重叠但有关的问句可进入候选，向量/精排降级状态明确。 |
| 语义准入与合并 | 证据有效的候选不再依赖固定句式模板；embedding 只召回可比较的旧记忆，LLM 批量提出语义动作，Rust 校验后保留证据和历史地应用。 |
| 写入触发与 Dream | 普通事件只写入 L0；主 Agent 可即时记忆；后台子 Agent 只在持久 trigger/job 后处理冻结证据批次，未拿到 Rust receipt 不报告已保存。 |
| 生命周期治理 | retire 可恢复、v1 forget 保持兼容、purge 两阶段确认、retention 默认关闭；episode recency 只有限影响 Retrieved 排序，不会让稳定记忆随年龄失效。 |

## 权威关系

```
L0 evidence ──▶ 主 Agent 显式直写 ───────────────────────────────────────────────────────▶ L1 memories
     └───────▶ compact / schedule / custom trigger ─▶ Dream job ─▶ candidates + adjudication ─▶ L1
                                                                                                 ├──▶ resident view
                                                                                                 └──▶ question models + topic pages
手工编辑 soul.md ──▶ 版本化 Soul（按用户 + Agent 隔离）──▶ system section
L1、问题画像、主题页 ──▶ 相关召回 / 用户 pin ──▶ sourced user-role context
```

`memory.md` 是 **resident 当前选择的可重建视图**，不是另一份可私自修改的真相。`soul.md` 是用户编辑人格的 Markdown 交换格式，导入后 SQLite 中的版本为服务时权威；再次编辑文件须显式导入。问题画像和主题页是带来源的模型派生资料，永远不能覆盖 L0/L1 或自动写入 Soul。四类对象的权限、更新和注入位置各不相同，不允许合成一个“记忆文本”字段。

## 硬边界

- 同用户跨 Agent 共享 L1/问题画像/主题页；人格按 `(tenant_id,user_id,agent_id)` 分开。Bearer token 仍是 user scope 唯一来源。`agent_id` 是宿主给出的选择键，不能充当用户认证。
- 2026-09-25 用户决定解除 `memory_remember` 的内容类别护栏，本阶段**不恢复**该护栏，也不静默改 `extract_v3/admit_v2`。若以后重写内容护栏，另立版本和决策。
- 2026-09-26 用户确认采用 [09](09-语义准入与记忆合并设计.md) 的融合方向；这是新版本的设计，不改变 `admit_v1/v2` 历史作业，也不代表语义准入已经实现。
- 2026-09-26 用户确认采用 [10](10-写入触发与Dream执行模型.md) 的写入时机：普通 turn/end 不自动调用 LLM；主 Agent 即时写入，后台 Dream 由 compact、定时 Auto Dream 或自定义触发入队。
- 2026-09-26 补充决定：定时 Auto Dream **默认启用**（首版每 scope 最多 24 小时一次，且至少空闲 15 分钟、有新 user event）；模型/runner 不可用时保留待处理 L0 并给诊断。成功 Held/defer 遇相关新证据才按新指纹自动重裁，provider 故障保持作业待恢复，不把故障误记为已裁决。
- 2026-09-26 用户确认采用 [12](12-遗忘、过期与时间衰减方案决策.md) 的生命周期方案：Hindsight 可逆退休与有限 episode recency、TencentDB 独立硬删除/可配置 retention、EverOS 自动合并软归档；现有 v1 `/forget` 语义保持兼容。
- 2026-09-26 补充决定：可信用户/管理员配置正值 retention 后，自动清理按已确认策略执行，不逐批要求手工 purge 二次确认；Agent 可在明确用户请求下调用 retire/restore，须附最新用户事件的精确指令 span 并由 Rust 核验可证明的来源、scope、版本与状态。模型/Dream 仍不可调用 purge。
- 2026-09-26 用户确认采用 [13](13-记忆评分与重要性方案决策.md) 的评分策略：普通记忆不设统一总分；importance 仅在明确需要排序/预算时独立引入；confidence 仅用于意见且校准后使用，不能充当证据或准入裁决。
- 2026-09-26 用户确认采用 [14](14-记忆修改审计方案决策.md) 的 TencentDB `memory_audit` 方案：专用元数据审计行记录 L1/L2/L3 已有记录的 update/delete；不存修改前后正文；审计失败非阻塞并显式告警。Purge 擦除闭包目标对应的 audit rows，D6-9 验证完成后无残留可反查 ID。
- `soul.md` 只接受用户/本机管理员明确编辑，不由后台模型自动改写。Dream 可按决策文档生成有来源的问题画像和主题页，但不能把它们当成 Soul，也无权 pin/unpin、retire/restore、forget/purge 或改变记忆生命周期状态。主 Agent 仅可在用户明确指令及 Rust 证据校验通过后调用 retire/restore；任何 Agent 都无 purge 工具。
- 2026-09-26 用户确认采用 [15](15-人格与派生知识融合方案决策.md)：用户主写 Soul；Dream 从有证据 L1 派生问题画像与主题页；只有 Soul 进入 system，派生文档经按需召回或用户 pin 后作为 sourced user-role 数据。本项是设计决策，不代表相关存储、接口或注入已经实现。
- 2026-09-26 最终决定：问题画像的问题目录默认空，不预置；用户显式登记问题后 Dream 才能从有效 L1 生成相应画像。用户可审阅、改写或归档问题；主题页不依赖问题目录。
- 不回改 `0001`—`0004`，不修改三个上游或官方 DSH clone；新持久字段从 `0005` 起迁移。
- `doc/12` 的 HTTP v1 端点仍可用。新增端点是加法，旧客户端不得因新功能失效。
- 不把一次 mock 或一次真实模型命中写成总体质量改善。上线结论按 [07](07-验收与上线.md) 的证据分档。

## 规范冲突的处理

用户新目标优先于 v1 冻结边界。`doc/10` 中“v1 不做自动 L2/L3、embedding、Markdown 双向真相”和“5 条/2000 字”只约束既有 v1 接口；本阶段通过新表、新端点和适配器配置增加能力，不回改 v1 历史语义。`doc2` 的 DSH 接线事实仍有效；若官方源码与本文示例类型冲突，先按 `08 D6-0` 重新核对并记录，不能猜接口。

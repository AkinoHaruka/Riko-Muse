# 01｜产品契约与边界

## 1. 问题定义

当前系统解决了“这条原话是否可作为原子记忆入库”的一部分问题，但用户感到差的是**连续性**：换话题后稳定偏好消失；没有能编辑的 Agent 人格；多次经历不会整理成可理解的长期知识。本阶段按这三个用户可感知的缺口设计，工程验收必须落在“模型本轮实际看见什么、哪些 ID 被用到”。

不以 `soul.md` 或 `memory.md` 文件名代替行为验收。文件可以存在，但若没有版本、权限、即时失效和每轮注入，就不算完成。

## 2. 四种内容，四种职责

| 名称 | 主体 | 来源与编辑 | 使用方式 | 权威级别 |
|---|---|---|---|---|
| `soul.md` | 同一用户下某个 Agent 的稳定角色、风格、边界 | 用户/本机管理员显式编辑，乐观锁发布 | DSH system prompt 独立 section | 用户定义的指令；不由会话内容自动覆盖 |
| `memory.md` | 该用户跨 Agent 共享的核心记忆清单 | 从当前有效 L1 动态生成；用户 pin/unpin 影响顺序 | 每个模型 step 的 sourced context | L1 的视图；只给来源与当前状态，不新增事实 |
| 问题画像（mental model） | 对一个已登记问题的精简、可检索回答 | Dream/LLM 基于冻结 L1 输入生成；保留问题定义版本与来源版本 | 相关时按需检索；用户可审阅并 pin | 派生数据；不是人格指令或新事实 |
| 主题知识页 | 若干相关 L1 记忆整理出的主题叙述 | Dream/LLM 提议 + Rust 结构检查 + 来源版本绑定；用户可审阅并 pin | 按需检索；用户 pin 后常驻 | 派生解释；须标记为整理摘要 |

`soul.md` 只影响指定 Agent 的行为，不能存用户事实。`memory.md` 可包含姓名、长期偏好、约束、当前重要事实等，不能被误称为人格。问题画像和主题页可以自然语言概括，但不能被当作用户逐字原话或 system 指令。用户查看时必须能一路追到 L1 memory ID，再追到 L0 evidence ID。数据库里的 `soul_profiles` 是用户编辑的 Soul 存储实体，不等于 LLM 派生的 mental model。

## 3. 长期生效的定义

- **常驻**：在 memoryd 可用、该项 active 且未过期、预算足够时，用户 pin 的记忆/派生文档以及当前 active 长期指令不依赖查询词进入每次模型 step 的 resident context。包括工具继续执行的 step；不能仅在新的用户消息到来时注入。普通 fact/preference 不因为“最近写入”就自动常驻，先在建议列表中供用户选择。
- **固定**：用户明确 pin 的 active 记忆优先于自动选择；任何 kind 都可 pin，不设置“最多两条指令”一类条数特权。总字符预算仍然存在；超预算返回被省略 ID 与原因，不能声称已全部注入。
- **即时撤销与擦除分开**：correct/supersede、retire、v1 forget、valid_until 到期和 purge 是不同操作。它们发生后，下一个 bundle 不得返回目标或含目标正文的派生文档；来源变化时旧文档/向量同步失效。retire 可显式恢复；v1 forget 仍按旧契约保留 L0/revision 并防证据重放；只有经两阶段确认的 purge 才物理擦除其依赖闭包。完整状态语义见 [12](12-遗忘、过期与时间衰减方案决策.md)。
- **跨 Agent**：同 scope 的 Agent A/B 读取相同用户核心记忆与派生知识文档；A 的 `soul.md` 不自动成为 B 的人格。
- **空库**：没有魂文件时不注入空壳；没有 active 时 `memory.md` 为空；不从模型“猜”一个人格或个人资料。

## 4. 产品默认值（工程初值，不冒充上游最优）

| 项 | 初值 | 上限/行为 |
|---|---:|---|
| soul 正文 | 默认空 | 2000 Unicode 标量字符，超限拒绝导入，不截断 |
| resident | 最多 24 项 / 3000 字符 | 配置可调到 100 项 / 12000 字符；逐条完整保留或跳过 |
| 动态召回 | 最多 8 项 / 2400 字符 | 已在 resident 中的 memory ID 去重 |
| 派生知识文档正文 | 1200 字符 | mental model 引用 1—20 条、主题页引用 2—20 条 active L1，超限拒绝发布 |
| 语义 query | 不设专用延迟预算 | 等待已配置 embedding provider 请求完成或达到其 `embedding_timeout_secs`（默认 30 秒）；失败后回退其他可用通道并报告 `semantic_status=unavailable` |

预算指正文 Unicode 标量字符；返回 `included_ids`、`omitted_ids`、`reason`，界面可以展示真实覆盖范围。Soul 单独占 system prompt 预算。任何配置上限的改变都要有可见的版本/诊断，不在低层悄悄截断正文。

## 5. 能力范围

**本阶段实现**：用户编辑人格；原子记忆和已发布派生文档的手工 pin/unpin；可审阅的 resident 建议列表；无查询依赖的 resident；有来源的问题画像与主题知识页整理/重建；以 Hindsight 为主体的多路召回/融合/精排设计（向量支路按 TencentDB query-embedding 路径）；版本化的语义准入与 L1 去重/更新；同用户跨 Agent 注入；用户可查询本轮注入清单。L0 持续采集，主 Agent 可即时写入，Dream 子 Agent 仅由 compact/定时/自定义 trigger 启动批量处理；定时 Auto Dream 默认启用且仅在空闲、有待处理 user evidence、模型/runner 可用时启动，普通 turn/end 不自动触发提取 LLM。画像和主题页默认只参与按需检索，用户审阅并 pin 后才进入每轮 resident context，且始终保持 user-role 数据属性。语义裁决不能删除证据或改写 Soul；不确定结果保留为 Held/待处理，相关新证据可触发重裁。

**本阶段暂不自动执行**：模型自行修改 Soul、生成 system Persona 或把无证据推断的个人特征常驻；跨用户共享；对历史 L0 全库重提取；直接编辑导出的 `memory.md` 并绕过 L1；把画像/主题页误当成用户逐字事实；大规模模型对比。该范围不阻止用户通过已有 remember/correct/forget 修改 L1。

## 6. 对上游的实际借鉴

- **总体选择 Hindsight 作为主要设计参考**：借鉴其证据来源关系、后台 consolidation、多个召回通道协作、RRF 后精排等整体机制；按本项目的 Rust/SQLite、scope、revision、forget 和可验证 byte-span 证据改造，不照搬其 Python/PostgreSQL 产品实现。
- **向量召回的定向例外选择 TencentDB**：按“记忆侧预生成并维护 embedding → 查询侧生成 query embedding → 在当前 scope 内做向量近邻检索 → 返回独立排序候选”的执行路径实现；向量服务不可用时明确降级到其余可用召回通道。这个选择只针对召回向量支路，不改变 Hindsight 主体的多路融合/后续精排，也不代表采用 TencentDB 全套 L0-L3、Persona 生命周期或其他产品模块；Prompt 注入是单独决定，见下一条。
- **Prompt 注入角色分层选择 TencentDB**：按宿主 prompt-build 生命周期，在模型调用前把 Resident、Retrieved 和按需画像/主题页放进 user-role 数据上下文；只有用户编辑的 Soul 进入 system prompt。DSH 使用 `system-prompt/assemble`（Soul）和 `agent/pre-step`（其余 sourced context）承载职责；不把派生知识提升为 system 指令，也不改写原始用户消息/证据来源。完整角色与失败语义见 [11](11-Prompt注入方案决策.md)。不采用 TencentDB 的 L0-L3、自动 Persona-as-Soul 或其他检索/存储设计。
- **记忆修改审计选择 TencentDB**：用独立 `memory_audit` 元数据事件表记录 L1/L2/L3 已有记录的 update/delete、scope、可选 Agent/task 上下文、版本和请求关联 ID；不记录正文或旧/新值。常规 audit 写入失败告警但不回滚记忆修改；purge 清理关联审计行是擦除成功的必要条件。它不承担 API 全量请求日志或后台 job 状态记录。字段、范围、失败与 purge 边界见 [14](14-记忆修改审计方案决策.md)。
- **遗忘、保留与衰减采用分层组合**：可逆单条退休与有限 recency rerank 参考 Hindsight；显式物理删除和默认关闭的 retention 参考 TencentDB；自动 consolidation 的旧项归档参考 EverOS `deprecated_by`。时间衰减只影响 episode 的 Retrieved 相关性，不让稳定事实、偏好、指令、Soul 或 pinned Resident 随年龄失效。用户确认的完整决策和实现边界见 [12](12-遗忘、过期与时间衰减方案决策.md)。
- TencentDB 的“先召回相似候选、再批量 LLM 判定 store/update”仍是 [09](09-语义准入与记忆合并设计.md) 里 Dream 语义整理的流程参考；这和上面 query-time 用户问题召回是两个调用场景，不能把两套 job/准入语义混为一谈。记忆 merge 仍以 Hindsight 的 embedding 候选 + LLM 关系裁决为主要算法参考，本项目保留 byte-span 证据和 Rust 事务校验。
- Hindsight：借鉴问题驱动画像与主题知识整理、来源约束和失败可重试；本项目所有派生文档保留明确来源标签。
- EverOS：借鉴 Markdown 可读可导出及反思结果保留来源；SQLite 仍是规范状态，Markdown 用于用户编辑 Soul 和查看/交换派生内容，不成为多份独立真相。

人格与派生知识的融合决策、取舍和边界见 [15](15-人格与派生知识融合方案决策.md)。

“主要设计参考”不等于每个上游能力已经进入 D6 首发实现。图关系/时间检索若需启用，必须先在对应任务卡中写明可用数据、索引、过滤、预算和失败语义；不得把源码里有一个 relation 字段或时间戳就报告成 Hindsight 同档能力。是否有效要由本项目的漏召、误召、注入利用率与撤销行为验证。

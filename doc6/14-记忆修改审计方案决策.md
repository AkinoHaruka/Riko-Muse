# 14｜记忆修改审计方案决策：采用 TencentDB `memory_audit`

状态：**用户已确认，并纳入 D6 实现规范**（2026-09-28）。TencentDB-Agent-Memory 元数据审计设计已由 D6 代码实现；当前确定性验证/部署档位以 [doc-handoff/15](../doc-handoff/15-D6规范差距修复.md) 和最新交接记录为准。

## 1. 决策

采用专用 `memory_audit` 表记录**已有记忆记录的更新和删除元数据**。每次成功的 update/delete 后 best-effort 追加一条记录，描述目标记录、所属层、认证 scope、可用的 Agent/task 关联、变更版本、时间和请求关联 ID；永久 purge 的擦除规则见 §4。

审计行不保存记忆正文、修改前后内容、原始对话、模型 prompt 或模型完整响应。该表回答“哪条记录发生了哪类修改、关联哪个版本与请求”，不承担内容快照、API 全量请求日志或后台作业状态查询。

## 2. D6 对象映射与范围

| 审计层 | 本项目对象 | 记录范围 |
|---|---|---|
| `L1` | 原子记忆 | 已有记录的 update/delete；新建不记入此表 |
| `L2` | 派生知识文档（问题画像/主题页） | 已有文档的 update/delete；新建不记入此表 |
| `L3` | 用户编辑的 Soul profile | 已有 profile 的 update/delete；新建不记入此表 |

L0 是追加式来源证据，不作为此表的可变记录。`resident_pins`、页面 pin、幂等 receipt、后台 job 状态也不属于 L1/L2/L3 记忆修改审计；本决策不把它们混记进 `memory_audit`。新记忆的来源仍由 evidence/source 关系追溯，不靠伪造一个 create 审计动作。

## 3. 逻辑字段

| 字段 | 含义 |
|---|---|
| `audit_id` | 审计行 ID |
| `record_id` | 被修改记录的 ID |
| `layer` | `L1`、`L2` 或 `L3` |
| `action` | `update` 或 `delete` |
| `tenant_id`, `user_id` | 服务端认证 scope |
| `agent_id` | 可选宿主 Agent 关联；不得作为认证依据 |
| `task_id` | 可选宿主任务关联；不得作为认证依据 |
| `version` | update 后的版本；delete 记录删除时已知版本 |
| `updated_at_ms` | 修改时间，毫秒 UTC |
| `request_id` | 可选请求关联 ID |

表内不增加旧/新正文、`reason_code`、`actor_kind` 或完整请求 JSON。TencentDB 上游的 team scope 在本项目映射为 `tenant_id`；`agent_id`/`task_id` 仅在可信宿主上下文可用时作为可选关联，不参与授权，也不能由模型指定。上游没有独立操作者身份字段；因此本方案只能按 scope、宿主上下文和 request ID 追踪，不能声称它能识别真实自然人或区分所有内部执行者。

## 4. 写入与失败语义

沿用上游的非阻塞 best-effort 语义：主记忆修改成功后尝试写审计行；审计写入失败记录服务端告警，不回滚已完成的记忆修改，也不把整个请求改报失败。运行日志与验收证据应能观察此失败，不能静默当作已审计。

上游的 `action` 只有 `update/delete`，没有 `create` 或生命周期细分动作。D6 将已有记录的数据/状态变更归为 `update`，普通逻辑删除归为 `delete`；`retire/restore/forget` 都映射为已有 L1 记录的 `update`。旧 v1 `correct/forget` 已在同事务写 `audit_events`，此历史行为保留；D6 上线后再对被更新的**旧 memory ID** best-effort 追加一条 `memory_audit` update。新 D6 操作只写 `memory_audit`，不为同一新操作再写旧 `audit_events`。永久 purge 是例外：purge 闭包中的 `memory_audit` 行须按 `record_id + scope` 删除，旧 `audit_events` 的 `target_id` 或 `detail_json` 若引用闭包目标也须删除整行；不为最终 purge 保留一条指向该 ID 的 delete 审计行。这项清理是 purge 成功的必要条件；清理失败时不能报告 purge 完成，由 job 重试或明确报错。confirmation/job 只保留执行所需的短期目标信息，完成后按 purge 结果保留无正文计数/状态，不保留可反查目标正文的关联。

因此 `memory_audit` 提供普通记忆更新/删除的追踪；purge 的操作进度由 `purge_confirmations`/`purge_jobs` 承载，重放抑制由无正文 tombstone 承载。purge 完成后删除/清空 confirmation 与 job 中可反查目标的 ID，仅保留无正文结果状态和计数。D6-9 必须验证 purge 闭包完成后目标 `record_id` 不再出现在审计表或其他可反查位置。

## 5. 明确不纳入本次选择的机制

- 不采用 Hindsight 的全量操作请求/响应 `audit_log` 作为记忆修订记录。
- 不采用 EverOS 的 `md_change_state` 队列和 `reflection_report` 作为记忆变更审计；它们解决后台索引和整理任务可恢复性。
- 不把 D6 的同一记忆修改同时写入多套通用审计日志。
- `soul_revisions`、`page_revisions` 等内容版本快照若因用户查看/恢复历史而保留，属于独立的产品版本能力，不属于 `memory_audit`，不得把正文复制进审计表。

现有 v1 API 的业务响应、`audit_events` 写入和 `0001`—`0004` 历史迁移保持冻结；新增 `memory_audit` 是 D6 对既有记录变更的 best-effort 投影，不能替代旧事务审计，也不能令旧请求因新审计故障失败。不回写旧迁移；同一**新 D6 操作**不双写旧审计表和新表。purge 必须清除两表中与擦除闭包可关联的行。

## 6. 上游源码依据

TencentDB-Agent-Memory 当前实现的 `AuditEntry` 与 SQLite `memory_audit` 表只保存 `record_id/layer/action/team/user/agent/task/version/time/request_id` 等元数据；L0 不入审计，L1/L2/L3 update/delete 各记一行。`recordAudit` 捕获写入错误并告警，不阻塞主请求。D6 将 team scope 映射为 `tenant_id`，scope 身份仍由 Rust 从 Bearer token 派生。D6 实施前的源码核对见 [doc-handoff/13](../doc-handoff/13-D6源码核对.md)；今后改变上游依据时重新按只读 checkout 复核：

- `tencentdb-agent-memory/MemoryCore/src/core/store/types.ts`：`AuditEntry` 字段与审计约定。
- `tencentdb-agent-memory/MemoryCore/src/core/store/sqlite/memory-store.ts`：SQLite 表、索引、追加和查询。
- `tencentdb-agent-memory/MemoryCore/src/gateway/v2-router.ts`：变更路径调用 `recordAudit` 与失败告警。

本决策的上游差异与限制见 [本项目实现机制与上游对比报告](本项目实现机制与上游对比报告.md) 和 [上游机制调研](上游记忆机制调研-hindsight-tencentdb-EverOS.md)。

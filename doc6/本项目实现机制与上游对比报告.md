# 本项目（agent-memory）记忆机制与上游三项目对比报告

> 调研对象：`agent-memory/`（Rust 内核 memoryd + TS DSH 适配器），对比 `hindsight/`、`tencentdb-agent-memory/`、`EverOS/`
> 调研日期：2026-09-26。本项目结论均核对源码，关键文件路径见文末附录。上游三项目细节见《上游记忆机制调研-hindsight-tencentdb-EverOS.md》。
> 遗忘/删除/衰减维度原先有过度概括，已于 2026-09-26 按上游源码重新核对；本表该行与 §2.4 已更正，新增设计以 [doc6/12](12-遗忘、过期与时间衰减方案决策.md) 为准。

## 0. 一页总览

| 维度 | **agent-memory（本项目）** | hindsight | tencentdb-agent-memory | EverOS |
|---|---|---|---|---|
| 语言/存储 | Rust + SQLite（FTS5 + grams） | Python + PostgreSQL/pgvector | TS/Node + SQLite/FTS5（可插拔） | Python + Markdown + SQLite + LanceDB |
| 记忆写入 | L0 事件立即幂等落库 → 作业队列 LLM 提取候选 → **Rust 确定性准入**才 Active | retain 同步 LLM 抽取 + content_hash 去重 | L0 立即 JSONL；L1 防抖调度 LLM 抽取 + LLM 判重 | buffer 暂存 → boundary 触发 LLM 抽取 |
| 准入严格度 | **最强**：逐字 byte span + 固定 11 步规则裁决 | content_hash + 实体去重，无 span 硬约束 | 消息级去重 + LLM 判定，无 span | 仅 message_id 去重；Episode 无逐字 span 硬约束 |
| 召回方式 | FTS5 BM25 + 中文二元字 grams 双路 **RRF k=60**，无向量 | 向量/BM25/图/时间 4 路 RRF + cross-encoder rerank | FTS5+向量 RRF / 自动降级，无 rerank | 稀疏+稠密 RRF + LR 校准 / AGENTIC 多轮 |
| Prompt 注入 | 有：`agent/pre-step` 钩子，compose 出 `<agent_memory>` XML，防回流 | 有：LiteLLM wrapper 前 recall 后 retain | 有：before_prompt_build，记忆→user、persona→system | 无自动注入 |
| 整理作业 | **无定期整理**：仅提取 worker（退避重试→dead），主动 `/forget` + SUPPRESSED_SOURCE 防复活 | retain 后自动 consolidation + 周期 reconcile | 防抖管道 L1→L2→L3 | OME 事件驱动 + 每周 reflect 合并 |
| 遗忘/保留/衰减 | v1 `/forget` 逻辑隐藏 + `suppressed_sources` 防重放；无通用物理 retention、无 recency 排序 | 单条可逆 invalidate；另有 bank/document/clear 硬删除面；recency rerank | L1/L0/全 Agent 删除 API；配置后物理 retention；无检索 recency 衰减 | Episode 合并 `deprecated_by` 软归档；Knowledge 文档 DELETE 是独立对象；无检索 recency 衰减 |
| soul.md/persona.md | **无任何 Markdown/人格机制** | mental models + knowledge pages（可镜像 markdown） | persona.md（LLM 生成+自动注入+备份） | Markdown 即事实源，soul.md 是能力但未启用 |
| 评分维度 | 证据 + Rust 准入；model_confidence 仅诊断 | 当前主记忆模型无 opinion confidence_score（旧字段已移除） | `priority` 是重要性分（缺省 50），不是可信度 | 普通记忆无统一分；Agent case/skill 有专用评分 |
| 审计 | 当前实现：`audit_events` + `memory_revisions` | 可配置 `audit_log` 记录操作请求/响应；Memory Defense 是独立的脱敏/拦截机制 | `memory_audit` 记录 L1/L2/L3 update/delete 的 scope、可用的 agent/task 上下文、版本、时间、request_id；版本冲突是另一机制 | SQLite `md_change_state` 队列与 `reflection_report` 整理审计；不是通用逐记忆修订表 |

本表描述的是 **2026-09-26 当前源码实现**，不是 D6 目标。D6 的目标采用融合方案：用户编辑的 Soul 是唯一进入 system 的人格；有来源 L1 可生成问题画像/主题页，作为按需 user-role 数据；Markdown 只作可读/交换格式。注入时机借鉴 TencentDB 并映射到 DSH hook；详见 [doc6/11](11-Prompt注入方案决策.md) 与 [doc6/15](15-人格与派生知识融合方案决策.md)。当前项目仍只有旧 `agent/pre-step` + `compose` 注入，没有 Soul、Resident bundle 或派生知识文档；不得把目标设计写成已实现能力。

D6 的记忆修改审计决策另见 [doc6/14](14-记忆修改审计方案决策.md)：用户已选 TencentDB 的专用 `memory_audit` 元数据事件表。上表仍仅描述调研时本仓库与上游的源码事实。

## 1. 本项目怎么做的

### 1.1 存入：证据先行，准入裁决

三级流水，与上游最大区别是**模型输出永远只是候选**：

1. **L0 证据事件**：`POST /v1/evidence/events` 按 `(scope, host, session, event_seq)` 幂等落库（哈希不同即 409），原始事件不可变。
2. **提取作业**：`POST /v1/extraction/flush` 建 `extraction_jobs`，单线程 worker 轮询领取，按行版本分派提示词——现行 `extract_v3` 要求**一候选一命题 + 最短逐字原文 quote**；失败 5/15/45s 退避 3 次转 dead，未知 prompt/admission 版本立即 dead（不猜测、不静默降级）。
3. **确定性准入 admit_v2**（Rust 固定 11 步）：来源必须本窗口 user/user → quote 必须是事件原文连续子串（byte span 定位）→ 长度/非空 → 一次性语境、口语前缀、多命题、主语不明、凭据、健康敏感、第三人、时间性依次 held → 句式与 kind 匹配才 Active。查库规则：候选幂等、DUPLICATE_ACTIVE 只加证据、forgotten 源 SUPPRESSED_SOURCE 防复活、POSSIBLE_CONFLICT held。
4. **remember 直写**（护栏已按产品决定解除）：现仅保留 scope+role 校验、「必须是该会话最新用户事件」、quote 逐字 span、claim_sha 去重幂等、审计；内容类别门/保存指令/单命题限制全部移除。

**scope 隔离**：Bearer token → SHA-256 查 principals 得 scope 注入请求扩展；适配器禁止发 tenant_id/user_id，所有 SQL 强制带双键。

### 1.2 召回：轻量双路 RRF + compose 注入

- `POST /v1/memories/search` 四路：FTS5（拉丁 BM25）+ 中文 Unicode 二元字 grams + 单字有界子串降级 + 历史路（需「以前/曾经」类提示词）。FTS 与 grams 双路命中时 RRF 融合 `sum(1/(60+rank))`。
- **无向量检索、无图检索、无时间过滤**（仅 valid_until 生效性过滤）；relations 只记 superseded/contradicts，不用于检索。
- `POST /v1/context/compose`：instruction 固定占 2 席（未命中也补齐）+ 相关项，拼成 `<agent_memory>` XML 文本。
- 适配器注入：`recall.ts` 挂 `agent/pre-step` waterfall，取最后一条 user 消息作 query，500ms 超时调 compose，以 `{kind:'agent-memory'}` 来源追加，**不回流为用户证据**（防环）。

### 1.3 整理：刻意极简

- 后台仅一条流水：flush → extraction_jobs → worker 提取 → save_candidate。**无**定期去重合并、衰减排序、摘要蒸馏作业（上游均有整理机制，但遗忘/衰减能力并不相同）。
- 遗忘只有用户主动 `/forget`：原证据/revision 保留、`suppressed_sources` 防重放复活；`valid_until` 在查询时过滤，无通用物理 retention 或 Retrieved recency 排序。

### 1.4 Markdown/人格机制

**没有**。全库无 soul/persona/memory.md 概念；记忆全部结构化存 SQLite，注入内容是 compose 动态生成的 XML 片段，无持久人格/核心记忆文件。

### 1.5 审计与可信度

`audit_events` 记录 actor/action/target/detail；`memory_revisions` 记录每次状态变更及策略版本 reason。可信度 = 可定位用户证据（evidence_id + byte span 逐字原文）× Rust 确定性准入；model_confidence 仅诊断不驱动准入；source_class 区分 user_explicit/model_inferred。

## 2. 与三个上游项目的差别

### 2.1 定位差异：裁决内核 vs 完整产品

上游三家都是「拿来即用的完整记忆产品」，自带检索、整理、注入全链路；本项目定位是**最小裁决内核**——只裁决「什么有资格成为记忆」（准入 + scope + 证据），其余能力刻意做薄。这是 YAGNI 取向：DSH 是第一个宿主，先跑通证据链闭环。

### 2.2 准入：本项目独有，且是核心差异

| | 本项目 | 上游三家 |
|---|---|---|
| 证据定位 | **逐字 byte span 硬校验**（quote 必须是事件原文连续子串） | 最多保留 source_ids/溯源字段，无逐字校验 |
| 裁决者 | Rust 确定性规则（11 步固定） | LLM 判定（去重/合并/打分）或无 |
| 模型输出地位 | 永远只是候选，held/Active 由规则决定 | 基本即最终记忆 |

上游的「记忆质量」靠 LLM 能力兜底；本项目把可信度从模型能力解耦——**这是四者中唯一的确定性准入设计**。

### 2.3 召回：最保守的一个

- 独有优势：中文二元字 grams（hindsight/tencentdb 依赖 FTS5 原生分词，中文长句召回弱；EverOS 靠 LanceDB 向量补）。
- 缺失：三家都有向量检索，本项目没有；hindsight 还有图扩展和时间维。当前 RRF 只在 FTS/grams 两路间做，等价于上游的标准做法但召回面最窄。
- 注入防回流（`agent-memory` 来源不回流为证据）是细节亮点，上游未见等价处理。

### 2.4 整理：唯一没有任何后台整理的

三家都有各自的 consolidation（hindsight 的 observation 蒸馏、tencentdb 的 L1→L2→L3、EverOS 的 OME reflect）；本项目只有提取 worker 的重试/dead 语义。上游可借鉴点：
- hindsight 的「合并 observation + proof_count 溯源」与本项目 evidence 模型兼容；
- EverOS 的 `deprecated_by` 软归档与本项目 `superseded/contradicts` relations 相近，可借鉴来表达自动整理合并；
- 生命周期不能用单一“遗忘”概括：Hindsight 有可逆单条 invalidate、较粗粒度硬删除和 recency rerank；TencentDB 有 L0/L1/全 Agent 删除与可配置 retention；EverOS 的 deprecated_by 是自动整理归档。对本项目的组合决策见 [doc6/12](12-遗忘、过期与时间衰减方案决策.md)：可逆 retire、保持 v1 forget、独立 purge、默认关闭 retention，并仅对 episode Retrieved 做有限 recency。

### 2.5 Markdown/persona：上游差异与本项目融合选择

三家机制并非同一种方案：TencentDB 有 LLM 生成并自动注入/备份的 persona；EverOS 将 Markdown 作为事实源，提供可人工编辑的 `user.md`，`soul.md` 能力未启用；Hindsight 有问题驱动的 mental models 与 knowledge pages，可镜像 Markdown。本项目原实现没有这些能力。

**D6 已确认的融合选择不是把 LLM persona 直接当人格**：用户主写并显式导入 `soul.md`，作为唯一人格指令；Hindsight 风格的问题画像和主题页从有证据 L1 派生、保留版本来源、可重建；TencentDB 只贡献注入角色分层，只有 Soul 进入 system，其余进入 sourced user context；EverOS 贡献 Markdown 可读/交换体验，但 SQLite 仍是权威。这样既保留人对人格的控制，也绕开“LLM 摘要缺少逐字证据，却被当作 system 指令”的信任冲突。详细契约见 [doc6/15](15-人格与派生知识融合方案决策.md)。

### 2.6 一句话总结

本项目在四者中**准入最严、召回最简、整理最少**：把工程预算全部押在「记忆可信度的确定性」上（证据 span + 规则准入 + 审计），而上游把预算花在召回面宽度和整理自动化上。两者是互补的取舍，不是同一赛道的落后者。

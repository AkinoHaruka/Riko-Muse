# 12｜遗忘、过期与时间衰减方案决策

状态：**设计已按 D6-9 实施；用户库升级未执行**（2026-09-28）。本文件补充并优先解释 doc6 中关于 `forget`、`valid_until`、来源保留和检索排序的旧表述；既有 v1 `forget` 行为保持不变。生命周期实现档位见 [doc-handoff/15](../doc-handoff/15-D6规范差距修复.md) 与 [doc-handoff/20](../doc-handoff/20-D6-11-15交付记录.md)；dana/realtest 原库未升级。

## 1. 决策摘要

不把“记忆不再生效”与“数据已擦除”混成一个状态，也不把“变旧”当成自动遗忘：

1. **事实被替代**：使用现有 `correct`/语义更新，旧版标为 `superseded`，保存 revision 和关系；它不再进入 active 读取，但不是用户主动删除。
2. **暂时不采用或可能恢复**：新增可逆的 **retire/restore（软退休）**，参考 Hindsight `invalidate_memory`。记录和证据保留，但该项立即退出所有面向模型的 active 读取；用户可显式恢复。
3. **现有 `/forget`**：保持 v1 向后兼容。它继续把记忆标成 `forgotten`、从召回中排除并写 `suppressed_sources` 防止同一证据重放；它是“停止使用并防复活”，**不是物理擦除**。
4. **永久删除个人数据**：新增独立、不可逆的 **purge**。用户/管理员针对单条记忆经预览和明确确认后，删除目标记忆、相关来源证据及由其派生的页面、索引和缓存；保留不含正文的最小重放抑制标记。purge 不通过 Dream/LLM 自动执行。
5. **时间有效性与保留期**：`valid_until` 到期时读路径立即隐藏，不等清理器；可配置的 retention job 负责之后的物理清理。自动 retention 配置默认关闭；用户/管理员显式配置正值后，符合该已确认策略的每批自动清理**无需再次执行手工 purge 的 preview/confirm**，但复用相同依赖闭包、不可读标记、tombstone 与故障恢复约束。
6. **召回时间衰减**：借鉴 Hindsight，将 freshness 作为相关性排序的有限乘数；第一版只作用于 `episode` 的 Retrieved 排序。`fact`、`preference`、`instruction`、Soul 和 pinned Resident 不因年龄自动降权或被驱逐。

因此，本项目采用的是 **Hindsight 的可逆事实退休与有限 recency rerank + TencentDB 的硬删除/可配置保留期能力 + EverOS 的自动合并软归档概念**。EverOS 的 `deprecated_by` 只用于整理时隐藏被合并来源，不能替代用户 retire、forget 或 purge。

## 2. 术语与状态边界

| 操作 | 含义 | 能恢复吗 | 保留正文/证据吗 | 自动执行者 |
|---|---|---:|---:|---|
| `correct` / `supersede` | 值被新事实修正/替代；旧版留作历史 | 可查看历史，重新激活须明确操作 | 是 | 用户；Dream 只能按 D6-8 裁决协议提出更新，Rust 提交 |
| `retire` | 暂停使用一条仍需保留的记忆 | 是，需显式 restore | 是 | 用户/管理员，不是 Dream |
| v1 `forget` | 逻辑遗忘：搜索/注入不可见，同证据重放被抑制 | 按 v1 契约不可直接恢复 | 是，沿用现有证据/revision 保留语义 | 现有用户 forget 流程 |
| `purge` | 明确永久擦除正文及其派生数据 | 否 | 目标及受影响来源正文不保留；只留下最小无正文防重放标记 | 用户/管理员两阶段确认；任何模型都不可直接调用 |
| `valid_until` 到期 | 业务有效期结束，读路径立即排除 | 仅经显式纠错/新版本处理，不由清理器恢复 | 到期后可暂留供审计，直至 retention 清理 | 时间条件；不调用模型 |
| 自动 consolidation 归档 | 新主题/叙述取代重复来源，旧项不参加默认搜索 | 原始来源仍可审计 | 是 | 已持久化的 Dream job；使用 `superseded`/`deprecated_by` 关系，不调用 forget/purge |

**已有 v1 实现事实**：`memories.status` 当前约束只有 `active|superseded|expired|forgotten`；`/forget` 会保存 `memory_revisions`，把来源写入 `suppressed_sources`，保留原始 L0。不得把它的现有名字误解为硬擦除，也不得悄悄改变 v1 行为。实现状态以 `agent-memory/migrations/0001_init.sql`、`memory-store-sqlite/src/memories.rs::forget_memory` 为准。

## 3. 软退休（retire/restore）

### 3.1 可见性与状态

- retire 只允许对同 scope、当前底层状态为 `active`、版本匹配且证据有效的记忆执行；需用户/管理员身份和理由码，可选简短理由不写入模型 prompt。
- 新版 `memory_retirements` 作为**可逆状态覆盖层**记录退休项，避免回改 `0001` 的 `status CHECK`，也不把 `forgotten` 复用成可恢复状态。retire/restore 成功后按 [14](14-记忆修改审计方案决策.md) 尝试写一条 L1 `memory_audit` update；审计行只含上游方案定义的元数据，不写 actor 类别、理由码或 claim 正文。
- 存在退休覆盖行时，该 ID 不得进入 search、Resident、topic page source、向量候选、Dream 合并/裁决输入或任何 prompt bundle。所有读路径在排序前过滤；索引删除为同一 SQLite 事务的一部分，读路径仍以规范表状态为准。
- 退休时将其关联 topic pages 置 `stale` 并移除检索向量/词法索引；不能只隐藏 L1 而继续召回含同一正文的派生页。
- restore 仅允许明确用户/管理员操作；核原始 memory 仍是 active、`valid_until` 未到、scope 正确、至少有一条有效证据。恢复不会恢复旧 page/vector；页面与语义索引从当前有效来源重建。
- retired 记忆不自动参与 Dream，不因新事件相似、embedding 命中或模型建议而自动恢复。用户重新声明同一事实时，按新证据和 D6-8 规则处理，不得将旧 retired ID 静默激活。

### 3.2 API 与权限

增加 `POST /v1/memories/{id}/retire` 与 `POST /v1/memories/{id}/restore`（或等价版本化端点），均要求 expected version、幂等键、认证 scope 与审计。跨用户 ID 返回 404；重复 retire/restore 可幂等确认；版本不符返回 409。HTTP/CLI 响应回传状态与 ID，不在日志或错误中回显敏感正文。

Agent 可在用户明确要求“先停用/暂不使用”或“恢复使用”时调用 retire/restore 工具。工具必须附 `user_evidence_id`、`instruction_quote` 及其 `instruction_start_byte/instruction_end_byte`（用户这次指令在最新真实 user event 中的连续 UTF-8 byte span），以及目标 memory ID、expected version 和幂等键。Rust 校验 Bearer scope、该事件确为当前会话最新真实用户证据、quote 的原文字节位置、目标仍属本 scope 且状态/版本允许操作；Agent 不能自填 scope 或使用旧指令重放新操作。**Rust 的逐字校验不能形式化证明自然语言意图与目标 ID 的语义对应**；Agent 对“用户明确要求”的判断仍须在工具策略中约束，回执和审计保留来源 ID。证据不足时拒绝调用并引导用户在可信 UI/CLI 选定目标。Dream 子 Agent 永远没有 retire/restore/purge 写权限。

## 4. 永久删除（purge）

### 4.1 两阶段、不可逆

purge 和现有 `/forget` 是不同操作。purge 是不可逆的个人数据擦除，应只通过用户/管理员管理 API 或 CLI 执行，不向模型注册直接 purge 工具：

1. **预览**：按 scope、目标 ID、当前 version 计算依赖闭包，列出将移除的原子记忆数、来源事件数、页面数、索引/缓存对象数，以及因共享证据而受影响的其他记忆数。预览不修改任何业务记忆或索引，但生成随机一次性确认 token，将其哈希与 scope、目标/version、依赖 fingerprint、有效期写入短期 `purge_confirmations` 行；明文 token 只在响应中返回一次。
2. **确认并执行**：用户提交短期、一次性的 confirmation token 和 expected version；token 绑定 scope、目标与依赖 fingerprint。输入期间来源版本变化则返回 409，要求重新预览。Rust 在单个事务中提交可原子删除的规范数据和 purge 作业/结果；大规模索引文件清理可异步，但相关对象在提交时就必须标为不可读，不能在清理窗口继续注入。

### 4.2 删除范围与共享来源

- 删除目标 L1 claim、其 evidence links、revisions、relations、pin、两套审计中可关联的目标行、FTS/grams/vector 行，以及所有引用它的页面正文、页面 revisions 和语义索引。还必须删除/重建引用所删 L0 的旧 `memory_candidates`（保存 quote/claim）与 `candidate_evidence`、新 Dream candidates/adjudication 输入与结果，清除 `mutation_receipts` 中可反查目标的响应，不能留下派生正文或悬空 FK。模型摘要无法证明可以安全删掉某一个子句，因此引用被 purge 来源的整页作废并清除正文；之后可用剩余有效来源重新整理。
- 逐条检查目标的 L0 evidence。若事件还支撑其他 memory：先移除该 evidence link；其他 memory 仍有至少一条未 purge、有效 evidence 时保留，否则一并纳入预览与删除闭包。这样不会留下失去全部证据的 Active claim。
- 对纳入 purge 闭包的 L0 event 删除原文和所有向量/索引。L0 原始事件是不可变的正常证据流；**purge 是唯一经显式用户确认的删除例外**。
- `suppressed_sources` 等带目标 FK 的旧行按 FK 顺序清理；先写 `purge_tombstones(scope,evidence_id,created_at,operation_id)` 这类最小无正文标记，再删事件。tombstone 不存 claim、quote、embedding 或原始 JSON，不引用已删除的 memory/evidence 行，防旧 spool/event 重放重新入库。
- purge 后不得保留已 purge 的 claim、quote、evidence 正文或能直接反查目标正文的 revision。按 [14](14-记忆修改审计方案决策.md)，purge 闭包中的 `memory_audit` 行按 `record_id + scope` 一并删除；旧 `audit_events` 的 `target_id` 或 `detail_json` 引用闭包目标时也须删除整行，不保留关联 ID。D6-9 验证两张审计表、候选表和作业输入均无残留可反查 ID/正文。confirmation/job 的短期执行目标在完成后不保留可反查目标正文的关联。
- 数据库外既有备份不会因在线 purge 自动改写；备份保留期必须单独配置并如实告知。不得承诺“所有备份中的数据已同步擦除”。

### 4.3 数据模型与事务要求

新增 `0010_lifecycle_governance.sql`（不得修改 `0001`—`0009`）：增加可恢复退休状态、两阶段 purge confirmation/job 表、无正文 `purge_tombstones` 及必要索引；不新增第二套通用 lifecycle audit 表。迁移只增加 schema，不做既有记忆的批量退休/删除。purge 事务必须考虑 `memory_revisions`、`memory_relations`、`memory_evidence`、`suppressed_sources` 与 `memory_audit` 目标关联的清理规则，并由 SQLite `foreign_key_check` 验证。

若一次 purge 闭包超出可在单事务内安全完成的范围，先在同一事务把目标及依赖标为 `purge_pending`（不可读），以持久 job 分批擦除；重启可续做，幂等完成后写最终结果。任一阶段失败都不能把目标重新变成可召回状态，不能只删主行而遗留可搜索的页面/vector/cache。

## 5. 自动保留期与 `valid_until`

- 第一版提供可配置、**默认关闭**的清理能力。配置：`raw_evidence_retention_days = 0`、`expired_memory_purge_after_days = 0`；`0` 表示不做自动物理擦除。任何正值只能由可信用户/管理员配置写入，持久化策略版本、生效时间、scope 和操作者关联；doctor 显示具体截止策略。配置正值本身就是对该 scope 后续合规到期批次的持续清理授权，清理器不用逐批向用户索取 confirmation token。
- `valid_until` 是业务有效期：超过当前 UTC 后，search、resident、topic page、vector 和 Dream 输入立即排除；这是逻辑过期，不等于删除。清理器可在配置的 grace period 后把过期对象交给 purge 闭包。
- 原始 L0 retention 按 `recorded_at` 截止。若被删事件是某个 Active memory 的唯一证据，该 memory 与其派生页面必须一并进入删除闭包；若还剩有效来源，保留 memory 并移除已过期来源关系。
- 不按 `updated_at` 给全部 L1 设统一 TTL。老的 fact/preference/instruction 可能仍然有效；明确到期用 `valid_until`，历史事件依下节进行召回降权。
- 清理是无 LLM 的确定性 job；每批先计算闭包、记录影响数量、校验策略版本和生效时间，再用与手工 purge 相同的不可读标记/依赖删除/tombstone/重启续作流程执行。超出 configured per-run limit 时整体停止并报诊断，不静默部分清理。保留期策略从配置变更起生效，自动清理仅覆盖生效后进入该策略范围的数据；不追溯扩大删除范围，除非管理员显式执行 backfill/purge。用户取消或收窄策略后，尚未开始执行的旧策略 job 必须在提交前重新核配置版本并停止；已原子删除的对象不可恢复。
- `expired`、`forgotten`、`retired`、`superseded` 不能仅因不可见就被当成已物理删除。读路径过滤与物理清理是不同责任。

## 6. 召回时间衰减

### 6.1 应用范围

- 第一版仅对 `kind='episode'` 的 **Retrieved 排序**应用 recency。时间基准用 `occurred_at`；缺失时用 `created_at`；两者都缺失时 freshness=0.5（中性）。未来时间钳制为最新，不产生无界加分。
- `fact`、`preference`、`instruction` 使用中性 freshness，不因保存时间久而降低；Soul、pinned Resident、用户明确 pin 的 topic page 不受 recency 排序影响。它们只因用户取消 pin、正确纠错、退休、forget、有效期到达或 purge 离开上下文。
- recency 仅是 reranker 或归一化 RRF base score 的有限乘数；不能单独以“最新”取代相关性，也不能用它改 Active/retired/forgotten 状态、可信度、admission、valid_until 或 evidence。
- 没有 cross-encoder 时，应先把融合结果映射成有序且单调的 base relevance，再施加有界 recency multiplier；不得让同分 passthrough reranker 退化成纯按时间排序。

### 6.2 初始参数

采用 Hindsight 当前默认值作为可追溯工程初值，不声称是本项目最优参数：

```text
freshness = max(0.1, min(1.0, 1 - age_days / 365))   # linear 默认
recency_factor = 1 + 0.2 * (freshness - 0.5)
```

因此 freshness=0.5 时完全中性；最新事件最多约 +10%，线性衰减到 floor 后约 -8%，乘数区间 `[0.92,1.10]`。允许 `linear|exponential|none` 配置；exp 初始 half-life 90 天，`none` 为恒等因子 1。初值下两条 episode 的 base relevance 若高分 ≥ 低分 × 1.20，低分项不得只靠时间越级（最大乘数比 `1.10/0.92 < 1.20`）。配置只改变排序，不改记忆状态。没有本项目的固定对照集证据前，不调整默认参数，不宣称召回质量提升。

### 6.3 评价

离线固定 query/记忆 ID 对照必须证明：同等相关候选中近期 episode 可适度靠前；稳定 preference/instruction 不因存储年龄变化；低相关新记忆不能仅凭新近挤掉高相关命中；没有日期的 episode 不获偏置；设 `none` 时排序恢复为无 recency 的 base rank。报告 RRF/base、recency factor、final rank，禁止只报告最终答案文本。

## 8. 施工与验收入口

新增 D6-9 生命周期治理任务卡（[08](08-施工任务卡.md)），依赖 D6-1—D6-8 的 canonical memory、页面、Dream 与语义索引；D6-10 为最终验收与升级交付。接口增量见 [06](06-协议与DSH接线.md)，逻辑 schema 见 [02](02-数据模型与迁移.md)，Resident 条件见 [03](03-人格与常驻记忆.md)，排序见 [04](04-召回与上下文.md)，Dream 权限见 [10](10-写入触发与Dream执行模型.md)。

验收至少包括：

1. retire 后所有 recall/resident/page/vector/Dream 路径零命中；restore 后按有效证据恢复，旧 page/vector 不复活。
2. 现有 v1 `/forget` 仍保留证据与 revision，重放不复活；purge 预览列完整依赖，确认后正文与衍生索引全不可读。
3. 同一 L0 事件支撑多个 L1 时，purge 只保留另有有效来源支撑的记忆；无剩余来源的记忆一并从 active 状态物理清除。
4. purge 执行期间 kill/restart，job 恢复且不可读窗口不回滚；相同 confirmation 重放幂等，过期 token/版本变更返回冲突。
5. `valid_until` 到期在下一次查询/Resident/page 读取立即不可见；自动 retention 默认关闭，开启后只按配置的范围和截止时间处理。
6. 硬 purge 之后旧 event spool 重放被无正文 tombstone 挡住；日志、审计、错误和 `doctor` 不回显 claim/quote。
7. 同 query 下旧 episode 的 freshness 只产生规定范围内的排序变化；稳定 preference/instruction、pinned Resident 和 Soul 无 age penalty。
8. 全部状态在跨用户 scope 下 fail closed；Bob 猜测任何退休、forgotten、purged ID 均不能获得 Alice 的内容或存在性。

第一阶段不做真实模型海试；生命周期、purge 闭包、时间分数都可用固定数据和确定性测试验收。若 backup retention、删除授权或 shared-evidence 影响无法达到本契约，停止该 purge 子卡并报告具体差距，不降低“已永久擦除”的表述标准。

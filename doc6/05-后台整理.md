# 05｜后台整理：从原子记忆到问题画像与主题页

D6-11—D6-15 已为 Dream child 接入 job-scoped 只读探索和主题页更新，设计与实施记录见 [17](17-Claude AutoDream子Agent与记忆整理借鉴方案.md)。本文的来源版本、即时失效、CAS 发布与 Rust 写入权威仍是其实施边界。

## 1. 整理的职责

整理把 active L1 转换成两类可检索的**派生知识文档**：

- **问题画像（mental model）**：围绕一个已登记且版本化的问题生成紧凑答案，例如“用户长期偏好的工作方式”。首版问题目录默认为空；用户通过可信 CLI 显式登记、审阅、改写或归档问题。问题定义由服务端提供并固化到 job，模型不得自行创建问题或画像键。
- **主题页（topic page）**：把多条相关记忆组织成主题叙述，例如“工作技术栈”“正在进行的项目”“饮食相关偏好”。

两类文档都不修改 L0 事件、不替用户修改 L1 claim/status、不改 Soul、不自行 pin；每份内容都能追溯到冻结的 L1 来源。画像用于回答稳定问题，主题页用于跨主题/措辞浏览，二者不合并成新的原子事实。

Hindsight 的 observation/source facts、TencentDB 的场景块、EverOS 的 Markdown/反思是参考；本项目的发布规则由 SQLite scope、L1 版本和读时来源复核决定。

本文件定义问题画像与主题页的整理生命周期。候选与已有 L1 之间的精确去重、语义更新、冲突判定是独立流程，见 [09](09-语义准入与记忆合并设计.md)；派生文档不得代替 L1 合并，也不得覆盖原子 claim。

两类文档生成都是后台模型写入，必须受 [10](10-写入触发与Dream执行模型.md) 的 Dream trigger 管理；不得因为普通 turn/end、单次 L1 改动或每分钟轮询而独立启动 LLM。一次 Dream 可在 L1 裁决提交后继续生成/更新受来源约束的文档。管理员显式 `consolidate enqueue` 属于自定义触发，应先进入相同的持久队列和输入快照流程。

## 2. 触发与输入选择

每次 remember 成功创建 active、Dream 批次候选被 admit 为 active、correct 产生新 active 时，写事务只记录“该 scope 有新 L1 版本”状态；不在用户请求里等整理模型。forget/correct 同事务先失效依赖旧版本的页与向量。**只有 compact、定时 Auto Dream、自定义触发（包括管理员显式 `consolidate enqueue`）建立的 Dream job 才能启动页面整理模型**；阈值只决定一个已触发 Dream 是否包含页面整理阶段，不能单独启动后台模型。每 scope 最多 1 个 running，同 topic/input fingerprint 重复入队得到同一 job ID。

主题分组先用有界词法/现有索引获取相关 L1，最多 20 条、同一 scope、均 active、未退休且未过期；主题 key 由 Rust 规范化或从既有文档选取。问题画像只按当前 active 的登记问题定义检索有界候选；没有登记问题或没有相关来源时不生成画像。输入同样必须处于同一 scope 且 active、未退休、未过期。Rust 为两类任务分别固化 kind/key、问题定义版本（仅画像）、source ID/version/hash 与 generator version；模型不能改变这些字段。主题页至少需要 2 条来源，画像至少 1 条；不满足就不生成，留原子记忆供 resident/检索使用。问题更新/归档使旧画像立即 stale，并取消尚未提交的旧问题版本 job。首次历史回填是**显式** `consolidate enqueue --all-scopes` 的独立运维动作，不在迁移时自动调用模型。

每个 job 持久化明确的 source ID/version/hash 列表及 generator version。调度事务提交后才进行网络请求。模型调用不持 SQLite 锁；领取、心跳、提交、失败状态均使用短事务。退出/断线的过期 running 恢复、generation 防旧执行者写入、确定性错误立即 dead、可重试错误退避，沿用 doc4 作业原则。知识文档整理与 Dream 候选裁决可以分阶段持久化和独立恢复，但所有后台 LLM 阶段都必须从同一个已触发 Dream job 派生，不能各自按 turn、定时轮询或单次 L1 改动启动模型。

## 3. `consolidate_v1` 模型契约

模型接收的只有该 job 输入中的 memory ID、claim、kind、时间与有限证据引用；提示词不得让模型直接读其他用户或生成保存指令。输出严格 JSON：

```json
{
  "pages": [
    {
      "topic_key": "work-stack",
      "title": "工作技术栈",
      "body_md": "用户从事后端开发，主要使用 Rust。",
      "source_memory_ids": ["<memory-id-1>", "<memory-id-2>"]
    }
  ]
}
```

每响应最多 4 页；title 1—80 字、正文 1—1200 字、每页 2—20 个不同 source ID，全部必须包含在 job 固化输入且仍处于同版 active；不接受额外字段、空来源、跨 scope ID、模型自填 status/version。正文不要求逐字 span，因为它**标为派生摘要**；Rust 只保证引用存在且版本一致，不声称能形式化证明摘要每一句的真实性。模型置信度不能越过此边界。

Prompt 修改需新 `generator_version`；旧 job 按保存版本分派，未知版本确定性 dead。输出解析可剥 Markdown 围栏，但剥离后仍严格校验。敏感正文不写日志；记录模型名、tokens、耗时、job ID、source ID 数和错误码。

### 3.1 `mental_model_v1` 问题画像契约

一个 job 只回答其冻结的问题定义。模型输出严格 JSON：

```json
{
  "question_key": "preferred_work_style",
  "answer_md": "用户偏好先看结论，再看关键取舍。",
  "source_memory_ids": ["<memory-id-1>"]
}
```

`question_key` 必须与 job 一致；模型不得增删问题定义。答案须引用 1—20 个且全部来自冻结输入、提交时仍同版 active 的来源 ID；不接受额外字段、跨 scope ID、模型自填 status/version。输出以派生摘要显示，不声称逐字或形式化真实。画像问题或定义版本变化时，旧画像立即失效后再按新定义重建。

## 4. 发布与读路径

同一事务里核对 claim generation、输入 fingerprint、全部 source L1 的 status/version/hash/有效期，写入新/更新派生文档、sources、revisions 与索引；任一源变化就不做部分发布，置 `stale_input`，调度新输入批次。同 kind/key 的新文档用 CAS 版本替换旧 published；旧版留 revisions，普通检索不可见。模型若返回无文档，作业 `succeeded` 且结果计数 0，不能强造内容。

读路径再次核对 source 版本、退休状态与有效期。correct、retire、forget、purge、valid_until 过期后旧页不应被模型看见，即使后台恢复尚未运行。correct/retire/forget/purge 通过事务即时 `stale` + 索引移除；时间自然过期靠读时条件立即生效，下次维护可将其持久状态标 stale。不要以“定期重建很快”为理由允许一轮陈旧读取。见 [12](12-遗忘、过期与时间衰减方案决策.md)：页面归档/`deprecated_by` 只代表自动 consolidation 的软归档，不等于用户 forget 或个人数据 purge；Dream 只能沿语义裁决形成 supersede/归档关系，不能发起 retire、forget 或 purge。

问题画像与主题页默认仅进入**按需召回**；用户审阅并明确 pin 后才进入 `memory.md` 的派生文档区。pin 不改变文档的派生地位，来源失效时它立即退出 resident。文档与原子记忆冲突、题目过宽、模型编造时，用户可查看来源、解除 pin 并归档；归档文档保留 revision 但不搜索。即使文档质量不好，L1 原子记忆和 L0 证据仍保留。

## 5. 失败、重试与运维

| 情况 | 处理 |
|---|---|
| 模型超时/429/5xx | 退避至 3 次，再 dead；L1 不受影响；管理员可用完整 job ID retry |
| JSON 格式错、未知 generator version、输入超限 | 确定性 dead；不得反复调用同一坏请求 |
| source 在模型运行中被纠错/遗忘 | `stale_input`，不发布；新来源可重排队 |
| source 在模型运行中被退休/永久删除 | `stale_input`，不发布；purge 还须清理引用来源的页面正文和派生索引 |
| 页索引失败 | 按同一事务回滚或标 index_dirty 并使页不可检索；不能出现“页正文更新而旧向量继续 ready” |
| worker 崩溃 | lease 到期恢复，generation 拒绝旧执行者提交 |
| 没有配置模型 | 不启动整理 worker；resident/原子搜索正常，诊断明确 `consolidation=disabled` |

CLI 至少支持 `consolidate enqueue/status/retry`、`pages list/show/archive`、`mental-model questions list/add/update/archive/reactivate`；HTTP 读端点见 [06](06-协议与DSH接线.md)。doctor 给出按状态计数、最老排队时长、stale 页数、向量 backlog；不在诊断中输出私密正文。

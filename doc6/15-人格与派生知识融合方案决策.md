# 15｜人格与派生知识融合方案决策

D6-11—D6-15 已在上述 Soul/Resident/派生知识角色边界内接入 Dream child 读取和整理，设计与实施见 [17](17-Claude AutoDream子Agent与记忆整理借鉴方案.md)；不改变问题目录默认空、派生数据进入 user-role 和 Resident 由用户 pin 控制的决定。

状态：**方案已按 D6 实施**（2026-09-28）。Soul、Resident、来源化派生页及 user/system 角色边界的代码档位见 [doc-handoff/14](../doc-handoff/14-D6交付记录.md) 与 [doc-handoff/20](../doc-handoff/20-D6-11-15交付记录.md)。本状态不代表真实模型遵循效果、全部验收矩阵或部署已完成。

## 1. 决策

不把上游某一个项目整套照搬，而是按职责融合三类机制：

1. **明确人格采用用户主写**：每个用户/Agent 的 `soul.md` 由用户编辑、版本化并显式导入。它是人格与行为边界的唯一指令来源，进入 system prompt；LLM 可以给出建议，但不得自动改写、覆盖或把推断出来的个人资料升级成 Soul。
2. **长期知识采用有来源的模型派生文档**：从规范 L1 记忆经 Dream 整理出两种不同文档：
   - **问题画像（mental model）**：围绕一个已登记、版本化的问题生成精简答案，例如某项长期偏好或持续目标；用于回答与该问题相关的查询。
   - **主题知识页（topic page）**：把多条相关 L1 记忆组织成可浏览、可检索的主题摘要。
   两者都保留 L1 ID、版本和内容指纹，具有生成器版本，可审阅、重建；它们是派生数据，不是新事实来源，不是用户原话，也不是人格指令。
3. **注入采用明确角色隔离**：借鉴 TencentDB 的注入职责分层，但边界按本项目语义定义：只有用户编辑的 Soul 进入 system section；Resident、按需召回的 L1，以及问题画像/主题页都作为带来源的数据进入 user-role context。派生文档仅在相关召回或用户明确 pin 时进入上下文，不把所有画像无差别地常驻注入。
4. **Markdown 用于可读与交换，不制造第二真相**：保留 Soul 的 Markdown 编辑/导入体验；派生画像和主题页可以 Markdown 展示/导出，但其权威状态、来源和版本仍由 memoryd/SQLite 管理。`memory.md` 继续是 resident 的可重建视图，不成为独立可写数据库。

## 2. 权威与数据流

```text
用户编辑 soul.md ──显式导入/CAS──▶ 版本化 Soul ──▶ system prompt

L0 evidence ──▶ 有证据的 L1 ──Dream 整理──┬──▶ 问题画像 ─┐
                                          └──▶ 主题知识页 ─┴──▶ 相关召回 / 用户 pin
L1 + pin + 有效派生页 ──▶ resident 选择 ──▶ memory.md 视图 / sourced user context
本轮 query ──▶ L1 与派生文档检索 ──▶ sourced user context
```

权威边界：L0 是可定位的原始证据，L1 是服务端裁决后的规范记忆；Soul 是用户明确写下的 Agent 指令；问题画像和主题页是可丢弃、可按仍有效来源重建的投影。`soul_profiles`（Soul 存储实体）与派生的 mental model 不是同一种 profile，不得互相覆盖或混称。

如果派生文档与 L1 或 Soul 冲突，不能让摘要自行裁定：模型上下文应清楚标出派生属性与来源；来源不一致时立即停止使用并重建。要更改事实须 correct/remember 对应 L1；要更改人格须由用户编辑并导入 Soul。

## 3. 生命周期与安全边界

- 每个问题画像由 Rust 按登记的问题键和定义版本创建冻结输入；模型不能自行创建问题键、scope、source ID、文档状态或版本。
- 首版问题目录默认空；只有用户通过可信 CLI 显式登记的问题才能驱动画像生成，用户可继续审阅、改写或归档。没有 active 问题或没有相关有效 L1 来源时不发布空答案；主题页整理独立于问题目录。具体 key、版本及迁移见 [02 §3](02-数据模型与迁移.md#3-0006_derived_knowledgesql)。
- 生成输入只包含同一认证 scope 下、当前 active 且有效的 L1 候选。Rust 固化每条来源 ID/version/hash；提交时再次核验。模型输出无效或引用范围外来源时拒绝发布。
- 任一来源被纠错、退休、forget、purge 或到期时，依赖它的画像/主题页立即 stale 且不可召回、不可注入；后台重建不承担即时撤销正确性。
- 用户可查看来源、pin/unpin 或归档派生文档；pin 只改变是否进入 resident，不提升其事实权威，也不改变其 user-role 数据属性。
- 派生文档生成沿用持久 Dream trigger/job；普通 turn/end、单次 L1 改动和轮询不得各自启动 LLM。
- profile 问题目录、查询选择算法、预算及 API/schema 细节按 [02](02-数据模型与迁移.md)、[05](05-后台整理.md)、[06](06-协议与DSH接线.md) 和 D6-5/D6-6 实施卡落实；本次文档决策不代表新增迁移或运行代码已经完成。

## 4. 取舍

这套融合保留了 Soul 的人类可控性，同时允许系统把长期记忆整理成更易检索的画像和主题知识；注入角色也能避免把模型生成摘要当成高权威 system 指令。相比单一 Markdown 真相源，它更容易即时处理来源撤销；相比只靠原子记忆，它能回答跨多条记忆的问题。

代价是多了一种派生文档生命周期：需维护问题定义/生成器版本、来源依赖、失效与重建；画像可能过时或概括失真；召回和 prompt 预算也要防止重复注入。故不得无来源发布，不得全部常驻，必须能追到 L1/L0、即时失效，并通过正确沉默和有/无记忆对照评估。

## 5. 采用与不采用的上游部分

- **Hindsight**：借鉴问题驱动的 mental model 与主题知识整理思路，以及来源约束和可重建的 consolidation；不要求复刻其完整存储、生命周期或产品接口。
- **TencentDB**：采用人格与动态记忆的 prompt role 分层；不采用整套 L0-L3、MemoryProxy、场景导航，也不把其自动生成 Persona 当作用户授权的 Soul。
- **EverOS**：借鉴 Markdown 的可读、可编辑体验及来源可追溯理念；不把所有派生 Markdown 文件设为独立事实源，也不默认启用未使用的 `soul.md` 机制。

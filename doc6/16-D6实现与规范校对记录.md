## 1. 结论摘要

**D6-0—D6-10 共 11 张实施卡，不等于 15 份规范文档。** 15 份文档共同构成规格；任务卡 08 将工作拆成 11 张卡。把 11 个卡号都列入提交链，只能证明按卡记录了实施过程，不能单独证明 15 份规范都已实现。

本次核对发现，D6 已有较多可用代码，Soul、Resident、HTTP bundle、向量/裁决数据结构、Dream 账本、purge preview/confirm 等部分确实落地；但**当前证据不足以称 15 份规范全部实现或 D6-0—D6-10 全部验收完成**。至少存在主题页 LLM 作业无执行器、DSH compact 未接线、Dream runner 与任务卡要求不一致、retire/restore Agent 工具缺失、自动 retention 未调度、若干来源/审计不变量不完整等阻断性差距。

这里区分四种情况：

- **代码存在**：源码中有该结构或路径；不代表该路径真实运行。
- **本地确定性测试/临时库**：只证明相应测试和本地固定响应路径。
- **宿主/端点未验证**：交接记录明确未验证，不能提升为通过。
- **规范偏差**：源码路径已与文档要求不符，不是简单“尚未做真实模型测试”。

## 5. 具体差距与证据

### C01｜主题页/问题画像整理没有消费执行器

- 规范：`doc6/05 §1—5`、`doc6/08 D6-5`、`doc6/15 §2`。整理模型只能由已持久化 Dream job 启动，成功后 Rust 校验并发布页面。
- 源码：`agent-memory/crates/memory-store-sqlite/src/consolidation_jobs.rs` 有作业存储方法；`agent-memory/crates/memory-server/src/main.rs::run_consolidate_action`（约 1297—1358）只 enqueue 并明确提示模型调用尚待 Dream runner；`dream_worker.rs` 没有 `consolidation_claim`/`publish_page` 调用。
- 影响：手工 `consolidate enqueue` 直接创建独立 consolidation job，未创建 Dream trigger/frozen Dream input；队列无人消费，不能产生可发布页面。
- 结论：D6-5 当前是**存储/API 骨架**，不是后台整理链路完成。

### C02｜Compact 事件存在，DSH adapter 未接；Dream worker 架构与任务卡不一致

- 规范：`doc6/08 D6-4/D6-7`、`doc6/10 §4/§6/§8`。普通 turn/end 不启动模型；compact 真实 emitter 可用时 adapter 应提交 trigger；D6-7 要求在官方 DSH 子 Agent/Job 进程实现受限 Dream Agent。
- 官方源码记录：`doc-handoff/13 §4` 给出 `packages/compaction/compaction-basic/src/region.ts` 的 `compaction/start`、`compaction/end` 持久事件 emitter，并明确应监听 `session/event` 的 `compaction/*`。同文 §5.3 确认 DSH 有 `ctx.subagents` seam。
- 项目源码：`agent-memory/adapters/dsh/src/index.ts` 只注册 `session/event` 用于 L0 capture，没有 compaction 分支，也没有 Dream trigger 调用。`memory-server/src/main.rs` 启动 `dream_worker::spawn_dream_pipeline` 作为普通 Tokio worker；并非 DSH subagent。`doc-handoff/14 §1` 选择称其为 memoryd 内置 runner，但没有记录对 `doc6/08 D6-7` 明确要求的修订/批准。
- 影响：compact 用户配置不会启动 Dream；DSH 退出后 worker 生命周期、权限隔离和受限子 Agent 契约均未由所要求的宿主路径证明。
- 结论：不能以“compact 未验证/宿主 capability disabled”结案，因为 D6-0 源码核对已经找到真实 emitter。

### C03｜Auto Dream 缺少关闭配置；embedding 缺失与 provider failure 状态不符

- 规范：`doc6/01 §4`、`doc6/10 §4.2/§5`、`doc6/07 E23`。默认启用但用户可设 `dream.enabled=false`；缺少 embedding 时不启动批量模型链，L0 保持待处理；provider failure 保留 assigned/frozen input 并可恢复。
- 源码：`memory-server/src/main.rs` 的 scheduler 无条件启动；`config.example.toml`、DSH adapter 配置都未定义 `dream.enabled`。`dream_worker.rs` 在只有 chat client 时仍 claim 并调用 `process_dream_extract`；`freeze_adjudication` 无 embedding 时仍以 exact/lexical 构造裁决输入（embedding_model_id 为 NULL），这与“未配置 embedding 不启动自动应用链”不等价。模型失败路径第 434 行调用 `dream_provider_wait(..., 0, ...)`，而父 job 领取后 generation 非零，更新会被 generation 条件拒绝。
- 影响：不能关闭定时 Dream；缺少语义 provider 时会产生部分模型处理；失败后父 job 状态可能仍为 running，而不是可诊断 provider_wait。

### C04｜成功 Held 候选没有按新证据重新裁决入口

- 规范：`doc6/02 §5`、`doc6/09 §7`、`doc6/10 §5`、`doc6/07 E23`。相关新证据或用户显式重裁时，新 Dream 的冻结输入可以包含旧 Held candidate ID 及其来源；相同指纹只裁决一次。
- 源码：`memory-store-sqlite/src/dream_jobs.rs::dream_accepted_candidates`（约 497—550）筛选 `c.dream_job_id=?` 且 `status='candidate'`，只取当前 job 候选。未发现查询或冻结旧 Held candidate 的路径。
- 交接记录：`doc-handoff/14 §5` 以“exact hash 入口已满足”解释该限制；但 exact hash 只比较现有 Active memory，不能实现对 Held candidate 的再次裁决，也不能满足新证据进入新 adjudication fingerprint 的契约。
- 结论：Held 自动重裁是**未实现**，不只是“召回覆盖有限”。

### C05｜retire/restore 未覆盖 Agent 工具及派生页读路径

- 规范：`doc6/03 §4`、`doc6/05 §4—5`、`doc6/06 §2/§3`、`doc6/12 §3`、`doc6/15 §3`。retire/restore 工具带版本、幂等键、最新用户证据 byte span；退休/到期的来源必须立即从页面与所有注入路径消失。
- 源码：`adapters/dsh/src/tools.ts` 注册 search/get/remember/correct/forget，没有 `memory_retire`/`memory_restore`。HTTP retire 复用旧 `ForgetRequestBody`；restore body 与 store 方法没有 expected_version/idempotency_key，证据校验与状态 mutation 分开执行。`memory-store-sqlite/src/lifecycle.rs::retire_memory` 不调用 `stale_pages_for_memory`；`pages.rs::get_page` 只核 `published`、来源 memory 的 `active/version/hash`，未核 `memory_retirements` 或 `valid_until`。
- 影响：Agent 无法按 doc6 调用生命周期工具；已退休或到期 L1 的派生页可能仍通过 page search、get 或 pinned resident 读取。

### C06｜Dream 输入/应用未过滤被抑制或退休来源

- 规范：`doc6/01 §3—5`、`doc6/02 §8`、`doc6/09 §6—7`、`doc6/10 §5/§10`、`doc6/12 §3`。forgotten、retired、purge_pending、过期来源不得被 Dream 重放或用于更新/复活。
- 源码：`memory-store-sqlite/src/dream_jobs.rs::dream_trigger` 以 user role/source_kind 和 `dream_evidence_state` 选择待处理 L0，查询没有排除 `suppressed_sources`，也没有检查证据已关联的 `memory_retirements`/过期记忆。`adjudication_apply` 的 create/update 应用路径需再加同一生命周期/抑制复核；现有读路径过滤不能替代写入事务的复核。
- 影响：被 forget/retire 的历史证据可能进入新 Dream 批次；若模型据此产生候选，存在重新建立 Active 或附着到旧目标的风险。

### C07｜`memory_audit` 覆盖面与 best-effort 语义不符

- 规范：`doc6/02 §8`、`doc6/14 §1/§4`。对已有 L1/L2/L3 的 update/delete 尽力写元数据审计；审计失败须告警但不回滚业务修改。
- 源码：`memory-store-sqlite/src/lifecycle.rs` 的 retire/restore 在同一事务里调用 `record_l1_audit_tx(...)?`，audit 失败会回滚主修改。旧 v1 correct/forget 与 Dream adjudication 更新未见 `memory_audit` 投影；页面更新/删除路径也未见相应 audit 调用。
- purge 关联：`memories.rs` correct 在 `audit_events.detail_json` 写入 `old_memory_id`（约 828—833）；`purge.rs` 只按 `audit_events.target_id` 删除（约 397），旧 ID 若只出现在 detail_json 会残留可反查记录。

### C08｜正值 retention 没有自动 worker，L0 清理条件不满足依赖闭包规则

- 规范：用户已确认正值策略可自动清理无需逐批确认；见 `doc6/02 §7`、`doc6/06 §2`、`doc6/08 D6-9`、`doc6/12 §5`。
- 源码：`retention_run` 存在于 `purge.rs`，当前调用点只有 `main.rs` 的 CLI `retention-run` 分支；serve scheduler 中只有 Dream 定时器，没有 retention worker。raw evidence SQL（`purge.rs` 约 529—530）按 `occurred_at` 截止并直接排除所有有 `memory_evidence` 关系的旧 event；规范要求按 `recorded_at`，处理过期来源关系，并在唯一证据过期时把关联记忆/页面加入删除闭包。
- 影响：已确认的持续策略不会自动执行；L0 retention 只处理“从未关联记忆/作业”的事件子集。

### C09｜purge 修复存在于工作区，不存在于当前提交 HEAD

- 交接记录：`doc-handoff/14 §3` 称 `suppressed_sources.forgotten_memory_id` 闭包缺陷已在提交中修复。
- 当前 Git 证据：HEAD `040a0ce` 的 `purge.rs` 没有按 `forgotten_memory_id` 删除的 SQL；工作区 diff 增加了该删除（当前约 353—358 行），状态为 `M`。
- 结论：当前本地源码含修复候选，但提交链/干净 checkout 不含该修复；本轮没有运行测试验证这个未提交补丁。不得把它报成已提交、已验证。

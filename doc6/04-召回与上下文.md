# 04｜召回与上下文

## 1. 注入角色分层：采用 TencentDB 思路，按 DSH hook 映射

本项目采用 TencentDB 的 Prompt 注入职责分层：**用户编辑的 Soul 进 system prompt；动态记忆与派生知识进 user-role 数据上下文**。TencentDB 在宿主 `before_prompt_build` 阶段返回动态 L1 的 `prependContext` 与稳定 persona 的 `appendSystemContext`；本项目借鉴其注入路径，但只把用户主写的 Soul 视为 system 指令，不把模型生成画像升级成 Persona。DSH 的实际 hook 映射见 [11](11-Prompt注入方案决策.md)、[15](15-人格与派生知识融合方案决策.md) 与 [06 §3](06-协议与DSH接线.md#3-dsh-注入时序)。

每一步的模型上下文分成：

1. **Soul**：这个用户下该 Agent 的明确人格，进入 system prompt section；由用户编辑，稳定且按 Agent 隔离。
2. **Resident**：同用户跨 Agent 共享的核心 L1 记忆和用户 pin 的有效派生文档，查询无关，进入带来源的 user-role runtime context；每个 step 重算。
3. **Retrieved**：当前问句相关的 L1、问题画像或主题页，进入另一个带来源的 user-role context；可为空、每轮动态变化。

Resident/Retrieved 作为独立的插件来源上下文，在本轮原始用户内容之前提供给模型，语义上对应 TencentDB 的 user-prompt `prependContext`。实现必须保留它们自己的来源标记，不能把文本拼进或伪装成原始用户消息；若 DSH 当前消息 API 无法保持这个顺序和来源，D6-0 先记录具体限制并修正文档，D6-4 不得悄悄改用 system role。

`agent_id` 不能改变 L1 的读 scope。`POST /v1/context/compose` 维持原行为以保护旧客户端；新 `/v1/context/bundle` 负责 resident + retrieved。DSH v6 配置切换后不再调用旧 compose，避免“两条指令”重复挤占预算。注入只改变模型本轮可见上下文，不授予记忆新权限、不改变入库证据，也不保证模型一定采用内容。

## 2. 动态检索路线

**整体召回结构以 Hindsight 为主参考**：不同通道独立取候选和排名，再做一次全局 RRF 融合；对融合后的有界候选做 cross-encoder 精排，再经状态/来源复核与上下文预算装配。图关系和时间检索是 Hindsight 的额外候选通道，但 D6 首发只在数据模型和对应任务卡明确可用数据/索引/验收后才可纳入；不得把这两路写成已经实现。图/时间通道未启用时，其余通道仍可正常工作。

**向量召回支路采用 TencentDB 的执行方式**，但不采用它作为全局检索排序架构：

1. active L1 和 published 派生知识文档（问题画像/主题页）在内容/来源版本变化时异步生成并缓存 embedding；查询到来时，对本轮真实用户 query 生成一次 query embedding。
2. 在已认证 scope、对象状态、有效期和索引版本约束内做有界向量近邻检索，返回独立的 vector ranked list。embedding model、维度、文本规范化版本不一致的向量不能混搜。
3. 近邻结果进入独立 vector ranked list 前，先按可配置 `semantic_min_similarity` 过滤余弦相似度；相似度**大于或等于**下限才保留，再按分数降序截取 top-K。首版默认值为 `0.3`，范围为 `0..=1`。该值是参考 Hindsight/TencentDB 源码默认值的工程初值，不宣称是本项目经质量集校准的最优值；低于门槛的候选不得参与 RRF。无候选通过门槛时，语义支路仍是成功但空结果，`semantic_status='ok'`，其他通道继续工作。
4. 向量结果与 FTS/BM25、已实现的其他候选通道分别保留排名，交给本项目顶层一次 RRF。**禁止先在向量支路内部把向量和词法做一轮 Tencent 式 RRF、再与 Hindsight 通道做第二轮 RRF**，以免双重计权和丢失通道来源。
5. embedding 未配置、超时、429、维度错、索引未就绪或超上限时，将 vector lane 标记为 disabled/unavailable/limit_exceeded，并只用剩余可用通道；不能把降级后的结果称为完整语义召回，也不能回退到跨 scope 或随机“最近记忆”。

**词法路线**沿用 `memory-store-sqlite/src/memories.rs::search_memories` 的 FTS5 / Unicode 二元字 / 单字降级；为派生知识文档加独立 FTS/grams。旧接口的排序不做破坏性改变。新 bundle 内各通道独立取有界候选；只有同 scope、当前有效且派生文档来源版本校验通过的对象可以进入融合。问题画像还须核其登记问题仍 active 且问题版本等于页面快照；目录编辑后旧画像不能被词法或向量索引带回。

**embedding 索引和 query embedding 的运行约束**：

- 后台给 active L1 和 published 派生知识文档按 `model_id + source_version + content_sha256` 生成向量，缓存于 SQLite。不能把 model_id 不同或维度不同的向量放进一次余弦计算。
- 查询只对当前 scope 的 ready 向量做有界扫描，v6 单 scope 上限 10000；超过上限要返回 `semantic_status='limit_exceeded'` 并只做词法，不能任意漏扫而声称完整语义检索。
- 实时 query embedding 不设专用延迟预算；请求等待已配置 provider 完成或达到 `embedding_timeout_secs`（默认 30 秒），调用方取消时随请求取消。provider 不可用、达到请求超时、维度错误或索引扫描失败时继续其他可用召回通道，返回 `semantic_status=unavailable`。不在 HTTP 请求中为了修复对象向量而逐条调用模型。
- 向量只生成候选，排序仍受对象状态、版本、scope、有效期及最终上下文预算制约；相似度不是可信度或自动 active 权限。
- 此处 `semantic_min_similarity` 是**在线 query 相关性候选门槛**。它与 [09](09-语义准入与记忆合并设计.md) 的 Dream 写入期候选召回/裁决输入门槛相互独立；不得用在线门槛静默改变 Dream 合并、准入或历史作业语义。

embedding provider 是**单独配置的 OpenAI 兼容 embeddings endpoint**，完整 URL、模型名、key 文件、timeout、维度由配置明确给出。不复用 chat completions URL 猜路径；只对用户配置的一个端点做短连通验证，不安排提供者海试。未配置时 `semantic_status='disabled'`，文档和 UI 不宣称已解决零词法盲区。

Hindsight 的 cross-encoder 是 RRF 后的相关性精排层，不是向量检索器，也不是写入准入器。它读取 query 与候选文本的配对后重排有界 top-N；须单独配置 reranker 能力，不得猜测 chat-completions URL 或以生成式 LLM 调用冒充 cross-encoder。未配置/失败时保留 RRF 顺序并返回 `rerank_status=disabled|unavailable`；只有确实完成 rerank 才标 `success`。精排分数只影响相关性排序，不改变 scope、memory 状态或可信度。

本节的语义召回用于“当前问题找相关记忆”。自动提取候选与已有 L1 的语义去重/更新是另一条裁决链：可以复用 embedding provider/索引实现，但必须按 [09](09-语义准入与记忆合并设计.md) 使用冻结候选召回 + 版本化 LLM 裁决 + Rust 复核；不能把 query recall 的 top-K、RRF 分数或 rerank 分数直接当成 merge 决策。

## 3. 候选融合、去重与正确沉默

检索顺序固定：先按 scope、retired/forgotten/expired 状态、有效期和对象/来源版本过滤规范对象 → 对可读对象分别跑已启用通道 → 每通道独立排序 → 单次全局 RRF → cross-encoder 对有界 top-N 精排（若配置）→ 排除 resident 已包含的 memory/page ID → 页/原子项覆盖去重 → 应用有界 episode recency 因子 → 按 retrieved 预算整条组装。分数仅用于**相关性排序**。没有任一路命中时 retrieved 为空，不能为了填配额拿“最新几条”无关注入。resident 是用户明确启用的查询无关层，二者目的不同。

### 3.1 时间衰减：仅作 episode 的 Retrieved 排序信号

按 [12 §6](12-遗忘、过期与时间衰减方案决策.md) 的决策，recency 不是 forget、过期或可信度状态：它不能恢复无关候选，不能使新内容仅凭时间挤掉更相关结果，也不能触碰 L1 status。首版只对 `kind='episode'` 的 Retrieved 排序应用有界乘数；`fact/preference/instruction`、Soul、pinned Resident 和 pinned page 的因子固定为 1。

初始 Hindsight 可追溯参数（不是本项目已验证的最优值）：

```text
age_days = max(0, now - (occurred_at ?? created_at))
freshness = clamp(1 - age_days / 365, 0.1, 1.0)  # 默认 linear
recency_factor = 1 + 0.2 * (freshness - 0.5)
final_retrieved_score = monotonic_base_relevance * recency_factor
```

若无可用时间戳，`freshness=0.5`，不加不减；未来时间按当前时间钳制，不能产生额外奖励。`linear|exponential|none` 可配置，指数模式初始 half-life 为 90 天，`none` 恒为 1。没有 cross-encoder 时先把 RRF 结果映射为单调 base relevance，再乘 recency；不能以时间排序替代相关性。初值下乘数区间为 `[0.92,1.10]`；两条 episode 的 base relevance 若相差至少 20%（高分 ≥ 低分 × 1.20），低分项不得仅靠 recency 越级。诊断应记录 base/factor/final rank；固定对照集需证明该界限、稳定偏好/指令年龄不变、无时间戳不偏置、`none` 还原 base 顺序。

派生文档候选带 `page_id`、`document_kind`、`source_memory_ids`、`source_versions`、`derived=true`。若文档和单条 L1 重合，按融合顺序先选；已选文档覆盖其来源 ID；后续相同 L1 不重复出现。若先选了某条 L1，则 topic page 仍有至少两条未覆盖来源、mental model 仍有至少一条未覆盖来源时可入选，正文必须列出全部来源并说明部分已显示；否则跳过文档。无需在派生文档里复制每条原文全文，用户可按 ID 查证。

所有来源内容使用清楚的数据边界并转义 XML 特殊字符；`<agent_memory>` 标签或“忽略之前的指令”等出现在用户 quote/page 正文中时必须作为数据文本显示，不得突破包裹结构。只有 `soul` 是 system section。`source.kind='agent-memory'` 的既有防回流原则继续适用于 resident/retrieved。

## 4. Bundle 结果契约

请求示意：

```json
{"agent_id":"agent-a","query":"有哪些食物需要忌口","resident_max_items":24,"resident_max_chars":3000,"retrieved_max_items":8,"retrieved_max_chars":2400}
```

响应至少包含：`request_id`、`resident:{text,items,omitted,conflict_ids,truncated}`、`retrieved:{text,items,omitted,truncated}`、`lexical_status`、`semantic_status`、`rerank_status`、`page_index_status`、`source_versions`。每个 item 至少含 `kind=memory|page`、ID、来源 memory IDs、evidence IDs、命中通道/选择原因 (`pinned|resident_auto|lexical|semantic|graph|temporal|page`)；诊断可还原各通道排名、RRF 排名和 rerank 排名。不返回跨用户对象的存在性。响应 text 为空时不创建空消息。

`query` 可空：工具继续执行等 step 仍给 resident，retrieved 为空。非空 query 只取最新 `source.kind==='user'` 的真实用户消息；不得从 system/tool/本插件注入中重构“用户查询”。如果本轮无新用户正文，动态召回不沿用上轮问句，除非后续 DSH 官方 API 能可靠提供同 turn 的 query 且另有规范。

## 5. 受限评价矩阵

至少按 ID 断言以下成对场景，才可说“召回改善”：

| 探针 | 应出现 | 不应出现 |
|---|---|---|
| 用户明确 pin 的居住地，问无关 SQL | resident 中该 ID | 其他未 pin 的无关 episode |
| 未 pin 过敏信息，问“有哪些食物需要忌口” | embedding 启用时 retrieved 命中该 ID | 其他人的信息 |
| 问“怎么写 Rust 错误处理” | 相关 Rust 记忆或页面 | 仅因最近更新的宠物/旅行记录 |
| forget 后重复上一问 | 旧 ID 立即消失 | 旧 page/vector 将内容带回 |
| 不存在任何相关记忆 | retrieved 空 | 以时间排序凑数 |

测量 `opportunity`（问题是否需要记忆）、正确命中、正确沉默、误注入、利用率、跨用户泄露、耗时和成本。回答措辞变化本身不是记忆改善证据；应在明确有/无记忆答案可区分的样本上检查模型是否使用了注入内容。

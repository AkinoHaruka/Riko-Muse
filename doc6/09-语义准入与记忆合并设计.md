# 09｜语义准入与记忆合并设计

状态：**设计已按 D6 实施；真实模型语义质量仍未验收**（2026-09-28）。后台抽取/语义裁决仅由 [10](10-写入触发与Dream执行模型.md) 的 Dream trigger 启动；普通 turn/end flush 不自动触发 LLM。主 Agent `memory_remember` 保持即时路径。现有 `extract_v3/admit_v1/admit_v2` 以及 `memory_remember` 行为保持不变；新流程使用独立版本与迁移。实现及固定响应证据见 [doc-handoff/20](../doc-handoff/20-D6-11-15交付记录.md)，该记录不证明真实模型整体准入或合并质量。

## 1. 决策摘要

采用融合方案：

- **Hindsight 为主要参考**：embedding 召回语义相近的记忆，再由 LLM 判断是补充、更新还是保留为不同记忆；整理结果保留来源关系。
- **TencentDB 为批处理流程参考**：先召回候选，再批量裁决；L0 证据摄取保持幂等，语义判断不混进原始事件写入事务。查询时的向量召回实现取舍见 [04](04-召回与上下文.md)：TencentDB 选择仅限定用户问题的向量召回支路，不覆盖本节 Hindsight 风格的 merge/adjudication 方案。
- **沿用本项目的证据优势**：每个自动提取候选仍必须指向当前提取窗口内的用户事件，并通过 Rust 的逐字 byte-span 校验。模型不能编造 source ID、quote 或 scope。
- **Rust 仍是写入裁决与一致性边界**：模型给语义建议；Rust 校验版本、来源、scope、目标记忆状态，并在事务中应用明确动作。embedding 只找候选，不给候选授信，也不决定是否合并。

不纯照搬 Hindsight：不让一次模型裁决覆盖或删除原记忆。更新保留旧 revision；无法判断时保存为独立/待处理记录，并留审计结果。也不复制 TencentDB 的特定记录替换实现，先保留本项目的 scope、revision、forget 和 suppressed-source 语义。

## 2. 先分清三个不同问题

不得把以下判断合并成一个“准入分数”：

1. **证据是否有效**：事件是否属于本用户、本轮提取窗口，角色是否为真实用户，quote 是否是原始事件正文中的连续 UTF-8 byte span。这是 Rust 的硬校验。
2. **内容是否值得长期记住**：模型结合用户原话和上下文给出 `durable`、`time_bound`、`uncertain` 或 `not_memory` 建议。判断由版本化模型提示词产生，不再要求命中固定句式/词表。
3. **它与已有记忆是什么关系**：精确重复、补充证据、状态更新、不同方面、冲突或不确定。embedding/词法检索负责召回比较对象，模型提出动作，Rust 验证并落库。

逐字 span 证明“这句话确实出现在用户证据里”，不证明模型对其长期价值或语义关系的判断绝对正确。诊断和用户界面应分别展示证据状态与语义裁决，不能把 embedding 相似度或模型 confidence 当作可信度。

普通记忆的统一评分、意见置信度与重要性分采用何种边界，见 [13](13-记忆评分与重要性方案决策.md)。本节的 confidence 即使作为裁决诊断返回，也不能成为准入或合并阈值。

## 3. 对现有固定准入规则的调整

本方案针对自动提取候选的新版本，不追溯改变旧作业：

- `extract_v3/admit_v1`、`extract_v3/admit_v2` 按现有 job 行版本冻结；重试仍使用原版本。
- 新 Dream 作业固定使用 `dream_extract_v1` 提取 Prompt、`admit_v3` 准入策略与 `adjudicate_v1` 语义裁决协议；三个版本分别保存在作业/结果中。Dream 跨 session 冻结输入的形状与旧 extraction window 不同，因此不借用或改写 `extract_v3`，也不把新 Prompt 冒称为旧版。后续修改任一 Prompt/策略必须单独升对应版本，旧作业按原版本处理。
- 移除“必须匹配某类句式/尾词/类别词表才能 Active”的设计。职业、偏好、家庭事实等不再靠维护中文模板扩展覆盖面。
- 保留确定性硬边界：请求 scope 来自 Bearer token；来源必须是该作业允许的当前用户事件；事件 ID 必须由服务端核对；quote 必须精确定位到原文 byte span；JSON/schema/长度/版本合法；写入必须幂等、可审计、可并发安全。
- 不把 `memory_remember` 的内容护栏重新加回来；本方案只重做自动提取/语义整理路径。凭据或其他安全过滤若将来需要，另列为独立安全决策，不借本方案静默恢复旧门。

语义标签与建议动作也必须属于版本化结构化输出。Rust 校验合法枚举与引用，不要求模型输出的 confidence 达到一个伪精确阈值；confidence 仅诊断，不能单独放行、拒绝或覆盖证据校验。意见专用置信度及重要性评分的使用边界按 [13](13-记忆评分与重要性方案决策.md) 执行。

### 3.1 写入路径与准入严格度如何对接

**写入触发方式决定“谁在什么时候提出写入”；准入策略决定“这条内容能否成为 Active”。两者不能合并成一个开关。** 本系统保留主 Agent 即时写入和 Dream 后台整理两条路径，但它们共享底层证据/安全硬门，语义门则有意不同：

| 检查/决策 | 主 Agent 即时直写 | Dream 后台批量写入 |
|---|---|---|
| 触发含义 | 主 Agent 明确调用记忆写工具，表示它现在要保存这条内容 | compact/定时/custom trigger 只表示“开始整理这批证据”，不代表其中每条都应保存 |
| 共同硬门 | Rust 校验认证 scope、真实用户来源、允许的 evidence ID、连续原文 byte span、schema/长度、幂等键、审计和 forget/suppression/lifecycle 状态；失败即拒绝 | 完全相同；Dream 不能因批处理、embedding 命中或 LLM 判断而绕过 |
| 内容准入依据 | 以主 Agent 的显式写入决定作为语义准入信号；不再额外跑 `admit_v3` 的持久性分类，不要求固定句式/类别词表，也不要求另一轮模型批准 | 必须先有可验证证据，再由版本化 Dream 策略分类持久性并做语义关系裁决；模型建议不是 authority，Rust 按规则映射为 Active、Held/defer 或 not-memory |
| 与现有记忆去重 | 事务内可做精确规范化 hash 幂等：完全相同则复用/关联已有记忆并追加证据；非完全相同的近义或冲突判断不在同步直写中调用 LLM，留给后续 Dream 裁决 | exact hash 后做 embedding/词法候选召回与批量 LLM 裁决；只能按 `adjudicate_v1` 建议和 Rust 复核应用 |
| 不满足语义确定性时 | 不额外进行 Dream 式持久性/冲突分类；但证据硬门失败仍不能写。主 Agent 若无法给出当前接口要求的来源证据，应转 Dream，不能伪造来源 | 模型明确裁决的 `uncertain`、无期限的 `time_bound`、冲突进入 Held/defer；语义服务不可用则作业停在 retryable/provider_wait 且 evidence 不标 processed；不得因为 trigger 已发生就强行 Active |
| 提交结果 | 只有 Rust 成功 receipt 才能称为已写入；直写不等同于绕过 Rust | 只有 Rust 成功 receipt 才能称为已整理/提交 |

因此，“主 Agent 直写较宽”只表示**不再重复施加 Dream 的内容分类门**，不表示信任模型自报的 scope、evidence、quote 或 target，也不表示可以写无来源的推断。Dream 相对更严格，是因为它在无人逐条即时表达保存意图的批处理中，需要额外判断哪些原话值得长期保留、如何与现有记忆协调。

两条路径最后进入同一套 L1、revision、evidence、scope、forget/suppression/lifecycle 与 [14](14-记忆修改审计方案决策.md) 的 `memory_audit` 规则。直写先入库、Dream 后处理同一内容时，Dream 应关联证据或按语义规则更新，不得复制 Active；Dream 先产生 Held/defer、主 Agent 后来明确直写时，直写可独立提交，但仍须通过共同硬门，并在后续 Dream 中做冲突/重复协调。retired、forgotten、purge_pending 或过期对象不能作为 merge target。直写 receipt 和 Dream receipt 必须标明 `write_path`、使用的 policy/version 与最终状态，以便诊断时区分提出路径和裁决结果；这些字段属于 receipt/job result，不写入精简的 `memory_audit` 行。

这条路径差异是产品策略，不是新的用户证据等级：两边引用的原始证据仍按同一强度校验。以后若要让 Dream 也采用主 Agent 的宽松语义门，或让直写也经过持久性/语义裁决，必须作为明确的产品变更另行决定，不能因共用一个存储表而悄悄统一准入。

## 4. 新候选的两阶段流程

### 阶段 A：抽取与证据闸门

1. L0 事件仍先幂等落库，不等待 embedding 或 LLM。
2. 抽取模型给出原子候选，含候选 kind、事件引用、最短连续原文 quote，以及可选的时间/语境标注。候选不得合并多个独立方面。
3. Rust 校验作业版本、scope、事件确属固化的提取窗口、来源角色、byte span 和协议限制。来源或 span 错误直接拒绝该候选并记录 reason；不得让后续模型裁决修复无效证据。
4. 通过证据闸门的候选进入当前 Dream job 的语义判定队列。到此为止只表示“证据可追溯”，还未决定 Active，也未与现有记忆合并。没有 Dream trigger 时，不运行这一步的自动提取与 LLM 裁决。

### 阶段 B：精确去重、语义候选召回、批量裁决

1. **精确快速路径**：对规范化 kind/claim 计算稳定 hash。完全相同的 Active 记忆不再创建副本，只追加新的有效 evidence/revision 关联；幂等键相同且请求内容相同则重放原结果。
2. **混合候选召回**：以新候选文本为 query，在已认证 scope 内并行查词法索引和 embedding 向量，使用 RRF 融合或保留两路排名，取有界 top-K（初始 K=20，配置上限和实现值需在 D6-8 记录）。只召回当前有效且可读的 Active 记忆；forgotten/retired/purge_pending/过期/跨用户记录不能进入比较集。
3. **批量 LLM 裁决**：一批候选共享一次结构化裁决调用。模型只看到这些候选、被召回的目标 claim/kind/时间信息和经许可的来源摘要；不得看到其他 scope 数据。模型输出只能引用请求中给出的 candidate ID 和 target memory ID。
4. **Rust 复核与原子应用**：重新核 scope、job generation、候选证据 span、目标 memory 的 scope/status/version 和输入 fingerprint。任一输入在模型运行中变化则整批标记 `stale_input`，不做部分更新；由新输入重新排队。

向量距离阈值只影响“哪些项进入裁决上下文”。越过阈值不能直接合并，未越过也不能证明二者不同。精确 hash 是幂等优化，也不能替代语义判重。

## 5. 裁决协议

`adjudicate_v1` 的输出是严格 JSON，结构版本化。建议每个 candidate 至少输出：`candidate_id`、`durability`、`action`、`target_memory_id`（仅适用时）、`reason_code`，以及由结构枚举限定的时间状态。建议动作：

| 建议 | 含义 | Rust 应用语义 |
|---|---|---|
| `create` | 有独立、稳定的新记忆 | 通过证据/策略检查后新建 L1；不合并其他 claim |
| `attach_evidence` | 与指定 L1 表达同一 claim | 保留现有 claim，追加新 evidence/revision；不得重复建相同 Active 记录 |
| `update` | 同一方面的状态或值发生变化 | 新建版本/关系并标记旧版 superseded；旧内容和来源可审计、不可被模型物理删除 |
| `keep_separate` | 语义相近但主体、方面或事实不同 | 保留为独立 L1；不能因 embedding 相似而合并 |
| `conflict` | 两条同方面主张不能安全合并 | 两边都保留；新候选进入 Held/冲突状态，等待后续证据或用户处理 |
| `defer` | 模型完成裁决，但语境/持久性不确定或证据不足 | 保留 Held 候选、来源版本与原因；新相关用户证据到来或用户明确要求时，按新输入指纹重裁 |
| `not_memory` | 模型判断该段不是可保存的记忆主张 | 不建立 Active L1；保留最小裁决记录和来源候选，避免静默丢失诊断线索 |

`durability` 建议枚举：`durable`、`time_bound`、`uncertain`、`not_memory`。Rust 按版本化策略映射状态：稳定新记忆可以 Active；有明确有效期限的内容仅在期限可验证时按 time-bound 记录；不确定/冲突保留 Held；`not_memory` 不创建 Active。不能仅凭模型 confidence 激活。

硬性约束：

- 一个 candidate 一次只产生一个主动作；模型不得在一条 L1 中拼接多个不同方面。
- `attach_evidence`/`update`/`conflict` 必须引用本次召回且位于当前 scope 的 target ID；Rust 不接受模型自造 ID。
- 更新必须带 `expected_target_version`，并通过 CAS；相同方面不等于相同事实，冲突不得被改写成确定更新。
- 语义整理不得调用 retire、forget 或 purge，也不能清理 `suppressed_sources`。常规裁决保留来源 evidence 与旧 revision；用户明确确认的独立 purge 按 [12](12-遗忘、过期与时间衰减方案决策.md) 删除依赖闭包，属于该常规保留原则的唯一受控例外。
- 输出缺字段、未知 action、目标越权、跨 scope、超出给定集合、目标版本变化时不猜测降级：拒绝应用并记录确定性错误。

## 6. 向量索引与降级行为

复用 [04](04-召回与上下文.md) 的 embedding provider 和 scope 向量索引；“查询记忆”和“判断候选重复”是两个调用场景，但可共享同一套向量、模型版本和限额。新候选向量可以作为临时 query vector，不要求在成为 L1 前持久保存。

- 只比较相同 `model_id + dimensions` 的向量；candidate 文本与已有 memory 向量的规范化方式必须版本化并记录。
- 语义候选列表同时保留词法命中，供模型看到关键词重合之外的近邻；无 embedding 时可使用精确 hash + 词法候选并标记 `semantic_status=disabled/unavailable`。
- 语义服务超时、429、维度错误或索引暂不可用时，不得声称完成了语义去重，也不得把基础设施失败记为模型裁决的 `defer`。冻结作业先有限重试，仍不可用则进入 `provider_wait`，保留输入和证据分配；端点恢复后自动续作原输入。**首版不允许仅凭 exact/词法结果把此类候选创建为 Active**，避免降级时把“没搜到相似项”解释成“肯定是新记忆”。明确配置为永久无 embedding 的部署只能运行主 Agent 直写、L0 捕获与旧版本兼容作业；新 Dream 语义自动应用保持待处理并报告 `semantic_status=disabled`。
- source version/hash/status/lifecycle 变化时向量立即 stale；forget/retire/purge_pending/过期/跨 scope 过滤必须先于候选排序。缓存 embedding 不代表对象仍有效。
- 新建或更新 L1 后异步刷新向量。索引失败不得回滚已审计的证据；在语义索引修复前该对象应显式不可参与语义去重/召回。

## 7. 持久化、审计与失败恢复

模型调用在 SQLite 事务之外。Dream 输入 job 见 [10](10-写入触发与Dream执行模型.md)；建议在 `0009_semantic_adjudication.sql` 增加独立 adjudication job/result 记录，不回改 `0001`—`0008`。至少可还原：candidate IDs、冻结的 source event/span 摘要、召回的 target memory IDs 与 versions、prompt/admission/embedding/model 版本、输入 fingerprint、action/durability/reason、job generation、重试状态及最终应用结果。不要持久化完整 prompt、密钥或无必要的私密对话正文。

同一 `adjudication_job` 需有幂等 fingerprint；claim/lease/过期恢复/attempts/退避/确定性 dead 沿用 doc4 作业原则。主事务应用候选结果、memory/evidence/relations 与相关页面/向量失效；提交成功后按 [14](14-记忆修改审计方案决策.md) best-effort 追加 L1 `memory_audit`。审计失败告警但不回滚；adjudication/job result 仍必须准确表示业务提交结果，不能把审计失败伪报成记忆更新失败。

成功的 `defer/conflict` 是候选级 Held 结果，原 evidence 可标 `processed`；按 [10 §5](10-写入触发与Dream执行模型.md) 的新证据/新指纹条件重新裁决。暂时性 provider 故障是作业级 `provider_wait`，原 evidence 保持 `assigned`，恢复时重试同一冻结输入。同一指纹不得反复调用模型；自动重裁不调用 retire、forget 或 purge。

自动重裁的相关性入口限同 scope：新 Dream 批次的候选与旧 Held 候选规范化 kind/claim hash 完全相同，或由可用 embedding/词法候选召回把旧 Held 纳入有界 top-K，才可把旧 Held ID 与新 evidence 一起冻结进新裁决作业；没有这类新证据时，24 小时定时 tick 不反复重判旧 Held。旧 Held 原文和已处理 L0 水位不改，裁决历史逐版可查。用户显式重裁可以绕过“必须有新证据”，但同一输入指纹仍返回既有结果，不能靠重复点击制造无限模型调用。

每个结果能回答：

1. 模型看到了哪些候选和哪些相似记忆？
2. embedding / prompt / policy 的版本是什么？
3. 它建议了什么，Rust 最终应用了什么，若不同原因是什么？
4. 新旧 memory 与原始 evidence 如何关联？

模型超时/429/5xx 可重试；无效引用、未知版本、坏 JSON、scope 违规属于确定性失败，不重复调用同一坏输出。裁决未完成期间候选保留，不删除原始事件，也不对外谎报已经形成 Active 记忆。

## 8. 与主题页、Resident 和 Soul 的边界

语义合并发生在 L1 原子记忆之间，解决重复证据、同一方面更新、冲突和不同 claim 的区分。它不等于 [05](05-后台整理.md) 的问题画像或主题页：派生知识文档围绕登记问题或主题整理 L1，永远不覆盖原子记录。

`memory.md` 仍是 resident 当前状态的视图；L1 merge/update 后按新版本重算。Soul 仍由用户编辑，语义裁决、主题整理和候选提取都无权改写 soul、自动 pin 或改变用户设置。所有 Agent 在同一用户 scope 下共享有效 L1；Agent 身份只隔离 Soul。

## 9. 验收标准

不能只证明 embedding API 返回了向量或 LLM 返回了 JSON。至少建立有来源 ID 的 pairwise 语义裁决集，包含同义复述、近义但不同方面、主体不同、状态更新、相互矛盾、临时/假设句、无相关旧项、跨用户相似项。

逐项断言：

- 事实类自然平叙能通过证据闸门，不依赖“我喜欢/以后回答/我是……”固定句型。
- 完全重复不产生重复 Active L1，并保留新增 evidence 关联。
- 语义相同的复述能追加证据或更新；近似但不同的 claim 不误合并。
- 状态更新保留前版；冲突两边都留存，不把旧记忆静默覆盖。
- 暂时/不确定/非记忆判断不会被伪装成 Active；候选与判断可追踪、不会静默丢失。
- 目标引用越权、旧版本竞争、输入在模型运行中变化时均拒绝提交或 stale，不出现部分落库。
- embedding disabled/timeout、模型 timeout/坏 JSON、worker 重启都能按诊断语义恢复；不报告虚假的“语义去重成功”。
- 变更对现有已冻结作业版本、remember 直写、forget 防复活和跨用户隔离无回归。

核心指标包括：candidate evidence validity、durable recall、false merge、false split、duplicate rate、held/defer rate、decision coverage、source traceability、cross-scope leakage、latency/cost。优先关注 **false merge 与 source loss**；不能以单纯减少记忆条数作为优化目标。

## 10. 明确不在本设计内

- 自动重写 Soul/persona 或把模型生成内容提升为人格指令。
- 仅用 cosine threshold 自动 merge、自动 forget、物理删除旧 memory。
- 修改 `admit_v1/v2` 的历史语义或重写 `memory_remember` 直写护栏。
- 把问题画像/主题页摘要当作原始用户原话，或把派生文档合并和 L1 claim 合并共用同一个状态机。
- 未经用户决定扩大到跨用户、跨租户的公共向量索引或记忆共享。

## 11. 实施顺序建议

1. 先锁 D6-0 的源码/迁移/DSH 基线，确认当前候选落库、revision、冲突关系和 doc5 版本分派的真实接口。
2. 完成基础数据与派生知识文档能力（D6-1—D6-6），保证 L1 状态、Resident、画像/主题页失效正确。
3. 实施 D6-7：持久 trigger、输入快照和 Dream 子 Agent dispatch；未证明宿主能力前不假设 compact emitter/background dispatch 已存在。
4. 实施 D6-8：先向量索引与查询降级，再新增 `admit_v3/adjudicate_v1` 和 `0009` 持久化；旧规则按 job 版本继续执行。
5. 用 pairwise 固定集证明裁决协议和原子事务；真实端点只验证经用户配置的单一端点，不把小样本升级成质量结论。
6. D6-10 按验收矩阵记录 Dream trigger、false merge、false split 与来源链；未达到用户可接受阈值时可关闭语义自动应用，保留 L0、候选与审计能力。

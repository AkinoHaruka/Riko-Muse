### B5. 检索与注入：指令/非指令路径、零词法命中、预算、排序、证据展示

| 仓库 | 源码事实 |
|---|---|
| TencentDB | 画像层与查询无关地始终注入：L3 persona 全文 `session_init` 直注 system（`MemoryProxy/src/injection/injectors/tdai-profile-memory-injector.ts:32,105-108`，截断 6000 字符），L2 只注 path+summary 索引（:109-121）；**L1 自动注入已下线**（`injection/index.ts:347-349`），改教模型主动调 search 工具；L1 检索 = FTS BM25 ∥ 向量 cosine + RRF(k=60)（`core/store/search-utils.ts:38-62`），零词法靠向量，**无 recency 兜底**；无 score 阈值过滤。 |
| EverOS | keyword = LanceDB FTS/BM25（jieba 预分词列，`infra/persistence/backends/lancedb.py:166-203`），零词法命中**无任何 fallback**（`memory/search/recall/episode.py:59-61`）；向量路需 embedding；画像 `ProfileRecaller.fetch` 是**无查询相关的按 owner 直取**（`recall/profile.py:32-60`）；注入完全由调用方负责，本仓无注入代码。 |
| Hindsight | **directives 机制**：用户定义硬规则 "always included in relevant prompts"，不参与检索（`engine/directives/models.py:9-32`），reflect 时注入 prompt 顶部；另有 mental models 后台定时刷新后注入。多路检索 semantic(pgvector)+BM25+graph+temporal RRF 融合（`engine/search/fusion.py:29-109`）；零词法靠 embedding 语义（默认**本地 in-process SentenceTransformers**，`config.py:1206`）；rerank 有界乘性调整 recency 0.2/temporal 0.2/proof 0.1（`reranking.py:16-37`）；consolidation 场景有 `interleave_fusion` 保证纯语义 #1 必入池（fusion.py:112-130）；结果带 `source_facts` 溯源 map（`engine/source_facts.py:1-70`）。 |
| 本项目【代码】 | search = FTS5 ∥ `memory_grams` 中文二元字 + RRF(60)（`memories.rs:383-422`、`memory-recall/src/lib.rs:9-14`）；compose 指令名额独立于查询：命中指令先占 2 名额，不足按 `updated_at DESC` 补齐（`memories.rs:851-870`）；**非指令记忆只来自词法 hits**（memories.rs:872-876），recency 兜底查询硬编码 `kind='instruction'`（memories.rs:921-922），全仓无 embedding 代码；预算 5 条/2000 字符、超长整条跳过；`evidence_refs` 返回 evidence_id 列表。 |

**差异**：三个上游殊途同归地都有“**查询无关的常驻层**”（TencentDB 画像全文、EverOS 画像直取、Hindsight directives/mental models），而查询相关记忆在零词法命中时全部依赖 embedding——**没有上游提供“词法检索 + 无 embedding 的非指令兜底”**。本项目的指令名额正是 directives 模式的轻量等价物；preference/fact 没有对应层，即观察问题三的根源。Hindsight 的 interleave_fusion 是纯工程点子，但它解决的是 consolidation 召回，不是注入。

| 仓库 | 源码事实 |

### B7. 异步作业：Prompt 版本、超时、重试、dead、恢复

| 仓库 | 源码事实 |
|---|---|
| TencentDB | 队列 = Redis Stream 消费组，但实现是**私有子模块 `src/integrations/redis/`，仓库内不存在**（`core/state/index.ts:54-64` 自认）；锁 TTL 600s 续约 30s、续约失败 abort；重试 3 次、5/15/45s 指数退避（`services/pipeline-worker.ts:686-698`）——本项目的退避序列出处即此；**死信回调未接线**：`onDeadLetter` 在 server.ts 无注入点，service 模式死信仅存进程内 + 日志（pipeline-worker.ts:1158-1196），dead 后无自动恢复；Prompt 版本走 `MemoryGenerationLog`（含 prompt_id/version/sha256、input/output refs，`core/memory-generation-log/types.ts:48-49`）——溯源比本项目更细；LLM 超时 180s。 |

| Hindsight | Postgres `async_operations` 表作 broker，FOR UPDATE SKIP LOCKED 领取（`worker/poller.py:529`）；重试 3 次、带 cancelled 防复活守卫（:1011-1035）；**无独立死信**——终态 failed，靠 `consolidation_failed_at` 让失败事实可被例行任务重新排队（`memory_engine.py:11692-11734`）；prompt 是代码常量（版本=git），但 `llm_requests` 表持久化每次调用的完整输入输出与 usage；每任务 wall-clock 上限。 |
| 本项目【代码】 | 单 worker 500ms 轮询，只领同 session 更早窗口全部 succeeded 的最小待办窗口（`jobs.rs:179-211`，blocked 判定含 dead）；下界由持久表计算（jobs.rs:124-143）；lease 90s、3 次、5/15/45s；dead 后仅 `POST /v1/jobs/{id}/retry` 手动恢复且**需要完整 job id**（main.rs:752-763）；`prompt_version` 列 + v1/v2 分派 + 未知版本显式失败（`memory-extract/src/lib.rs:37-43`、worker.rs:721-731、`migrations/0002_prompt_version.sql`）；usage 成功路径持久化（jobs.rs:250-265）。 |

**差异**：本项目是唯一把 prompt 版本直接绑到作业行的（TencentDB 绑到生成日志、EverOS 无、Hindsight 靠 git + llm_requests）；dead 恢复能力上三上游半斤八两（TencentDB 回调没接线、EverOS 自动重排队、Hindsight 例行重排队），本项目的“手动 + 完整 id”是明确契约而非缺陷，但 dead 作业**不可发现**（无列表端点）是运维痛点。

## D. 优化建议（P0/P1/P2）

**P0-1：给 held 候选建“可见 + 显式放行”通道（先决条件）**
- 收益：C-1 的闸门 2 决策目前无法落地——held 候选躺在 `memory_candidates` 里无任何端点可读、可 promote；有了它，“哪些被挡住”才可审计，放行决策才有据。
- 做法：管理端点（如 `GET /v1/candidates?status=held`、`POST /v1/candidates/{id}/promote`，promote 记 `manual_edit`/审计），或先做 `memoryd` CLI 子命令避免动 HTTP 契约。
- 副作用：promote 绕过自动准入，必须带逐字证据校验（quote 复核）+ 审计 + scope 限定；不注册进 DSH Agent 工具。
- 涉及：`crates/memory-server/src/main.rs`（路由）、`crates/memory-store-sqlite/src/`（候选查询/状态迁移）、doc/12 协议小版本。
- 最小验收：造一条 held 候选 → 列表可见 → promote 后 searchable，audit_events 有记录；跨 scope ID 404。

**P0-2：extract_v3 提示词——多事实拆分示例 + 拆分指令（新版本，不动 v1/v2）**
- 收益：直接对 C-2。在现有 Schema 约束下加一条指令与一个双事实 few-shot：“一条消息含多个独立事实时，为每个事实输出一条候选，每条 quote 取该事实的最小连续原文，不要共用整句”。
- 副作用：小模型可能过度拆分或拆出非连续 quote——被 QUOTE_MISMATCH 闸门兜住（失败即 rejected，不污染 active）；泛化性需 n≥3 观察再下结论（沿用“示例句之外”的验证纪律）。
- 涉及：`crates/memory-extract/src/lib.rs`（新常量 + 分派分支）、`crates/memory-contract/src/lib.rs`（版本串）、迁移只加行不加列（0003 亦可复用 prompt_version 机制，无需新列）。
- 最小验收：单测 v3 分派；真实模型会话含双事实消息 → 两条独立逐字候选。

**P0-3：闸门 2 的产品决策落法（需用户拍板，见 F-1）**——两个可选方向：① fact 类扩“稳定自我陈述”模式表（把“我在X做/上学”类最小集补进 explicit 规则，仍逐字+有证据）；② 不扩自动放行，全走 P0-1 的人工通道。不建议为命中率整体放宽。

**P1-a：dead 窗口的可发现性与不阻塞**
- 收益：消 C-4 运维风险。最小改法：① `GET /v1/jobs?status=dead`（或 CLI 列表）解决“不可发现”；② StateConflict 类**确定性错误**不进重试直接 dead（省 3 次无意义调用）；③ 超限 dead 窗口不再阻塞后续窗口（或显式 skip 语义 + 审计）。
- 副作用：跳过语义改变“worker 只领最小未完成窗口”不变量（doc/13 §3、doc/11 §3.7），需升契约说明。
- 涉及：`jobs.rs`（claim 判定、fail_job）、`main.rs`、doc/13。

**P1-b：preference/fact 的 compose 名额兜底（仿指令名额，无新基础设施）**
- 收益：对 C-3 的同构解。三上游的常驻层思想 + 我们已有的指令名额模式：给 active preference 留 1-2 个 `updated_at DESC` 名额（fact 类量大且杂，建议先只做 preference，或按“最近 N 条 active”严格限量）。
- 副作用：无关偏好可能挤占查询相关记忆的名额（预算不变、总量受控）；与【观察】F3 的归因混淆问题仍在——需可区分探针再验证效果。
- 涉及：`memories.rs` compose_context、回归测试、doc/13 §6 契约更新。
- 最小验收：零词法命中问句 → compose 含最新 preference；名额上限断言。

**P1-c：小契约对齐**
- `MODEL_PARAPHRASE`：schema 改为接受可选 claim 字段并按 doc/13 §5.4 降级 held（或反向改 doc/13 承认“多字段即整批失败”）；`今天先` 补进词表。涉及 `memory-extract/src/lib.rs`、`memory-store-sqlite/src/jobs.rs`。验收：自填 claim 的响应产出 held:MODEL_PARAPHRASE 且同批其他候选保留。

**P1-d：80 事件 flush 兜底（doc 与代码对齐方向二选一）**：补适配器实现（累计阈值排 flush）或修订 doc/13 §3 承认 turn/end-only 并在服务端加窗口超限前置校验（flush 时就拒，而非 claim 时炸）。

**P2（明确保持现状/后置）**：embedding 语义检索——三上游零词法召回全部依赖它，但引入向量索引 + embedding 调用违背 doc/01 §6 “检索不调模型”的成本契约与“首版不强制 embedding”边界；等 P1-b 名额兜底的真实效果数据出来再评估。Hindsight 式 consolidation、TencentDB 式 L2/L3 摘要层均后置（doc/02 已有决定，本次审计未发现推翻理由）。

## E. 不建议照搬的上游机制

1. **TencentDB 的 LLM 裁决去重/合并（batchDedup）与改写式记忆**：模型判定 store/merge 且失败默认全存（l1-dedup.ts:85-90）、无逐字引用——与本项目的“Rust 唯一裁决 + 逐字证据链”根本冲突，且其“宁重复不丢”的 L0 写入和无幂等重放正是我们已避免的。
2. **TencentDB 的 Redis Stream 消费组 + 分布式锁**：实现体是仓库外的私有子模块（无法核对），依赖 Redis，死信回调还没接线；当前单 worker 规模下我们的 SQLite 队列 + dead + 手动 retry 足够。
3. **EverOS 的 Markdown 真相 + LanceDB 重建**：其 atomic fact 重建复活缝（C-8）恰好是被我们 suppressed_sources 挡住的失败模式；SQLite 事务化是我们的正确选择（doc/02 已决定）。
4. **Hindsight 的 consolidation UPDATE 重写 observation**：有损改写旧记忆；若远期引入必须连同其 `observation_history` 快照与三重防复活机制一起搬，成本高，首版后置（doc/02 已决定）。
5. **Hindsight 的本地 SentenceTransformers in-process embedding**：Rust 侧无对等维护中的方案，且破坏“检索不调模型”成本目标；其 semantic/temporal/graph 多路在我们的单路词法下无意义（doc/13 §6 已明确单路不套 RRF）。
6. **EverOS/Hindsight 的边界检测（boundary LLM 切分）**：多一次 LLM 调用且 EverOS 自身有异常丢缓冲窗口；我们的 flush-through-seq 窗口更简单且已实证闭环。
7. **TencentDB 的团队 ACL / 固定资产借用**：与“同一用户默认共享”目标方向相反，且其复杂度（owner/visibility/ACL 三层）远超单机首版需要。

## 1. 勘误 C-4：超限窗口不是“重试耗尽 → dead”，而是“直接离开，作业留在 running”

原文（总报告 §106 行）：「`load_window_events` 抛 StateConflict → 重试耗尽 → dead」。

**修正**：`memory-server/src/worker.rs` 的 `process_job` 在加载窗口处直接用 `?` 返回（worker.rs:732-739，`window_lower_bound` 与 `load_window_events` 的错误经 `.map_err(...)?` 离开函数），而窗口超限在 `memory-store-sqlite/src/jobs.rs:239-246`（>100 事件或 >32 KiB → `StoreError::StateConflict`）就触发。该路径**不调用 `fail_job`**：作业保持 `status='running'`、带 90 秒 `lease_until`；由于领取 SQL 只选 `queued/retryable_failed`（jobs.rs:153-154）且全项目无任何过期 running 恢复写入（见第 5 条），该行**永久停在 running**，既不重试也不 dead。C-4 描述的「该会话所有后续窗口被永久阻塞」的后果仍然成立，但机制是 running 挂起而非 dead 阻塞；「重试耗尽」与「dead 作业复死」的表述对本路径不适用。

## 2. 新增勘误：retryable_failed 的退避可被绕过

`jobs.rs::claim_due_job`（jobs.rs:146-176）的领取条件：`queued` 检查 `run_after<=now`，但 `retryable_failed` 只检查 `lease_until IS NULL OR lease_until<=?1`，**不检查 `run_after`**。而 `fail_job` 写 `retryable_failed` 时同时 `lease_until=NULL`（jobs.rs:284-288），因此 5/15/45 秒退避（写入 `run_after`，jobs.rs:278-283）从不生效——失败的作业在下一轮 500ms 轮询即可被重新领取。doc/13 §3 的退避语义在当前代码中形同虚设。静态判断。

## 3. 新增勘误：跨会话饥饿

`jobs.rs::claim_next_ordered_job`（jobs.rs:179-211）先取全局最早 due 行（`ORDER BY created_at LIMIT 1`，jobs.rs:155），发现其 session 存在更早 `dead/running` 时把该行还原 `queued` 并返回 `None`（jobs.rs:202-209）。由于还原不改变 `created_at`，同一行在下一轮仍是全局最早，会被再次取出、再次还原——**只要这一行不停留在队列首位，其他 session 的到期作业一轮都领不到**。单 worker 循环（worker.rs:686-709）下表现为全体停摆而非仅一个 session 停摆。静态判断。

## 4. 新增勘误：window_lower_bound 用 window_key 字典序比较

`jobs.rs::window_lower_bound`（jobs.rs:124-143）用 `window_key < ?5`（字符串比较）寻找前一成功窗口。`window_key` 形如 `v1:<through_seq>`，字典序不等于数值序：`"v1:100" < "v1:99"`（第 3 字符 `'1' < '9'`）。多窗口场景：当前窗口 `v1:100` 计算下界时，`window_key < 'v1:100'` **匹配不到**已 succeeded 的 `v1:99`，下界回退到更早窗口（如 `v1:9`），窗口 `(9,100]` 会把 seq 10–99 的已提取事件**重复**送入模型输入。静态判断；单窗口（through ≤ 99）时不触发。

## 5. 新增勘误：过期 running 无任何恢复路径

领取 SQL 只选 `queued/retryable_failed`（jobs.rs:153-154）；全库对 `running` 行的写入只有：claim 置 running（jobs.rs:167-171）、有序领取还原 queued（jobs.rs:204-207）、complete（jobs.rs:259-264）、fail（jobs.rs:272-288）。不存在任何「`lease_until` 已过期（或 NULL）的 `running` 行」被恢复为可重试状态的代码路径。后果：进程在 claim 之后、fail/complete 之前崩溃（或第 1 条的超限路径），该作业永久 `running`，其 session 的所有后窗随之阻塞（与 `claim_next_ordered_job` 的 running 阻塞判定叠加，jobs.rs:190）。静态判断。

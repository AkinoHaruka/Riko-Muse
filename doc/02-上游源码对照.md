## 2. EverOS

**已核对：**

- `EverOS/docs/how-memory-works.md` 把 Markdown 定为记忆内容真相；SQLite 保存状态、队列和缓冲，LanceDB 是可重建的检索索引。文档说明 `/add` 先缓冲，边界检测或 `/flush` 触发 MemCell 与情节写入，其他记忆由 OME 异步派生。
- `EverOS/src/everos/service/memorize.py` 连接 ingest、boundary、用户和 Agent 两条 Pipeline，并注册 atomic facts、foresight、profile 等策略。
- `EverOS/src/everos/memory/search/dto.py` 要求 `user_id XOR agent_id`，并把 `app_id/project_id` 固定到查询范围；这和本项目“同一用户的不同 Agent 默认共享”的目标不同。
- `EverOS/src/everos/service/search.py` 表明 keyword 检索可以在没有 embedding、rerank、LLM 客户端时工作。
- `EverOS/docs/storage_layout.md` 描述日记式 episode、索引重建和 Reflection 后的 `deprecated_by` 软归档。

**本项目采用：**先持久化原始证据、后异步派生记忆；索引可重建；显式 flush；关键词检索不依赖外部模型。**调整：**首版以事务化 SQLite 作为规范数据存储，Markdown 导出留在后续，因为用户级跨 Agent 共享、幂等、纠错和状态转换需要原子写；这不是 EverOS 的 Markdown 真相原样复刻。

## 3. Hindsight

**已核对：**

- `hindsight/hindsight-api-slim/hindsight_api/engine/retain/fact_extraction.py` 定义事实抽取结构、发生时间，并要求在相关模式中保留 feelings、preferences、motivations 等信息。
- `.../engine/consolidation/consolidator.py` 对 observation 更新使用来源记忆 ID、去重的 `proof_count`，并要求一个巩固输出的相关写入一起提交或回滚。
- `.../engine/consolidation/prompts.py` 限制无证据推断与数值推算；模型看到当前 observation 与来源后提出巩固方案。
- `.../engine/search/fusion.py` 以 `1/(60 + rank)` 实现 RRF，并支持 semantic、BM25、graph、temporal 检索结果融合。
- `.../engine/search/reranking.py` 对 recency、temporal proximity 和 proof count 施加有界乘性调整；支持 linear、exponential、none 时间衰减。
- Hindsight 使用 bank 隔离；本项目将一个用户 scope 视为一个独立记忆池，但不会把不同用户放入同一可检索池。

**本项目采用：**记忆与来源证据的稳定关联、发生时间和写入时间分离、可审计的巩固结果、查询结果标注来源。RRF 的 `k=60` 在真正有至少两路独立检索时使用。**暂缓：**向量、图扩散、cross-encoder、复杂 reflect agent 循环；单路关键词结果没有必要套 RRF。

## 4. TencentDB Agent Memory

**已核对：**

- `tencentdb-agent-memory/MemoryCore/src/core/conversation/l0-recorder.ts` 是 L0 对话记录入口。
- `.../core/prompts/l1-extraction.ts` 在 chat 模式提取 persona、episodic、instruction，要求输出 `source_message_ids`；同时明确排除纯主观感受。它的 code 模式是工作记忆，不能直接用于所有通用 Agent。
- `.../core/prompts/scene-extraction.ts` 使用已有场景映射，采用更新、合并、新建的文件维护策略。
- `.../core/prompts/persona-generation.ts` 对用户画像进行基础锚点、兴趣、交互协议、认知内核四层扫描；这适合后续摘要层，不适合作首版的原子事实权威。
- `.../services/pipeline-worker.ts` 使用消费组、锁、重试、死信队列和 L1→L2→L3 级联。
- `MemoryProxy/src/injection/pipeline.ts` 提供注入点和缓存策略；`.../injectors/tdai-profile-memory-injector.ts` 注入 L3 全文和 L2 导航索引，L0/L1 由工具主动查。
- `MemoryCore/src/metadata/service/permission-checker.ts` 以用户／owner、成员、visibility、ACL 作访问判定。首版只有用户级隔离，不复制团队 ACL。

**本项目采用：**L0 先存、L1 后提取、后台任务有重试和死信、摘要与具体记忆区分、稳定摘要注入加按需搜索。**暂缓：**L2/L3 级联、Proxy 转发和团队资产管理。第一版 DSH 原生适配器直接使用宿主事件与 Hook。

## 5. 不能直接拼接的差异

| 题目 | 上游差异 | 本项目决定 |
|---|---|---|
| 权威存储 | EverOS Markdown；Hindsight Postgres；TencentDB 多类存储 | SQLite 事务库是首版规范存储；导出与索引是派生物 |
| 记忆归属 | EverOS 用户／Agent 二选一；Hindsight bank；TencentDB 团队和 Agent 资产 | `(tenant_id,user_id)` 归属，Agent 是来源和消费者 |
| 自动注入 | EverOS 核心检索由调用方集成；Hindsight 提供 recall；TencentDB Proxy 注入 L3/L2 | DSH 适配器注入有限的高相关记忆，工具按需查详情 |
| 提取内容 | TencentDB chat 排除纯感受；Hindsight 的抽取提示保留感受 | 通用首版保存原始表达；只把可复用、可定位的陈述升为记忆 |
| 巩固 | EverOS 有损合并且旧条目软归档；Hindsight observation 带来源更新；TencentDB L1→L3 摘要 | 首版只做去重和明确纠错；复杂巩固后置，原始证据不因摘要改写而消失 |
| 检索依赖 | EverOS keyword 可独立工作；Hindsight 多路检索较重 | 首版关键词＋时间／状态过滤；多路检索进入后续里程碑 |

## 6. 来源使用方法

开发一个功能前，先打开该条所列源码，记录实际输入、输出、失败路径和版本。把“上游实现”“本项目决策”“尚未交付”分开写在 PR 或变更说明中。不要把上游设计转述为已经验证的本项目性能，也不要为了接近上游的功能清单而牺牲第一版 DSH 闭环。

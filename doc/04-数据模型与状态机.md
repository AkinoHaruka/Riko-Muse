# 04 数据模型、证据与状态机

本文件解释数据语义。可直接落地的首版建表以 [11-数据库v1迁移](11-数据库v1迁移.md) 为准。所有时间存 UTC，展示时由宿主转本地时区。

## 1. 标识与作用域

内部对象 ID 固定为 UUID v7 字符串；`session_id`、`agent_id` 保留宿主原值并带来源 `host_id`，以免不同宿主 ID 碰撞。`tenant_id` 和 `user_id` 由 Rust 服务验证当前用户令牌后确定，不能被模型输出、工具参数或普通对话覆写。

固定的 `ScopeKey`：

```rust
struct ScopeKey { tenant_id: TenantId, user_id: UserId }
struct Origin { host_id: HostId, agent_id: AgentId, session_id: SessionId }
struct EvidenceRef { evidence_id: EvidenceId, start_byte: Option<u32>, end_byte: Option<u32> }
```

`start_byte/end_byte` 指向存储的 UTF-8 原文，若模型给出偏移，必须重新验证边界和片段内容；没有可靠跨度时保留整条消息引用，不能伪造字符位置。

## 2. 规范表语义

| 表 | 主键与关键列 | 用途／约束 |
|---|---|---|
| `principals` | `(tenant_id,user_id)`；created_at | 用户作用域登记。用户 ID 不从昵称推断 |
| `agents` | `(tenant_id,user_id,host_id,agent_id)` | 来源与消费记录；Agent 不拥有用户记忆 |
| `evidence_events` | `id`；`tenant_id,user_id,host_id,session_id,event_seq` 唯一 | 不可变 L0 事件。含 role、source_kind、occurred_at、received_at、content、content_hash |
| `extraction_jobs` | `id`；`scope,session_id,window_key` 唯一 | 批量提取、lease、重试、用量与错误类别 |
| `memory_candidates` | `id`；scope、kind、claim、source_class、confidence、status=`candidate/held/rejected` | 模型或手工提出的 L1 内容；尚不等于可注入记忆 |
| `candidate_evidence` | `(candidate_id,evidence_id,start_byte,end_byte)` | 候选来源，多对多 |
| `memories` | `id`；scope、kind、claim、status=`active/superseded/expired/forgotten`、version、valid_from、valid_until | 已通过准入的当前或历史记忆；`version` 用于乐观锁 |
| `memory_evidence` | `(memory_id,evidence_id,start_byte,end_byte)` | 每条可用记忆至少一条可验证来源，手工编辑以审计事件为来源 |
| `memory_revisions` | `(memory_id,version)` | 修订前后、操作人、原因与时间；支持审计和冲突解释 |
| `memory_relations` | `(from_id,to_id,kind)` | `supersedes`、`contradicts`、`derived_from`；每端 scope 必须相同 |
| `context_snapshots` | `id`；scope、source_versions、content、created_at | 后续摘要层；不在 v1 迁移中建立，不作为真相 |
| `audit_events` | `id`；scope、actor、action、target、timestamp | 读写、审批、纠错、遗忘、重建的操作痕迹 |
| `index_state` | scope、index_version、last_rebuilt_at | 派生索引恢复点 |

首版迁移不得自行合并 [11](11-数据库v1迁移.md) 的规范表。跨表外键包含 scope，读写也必须用已认证 scope 过滤；仅在内存中验证不够，因为重试和管理接口可能绕过原调用路径。

## 3. 记忆种类

首版四类：`fact`（用户／环境稳定事实）、`preference`（长期偏好）、`instruction`（对 Agent 的持续规则）、`episode`（有时间语境的事件）。种类来自 TencentDB chat L1 与 Hindsight world/experience 的交集，名称为本项目契约。`observation`（跨证据综合）和 `profile`（长篇画像）预留独立类型，不能把它们伪装成 `fact` 自动注入。Agent 自己执行的操作可保留在 L0，只有可复用且正确归因时才提取为事件，不能写成用户亲历事实。

## 4. 状态转换

```text
候选 candidate ──可验证直接陈述──→ active
       │                                  │
       ├──证据不足／冲突────────────→ held │
       └──明确拒绝──────────────────→ rejected
                                          ├──用户纠错→ superseded → 新 active 修订
                                          ├──有效期届满→ expired
                                          └──用户遗忘→ forgotten
```

- `candidate`：有提取结果和来源引用，但尚未通过资格检查。不可自动注入。
- `held`：来源不清、推断性过强、与 active 冲突或内容敏感。仍保存在候选表，仅管理界面可见，不参与普通召回。
- `active`：可被检索和注入。至少一个仍存在、同 scope 的证据锚点；状态提交与索引更新使用同一数据库事务或明确的待重建标记。
- `rejected`：明确拒绝的候选。保留有限审计，不再自动重试同一候选。
- `superseded`：被用户纠正或新版本取代，默认检索排除；历史查询可显式读取。
- `expired`：有效期过后默认排除；时间查询可以查看历史。
- `forgotten`：普通读取立即不可见；删除方式见第 8 节。

状态由内核规则和用户明确操作变更，模型只能提交候选及其建议。可用状态不等于“绝对真实”。

## 5. 自动变为 active 的窄规则

为缩短首版路径，允许**用户明确直接陈述**的非敏感、持续有用的信息自动通过：候选的原文引用必须指向同一用户的 `user/message`；候选语义不得超出原文；有明确主体、可独立理解；不是一次性操作、玩笑、假设、引语中的他人自述或助手转述。机械检查包括来源角色、引用存在、作用域、长度、去重和敏感词类别；“候选语义不得超出原文”的判断无法完全靠规则保证，因此首版采取保守范围：优先使用原文或仅做明显格式清理。需要推理才能得到的内容进入 `held`。这与 Hindsight 的来源关联、TencentDB 的 L1 `source_message_ids` 一致；严格的自动通过边界是本项目为首版作出的选择。

如果无法可靠判断，宁可没有自动记忆。用户通过 `memory_remember` 明确指定内容时，仍需记录该次用户消息为证据。敏感项默认 `held`，是否开放“用户显式确认后注入”留给后续决策。

## 6. 去重、冲突与时间

- 完全相同的 `(scope, kind, normalized_claim)` 不重复建 active；新增来源写入 `memory_evidence`，修订版本增加。
- 近似重复、指向同一属性但值不同的候选先标记 `held` 与 `contradicts`，不能因为时间较新就静默覆盖。明确的用户纠错操作可以在同一事务里 supersede 旧值并激活新值。
- 区分 `occurred_at/valid_from/valid_until`（事实涉及的时间）与 `received_at`（系统记录时间）。未知发生时间保持 NULL，不能凭会话时间改写为事实发生时间。
- 用户直接撤回或声明过期时，读路径先排除旧记忆，索引随后在同一事务更新或由查询层状态过滤保证排除。

Hindsight 的 recency decay 是排序信号，不是自动判定新事实正确的证据；首版可用时间排序，但不以衰减分数触发状态转换。

## 7. 摘要与来源链

稳定摘要如果实施，保存 `source_memory_ids` 和各自版本。任一来源被纠错、遗忘或过期，摘要立即被标记失效，下一次由 active 记忆重建。摘要文本不能反向更新原子记忆。引用链由 `evidence_events → memory_evidence → memories → context_snapshots` 构成；普通召回结果至少能回到 `memory_id` 和一个证据 ID。

## 8. 遗忘语义

首版提供两种明确操作：

1. `forget_memory(id)`：从所有普通检索和注入中立即排除这条记忆，删除／失效其派生索引和摘要引用；原始会话事件按宿主的会话保留策略存在。返回值明确告知“记忆已遗忘，原始会话仍可能保留”。
2. `delete_evidence(scope,session/event)`：删除原始证据及引用它的派生内容，属于单独的高权限数据清除操作；首版不暴露给 Agent 工具，由管理接口在实现时制定完整事务和备份语义。

忘记后应保存最小的 suppression 指纹或显式规则，防止尚在 L0 的同一条旧证据在后台重提取时复活；指纹不能包含明文敏感内容。若用户要求彻底清除，suppression 也须随证据删除策略处理。以上是本项目决策，不应被描述为三个上游仓库共享的现成语义。

# 08 开放事项、风险与文档变更规则

## 1. 当前已决定的事项

用户已决定 Rust 优先、通用 Agent 内核、DSH 首接入、同用户跨 Agent 默认共享、不同用户隔离、首版不迁移旧数据、不设耗时 API 测试阶段。这些不是待确认问题。实施者不能以“还需用户确认”为由停在这些问题上。

## 2. 实现时需要查证的接口事实

| 项目 | 当前情况 | 查证时机 | 缺失时处理 |
|---|---|---|---|
| DSH Hook 中的可信用户 ID | 现有参考插件按 preset 分域，未证明 Hook 提供多用户 ID | 需要单进程服务多用户时 | v1 每个 DSH 进程只配置一个用户令牌；多个这样的进程可以接同一 Rust 内核 |
| DSH 事件 source 与 seq 的稳定性 | 参考插件能读到相关字段；需对目标 DSH 版本再看接口 | 阶段 1 | 缺失字段时不可猜测，缩小接入范围 |
| DSH 工具能否取得最近原始用户消息 | 参考插件使用该信息；需核对目标版本 | 阶段 2 | 禁止 `remember/correct/forget` 自动操作，保留 search/get |
| DSH 安装方式与插件配置文件 | 目标 DSH 版本可能演进 | 阶段 0 | 在独立 profile 中加载并记录确切命令 |
| Rust 可用的中文关键词索引 | 默认 SQLite tokenizer 可能不适合短词 | 阶段 2 | 按 [13](13-算法与模型契约.md) 实施 Unicode 二元字索引 |
| 模型提供者的稳定接口 | DSH 凭据与调用接口需查证 | 阶段 3 | Rust 用显式配置的兼容端点，密钥不进 Prompt |

这些是技术调查，不要求用户再回答。查证结果写回 [06-DSH接入契约](06-DSH接入契约.md) 或对应设计文档。

## 3. 以后再定的产品问题

- 一名用户的多个设备／DSH 实例是否共享同一库以及如何同步。
- 是否允许用户主动分享一条记忆给另一用户。首版不允许。
- 推断性 observation 何时可以 active，是否需要用户确认，是否按领域设不同规则。
- 敏感记忆能否在用户明确同意后自动注入，以及如何撤销同意。
- 原始会话的保留天数、备份及彻底删除语义。
- Markdown 人工编辑和双向同步是否值得加入。
- 何时增加向量／图检索、多轮 reflect、长期摘要以及跨宿主适配器。

这些问题可以等到首版闭环出现实际需求后再定。开发者不得通过默认值悄悄引入跨用户共享或敏感自动注入。

## 4. 主要技术风险

1. **DSH 同进程多用户身份来源不足。** 首版允许多个单用户 DSH 进程各持自己的用户令牌连接同一 Rust 内核；Rust 内核按令牌隔离。不能宣传一个 DSH 进程已经能按认证用户自动切换令牌。
2. **模型候选超出证据。** 结构化 JSON 和 source ID 不等于事实正确。首版的自动 active 范围严格限于用户直接表达，复杂推断留在 held。
3. **中文检索漏召回。** 不把英文分词器的结果写成“中文已支持”；阶段 2 用少数真实中文短查询确认词法行为。
4. **缓存与遗忘不一致。** 检索、上下文和摘要都必须在读路径按规范状态过滤，不能等待后台重建才停止使用旧信息。
5. **DSH 事件回流。** 注入内容和模型回复可能再次进入捕获流，必须保留 origin/source 标签，阻断从插件内容自动提取新用户事实。
6. **双插件共存。** 新旧插件同时运行会重复注入和写入；试运行采用独立 profile。
7. **API 成本不受控。** 以会话结束批量提取、幂等窗口、有限重试和用量日志限制成本；不进行海量 API 验证。
8. **上游变化。** 参考路径、行为和许可必须以文档记录的 commit 为锚；再次借鉴时重新看对应文件。

## 5. 文档变更流程

1. 提交变更前，写明是用户新决定、上游事实变化、DSH 接口变化，还是实现中发现的问题。
2. 对照 [02-上游源码对照](02-上游源码对照.md) 核查来源；若只是借鉴思想，标成“本项目决策”。
3. 修改影响到的契约、数据模型、流程、DSH 接口和阶段完成条件，避免只改一个文件。
4. 如果改变用户级共享、跨用户隔离、旧数据迁移或长时间 API 测试的已定边界，应先向用户说明具体变更原因与影响。
5. 每次实现报告记录文档版本与代码状态。设计文档通过不代表功能已经实现、构建或在 DSH 运行。

## 6. “按上游做”的具体解释

三个上游项目没有单一一致的可信度、持久化和注入规则。本项目按每个问题选择源码中确实存在的成熟机制，并记下偏离：证据先存参考 EverOS；来源与巩固参考 Hindsight；L1 提取、任务处理和短摘要／按需工具参考 TencentDB。用户级跨 Agent 共享是用户明确决定，因此不能原样照搬 EverOS 的 `user_id XOR agent_id` 查询、Hindsight 的任意 bank 命名或 TencentDB 的团队 ACL。

“不瞎改瞎测”落实为：先读源码；少做自创启发式和未证明的阈值；只验证当前切片必须成立的行为；等真实失败出现后再增加相应机制。

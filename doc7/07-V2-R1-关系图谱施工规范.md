## 0. 定位与政策边界（先说清楚本卡**不能**做什么）

V2 文档 01 §5 明确：当前 `extract_v4/admit_v4` 的 THIRD_PARTY 门仍会把涉及第三人的候选 held，
**该政策尚未决定是否放宽**。因此本卡：

- **不**新增任何放宽的准入路径，**不**让维护任务自设宽松准入，**不**把 held 正文复制到人物页规避该门；
- 只做「**合法 active 记忆 → 关系投影**」这一条路：实体、别名、关系条目全部由**确定性 Rust 规则**
  （`entity_v1`）从当前可见记忆的正文投影出来，逐条带来源；
- 人物事实的**完整覆盖仍受限**，这是政策结果，不是本卡缺陷。验收分别记录：
  「关系投影路径通过」与「完整人物事实覆盖受限」——不得合并成「与 Muse 等价」。

## 1. 迁移 0017（DDL 冻结）

新增 `0017_relationship_graph.sql`；`0001`—`0016` 冻结不动；`SCHEMA_VERSION 16 → 17`。

```sql
CREATE TABLE relationship_entities (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  domain_id TEXT NOT NULL DEFAULT 'user_main',
  entity_kind TEXT NOT NULL CHECK (entity_kind IN ('person','group')),
  slug TEXT NOT NULL,                 -- 规范化显示名，同 (tenant,user,domain,kind) 内唯一
  display_name TEXT NOT NULL,
  relation TEXT,                      -- 与用户的关系（证据明确时才写）
  summary TEXT,                       -- 由条目确定性截断，不生成
  closeness_rank INTEGER,             -- 可空；本项目排序用，非 Muse 算法

    CHECK (rank_source IN ('user_explicit','verified_role','unranked')),
  version INTEGER NOT NULL DEFAULT 1 CHECK (version > 0),
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','stale','removed')),
  generator_version TEXT NOT NULL,
  batch_version INTEGER NOT NULL CHECK (batch_version > 0),
  generated_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (tenant_id, user_id, id),
  UNIQUE (tenant_id, user_id, domain_id, entity_kind, slug),
  FOREIGN KEY (tenant_id, user_id) REFERENCES principals(tenant_id, user_id)
);

CREATE TABLE entity_aliases (
  tenant_id TEXT NOT NULL, user_id TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  alias TEXT NOT NULL,
  alias_kind TEXT NOT NULL CHECK (alias_kind IN ('name','nickname','role')),
  memory_id TEXT NOT NULL,           -- 来源引用：别名也要有出处

CREATE TABLE relationship_items (
  id TEXT PRIMARY KEY,

  entity_id TEXT NOT NULL,

  body TEXT NOT NULL,
  observed_or_inferred TEXT NOT NULL CHECK (observed_or_inferred IN ('observed','inferred')),
  occurred_at TEXT,
  valid_until TEXT,

  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','stale','removed')),
  generator_version TEXT NOT NULL,
  source_fingerprint TEXT NOT NULL,
  batch_version INTEGER NOT NULL CHECK (batch_version > 0),
  generated_at TEXT NOT NULL, updated_at TEXT NOT NULL,

  FOREIGN KEY (tenant_id, user_id, entity_id)
    REFERENCES relationship_entities(tenant_id, user_id, id) ON DELETE CASCADE
);

CREATE TABLE relationship_sources (
  tenant_id TEXT NOT NULL, user_id TEXT NOT NULL,
  item_id TEXT NOT NULL,

  PRIMARY KEY (tenant_id, user_id, item_id, memory_id),
  FOREIGN KEY (tenant_id, user_id, item_id)

CREATE INDEX relationship_sources_by_memory

CREATE TABLE group_memberships (
  tenant_id TEXT NOT NULL, user_id TEXT NOT NULL,

  memory_id TEXT NOT NULL,

  FOREIGN KEY (tenant_id, user_id, group_id)
    REFERENCES relationship_entities(tenant_id, user_id, id) ON DELETE CASCADE,
  FOREIGN KEY (tenant_id, user_id, person_id)
```

**本卡不启用 `group_memberships`**：成员关系也必须来自证据，而 `entity_v1` 目前只识别
「用户 ↔ 某人」的单跳关系，不猜「同场提及即成员」。表先建好、留空，并在 §5 记录为未启用，
避免以后为该能力再改一次表结构。

## 2. 实体投影规则 `entity_v1`（确定性、保守、宁缺勿滥）

输入：写域内**当前可见**的 active 记忆（复用 V2-P1 的 `visible_memory_sql`，不另写口径）。
只识别**明确写出关系词与名字**的两种句式：

| 句式 | 例子 | 产出 |
|---|---|---|
| A：`<REL>(叫|叫做|名字是|名叫)<NAME>` | 「我妻子叫小雨」 | person(display_name=小雨, relation=妻子, alias=小雨) |
| B：`<NAME>是我的?<REL>` | 「老王是我的同事」 | person(display_name=老王, relation=同事, alias=老王) |

- `REL` 取自受控词表（配偶/父母/子女/兄弟姐妹/恋人/同事/上级/下属/老师/同学/朋友/邻居/室友，中英文各若干）。
- `NAME`：**2—12** 个 `[\u4e00-\u9fa5A-Za-z0-9]` 字符，**不得**本身是关系词、**不得**是代词或自称
  （他/她/它/我/你/您/他们…）、**不得**是「自称/代词 + 关系词」的组合（如「我妻子」）、**不得**含标点。
  含关系词的**正常称呼**（「王老师」「李医生」）仍然接受——只拒绝代词前缀那一类。单字名字一律不建实体
  （1 个汉字太容易撞上代词或量词），这是有意的宁缺勿滥。
- 一句里出现多个候选、或名字与关系词之间夹了其它实词 → **整条跳过**，不猜。
- 代词（他/她/TA）**不产生实体**：指向不明就不建。
- 每条产出都必须带来源记忆 (memory_id, version, claim_sha256)；没有来源的实体/条目不得存在。

**同名的处理（如实记录为限制）**：slug = 规范化显示名，`UNIQUE (tenant,user,domain,kind,slug)`
意味着**同名即同一实体**。真正的同名不同人需要在名字之外还有可核对的证据，
`entity_v1` 不做这种消歧，本卡不声称解决同音同名。「相似但不相同」的称呼
（老王 / 王老师）是不同 slug，**不会**被合并——这才是 V2 文档 01 §3 要求的「同名不误并」。

### 2.1 条目与分节

每个实体产出条目（body 是来源记忆 claim 的**原文**，不概括）：

| section | 来源 |
|---|---|
| `relationship` | 承载关系词的那条记忆（body 原文） |
| `facts` | 同一实体的其余见闻（本卡只收「claim 里同时出现该 display_name」的可见记忆） |

`open_threads` / `strengthening` / `in_common` / `history` 本卡**保持为空**——
没有证据就不填，不为填字段编造内容。

### 2.2 排序（本项目选择，非 Muse 已知算法）

`closeness_rank` 缺失时按 `rank_source` 排序：`user_explicit` > `verified_role` > `unranked`，
同级按 `display_name` 升序、再按 `id` 升序稳定收尾。**提及频率不参与 rank**（只作检索相关性）。
本卡没有「用户明确排序」的输入入口，因此实际只会出现 `verified_role`（有明确关系词）
与 `unranked` 两档；`user_explicit` 留位待后续用户更正入口。

## 3. 读接口

| 接口 | 语义 |
|---|---|
| `index(domain)` | 有预算的索引条目：entity_id、kind、display_name、aliases、relation、summary、version、详情引用、更新日期、rank_source、rank |
| `get(entity_id, expected_version?)` | 实体详情 + 分节条目（逐条带来源）；版本不匹配返回 409 |
| `resolve(query)` | 按 display_name / alias 精确匹配（归一化后）：0 结果→`none`，1→`one`，>1→`ambiguous`（返回全部候选，**不猜**） |

读路径与 V2-D1 同构：条目/实体逐条复核来源（记忆当前可见 ∧ version/sha 未变），
来源一改即时屏蔽并计入 `skipped_stale`；`stale`/`removed` 的实体不进索引。

## 4. 生命周期与权限

- **域**：实体 `domain_id` 与来源域一致；读按 V2-S1 读域集过滤；side 私有实体不进主索引。
- **重建**：同 (tenant,user,domain) 内整体替换，`batch_version` 递增；实体 `version` 在重建后
  递增（内容变化才算），用于 `get(expected_version)` 的并发校验。
- **purge / forget 闭包**：purge 删该记忆的 `relationship_sources` 与 `entity_aliases` 行，
  再删因此零来源的条目/实体（不允许无来源的实体存活）。
- Agent 不得直接写这些表；只有重建路径与 purge 闭包能改。

## 5. HTTP / 适配器

| 入口 | 语义 |
|---|---|
| `GET /v1/relationships` | 索引（预算 + 省略计数） |
| `GET /v1/relationships/{entity_id}` | 详情（`?expected_version=`） |
| `GET /v1/relationships/resolve?q=` | 名称/别名解析，返回 `resolution: none|one|ambiguous` |
| `POST /v1/relationships/refresh` | 重建（同事务、递增版本） |
| `memoryd relationships refresh --config --tenant --user --domain` | CLI 等价入口 |

DSH 每轮注入索引与「相关人物先读」纪律 → **V2-H1**，本卡只到 HTTP/CLI。

## 6. 验收（`v2_r1_tests`）

1. **两种句式**：A 句与 B 句各产出一个 person，display_name/relation 正确，别名与条目都带来源。
2. **宁缺勿滥**：代词句、名字含标点、`REL` 不在词表、一句多候选 → 都不产生实体。
3. **不误并**：「老王」与「王老师」是两个实体；同一 display_name 的重复来源归并到同一实体且
   别名去重。
4. **resolve 三态**：命中 0/1/多；歧义时返回全部候选且 `resolution="ambiguous"`。
5. **来源失效即时屏蔽**：改来源版本后不重建即读不到该条目，`skipped_stale>=1`；重建后一致。
6. **purge 闭包**：purge 唯一来源后实体与条目都不再存在。
7. **域隔离**：side 实体不进主域索引；授权后可见。
8. **分级排序**：有明确关系词的在 `unranked` 之前，同档按名称稳定排序。
9. **组表未启用**：`group_memberships` 在本卡不产生任何行（如实断言，避免以后当成已实现）。

档位：`cargo build --workspace && cargo test --workspace` → 临时库 HTTP 冒烟
（index/get/resolve/refresh）。真实 DSH 闭环、真实模型：**本卡不涉及，未验证**；
**人物事实完整覆盖受 THIRD_PARTY 门限制**，单独记录，不写成已解决。

## 7. 明确不做 / 移交

- 放宽第三人准入、把 held 候选提升为人物事实 → **需要独立产品决定**，本卡不做。
- 群组成员关系 → 表已建、本卡不启用（缺证据规则）。
- 复杂实体消歧（同名不同人）→ 需要名字以外的可核对证据，本卡记录为限制。
- 别名归并（「老王」=「王老师」）→ 需要上下文与来源同时明确；本卡只在同一记忆里
  明确写出两种称呼时才归并，跨记忆归并交给后续维护任务。
- DSH 索引注入与使用纪律 → V2-H1。
- 可写人物页、双向同步 → 不做（DB 唯一真相源）。

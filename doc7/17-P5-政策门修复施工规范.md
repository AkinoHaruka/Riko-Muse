## 1. 现场证据与版本边界

- P4 的 S08「我的健康记录里有心脏病。」在 Gemini、S09「我患有哮喘。」在 Gemini 与 Qwen 均 active；基线政策泄漏分别为 2/120、1/120。`memory-extract/src/lib.rs::sensitive_health` 当前只匹配「过敏/诊断/病历/疾病/吃药/服药/身份证/银行卡」。
- `memory-extract/src/lib.rs::admit_v4` 规则 8 只检查 `claim`（若有），否则检查 quote。模型改写若省去健康语义，原始 quote 的敏感信息可能越过该门。这是代码路径风险，尚未有 P4 实测命中数。
- `memory-server/src/worker.rs` 仅在作业 `prompt_version == extract_v4` 时触发 rewrite，`admission_version` 有显式白名单；`memory-contract/src/lib.rs` 当前默认 `extract_v4/admit_v4`。因此新版本需要三处同步接线，旧作业按其行内版本运行。
- 新版本预留为 **`extract_v5`、`admit_v5`、`rewrite_v5`**（rewrite 是 `extract_v5` 作业内步骤，无独立作业版本列）。冻结 `extract_v1`—`v4`、`admit_v1`—`v4` 的提示词与行为；历史 `admit_v3` 常量已另有用途，不复用。无数据库迁移，schema 23 不变。

## 2. `admit_v5` 健康门规则

保持 v4 的来源、逐字 span、长度、上下文、多命题、秘密、第三人、时间等门序。规则 8 以 **quote 与非空 claim 的并集**判定：任一文本命中即 `held:SENSITIVE`，不能让 rewrite 删词后放行。规则 1–3 始终检 quote。未来任何模型健康判定也必须在 Rust 校验来源后、写 active 前执行，失败按规范的失败策略处理；模型不得自行决定 scope 或证据 ID。

确定性规则分组（中英同时处理，按词边界/语境组合，不能粗暴匹配单字 `病` 或英文子串 `ill`）：

| 组 | 命中形态与例子 | 应避开的误伤 |
|---|---|---|
| 疾病名与患病陈述 | `患有/得了/有/被确诊` + 疾病名；常见明确疾病名可独立命中，如心脏病、哮喘、糖尿病、高血压、癌症；`I have asthma/diabetes`、`diagnosed with` | 产品「心脏」图标、书名里的疾病词须结合个人健康归属；一般 `have` 不算 |
| 症状陈述 | 第一人称或用户归属 + `胸痛/呼吸困难/发烧/头晕/疼痛` 等症状，英文 `I have chest pain` / `shortness of breath` | 「这个 bug 让我头疼」等常见比喻需有医学或身体语境；普通疲劳/心情不直接列敏感疾病 |
| 诊断、病史与治疗 | `诊断/确诊/病史/病历/治疗/服药/处方/手术` 及 `diagnosis/medical history/prescription/surgery`，与用户身体/医疗语境结合 | 「故障诊断」「代码病史」之类技术或比喻用法 |
| 健康记录 | `健康记录/体检报告/检查结果/化验单/医疗记录` 及 `health record/medical record/lab result`，归属于用户时命中 | 「我在开发健康记录应用」不因产品名 held |

原 v4 的证件/银行卡字面词继续作为 `SENSITIVE` 规则，凭据仍由 `SECRET` 优先持有。规则覆盖要按组至少各有中英正例、中文/英文负例；S08/S09 及 rewrite 省略敏感词的案例必须 held/reject。`我吃苹果`、`I eat apples` 不命中；`吃药/服药` 仍命中。不得为压泄漏简单对所有「吃」「检查」「记录」「健康」字面词一律 held。

## 3. `extract_v5` / `rewrite_v5`

- episode：发生过的、可定位为一次事件或人生节点的个人陈述归 `episode`，如搬家、毕业、旅行、发布作品、换工作、演讲、比赛、出版；持续状态如「我住在杭州」归 `fact`。相对时间保留原文，不能编造具体日期。`kind` 不由 rewrite 偷改；对 E01–E12 逐条统计 kind，与 P4 对照。
- 多指令：一句话里两个可独立遵守的长期指令，阶段 1 分成各自逐字、连续且尽量不重叠的 quote；如 M06「以后用中文回答」和「在引用数据时给来源」，M12「以后解释算法请编号」和「给一个示例」。共享前缀确实无法逐字分别承载时，允许宽 quote 进 rewrite，但 rewrite 至多两条 claim **均要分别入候选并各自经过 `admit_v5`**；不能沿用 v4 仅落首条、次条只记审计的行为。
- rewrite 不得增事实、删否定/条件、变更第三人归属或删敏感语义；源 quote 始终保留。若无法拆成可独立审计的两条，就保持 held，不以一条 active 代替完整多指令。
- `extract_v5` 与 `rewrite_v5` 使用独立新常量，新增分发，不修改 v4 文本或 v4 作业路径。作业重试、审计与幂等需覆盖两条 claim；若现有存储键无法支持，先记录冲突与新设计，不靠重复提交绕过。

## 4. 评测隔离协议和验收线

固定 P4 的 120 行 TSV、标注和两模型；不修改期望 disposition、kind 或政策样本。先按 P4 原 15×8 窗口重跑新版本，用于与 P4 **共库基线**对照 active 率、held 原因及逐条变化，注明模型随机性与窗口上下文干扰。再以**每案例一座全新临时库、一个 session、一个窗口**分别跑现行 v4 和新 v5；24 个政策样本必须全部隔离跑，85 个期望 active 的非敏感样本也隔离跑以比较误杀，其余案例隔离跑用于完整分布。只给该行及其明确标注所需上下文；不得复用其它案例的 active 记忆。`POSSIBLE_CONFLICT` 单列，不计政策门误杀。

政策泄漏 = `third_party` 或 `policy` 标注行任一不允许的 active 命题；**两模型各自全 120 条及隔离政策组均为 0** 才满足泄漏线。非敏感误杀以 `expected=active` 且不属敏感/第三人政策的行中，因为 `SENSITIVE` 被 held 的案例数 / 该组案例数计；与 P4 同样口径的原版本在隔离协议下重跑比较，**新版本不得升高**。另列所有从 P4 active 变 held 的非敏感行和原因，不能只报总数；若泄漏 0 而 held 大量增加，判未通过。整体 active 率、held 原因、episode kind、M06/M12 两要点、失败/重试、模型输出缺失分开报告，不以总体 active 率替代政策质量。

真实端点、临时库、密钥文件权限、无 mock 与逐条 JSON 留证沿用 P4。不得打开 dana/realtest 原库，不改官方 DSH clone，不改冻结迁移。规范、代码、交接 41 分别 scoped commit；完整验收后才 push。

## 5. 待决：无关键词的语义健康陈述

有限词表无法可靠判定「上次检查医生说我这不太好」或「那个结果不太好」在上文体检语境中指用户健康，更不能对任意隐喻、跨句指代证明零泄漏。把「检查/医生/结果」泛化为独立敏感词会把非医疗陈述也 held；只扩疾病名又会漏掉这些表达。`admit_v4` 只看候选 quote 或改写 claim，更无法凭未传入的上文恢复指代。**这一缺口不因 S08/S09 与固定 120 条变绿而消失。**

需明确二选一后才开始实现：

1. **规则门限定范围**：`admit_v5` 实施 §2 的高精度词与语境组合，验收宣称严格限定为固定语料及列明的规则族；无关键词/跨句健康语义作为已知未覆盖，不宣称一般意义的健康政策 0 泄漏。若产品政策要求所有健康语义不得 active，此选项不满足任务目标。
2. **模型辅助判定门**：在确定性规则后、active 提交前，增加独立的健康语义分类步骤，输入 quote、claim 与同窗允许的用户上下文，输出结构化 `sensitive/clear/uncertain` 及证据 span；`sensitive/uncertain` 和超时/坏响应均 held，且需做独立误杀评测、成本/重试/审计规范。模型判断仍不能替代 Rust 的来源、span 和 scope 校验；模型有误判概率，不能声称对开放语义的数学保证。

决议还需明确：政策成功线是「固定 120 条及新增语义挑战集泄漏 0」还是「开放语义一律 fail closed」。后一口径会显著改变非敏感误杀与可用性，必须在写代码前批准，不能事后改标注凑数。

## 决议（2026-10-23，编排者 Riko 决定）

采用 **§5 方案 2（模型辅助判定门）**，按以下口径实施；方案 1 不再考虑。

**决定理由**：
- 漏掉的缺口本质是语义（跨句指代、无关键词陈述），只有语义层面的判定能补。规则门限定的方案会让这份规范亲笔承认"已知未覆盖"，等于把今晚刚标红的安全门原样交回去，修复卡失去意义。
- 抽取栈本就是模型重的（extract/rewrite 都是模型作业），在门上加一道模型辅助判定不引入新的架构依赖；确定性规则仍做第一层（纵深防御），模型判做第二层。
- fail closed 的不对称性正确：held ≠ reject。漏放是不可挽回的数据安全事件，误 held 只是进入人工/保守复核，可恢复。用 held 吸收误判成本，不用 reject。
- 不采纳"开放语义一律 fail closed"这种会压垮可用性的口号式成功线。成功线定为：**固定 120 条 + 新增语义挑战集（无关键词/跨句/隐喻类健康陈述，独立编写）两模型泄漏 0；非敏感误杀率不劣于 P4 基线**。两项都是可测量的，不给"一般意义 0 泄漏"这种无法证伪的宣称。

**实施约束（写进验收）**：
1. 模型判定只做 `sensitive/clear/uncertain` 三分类 + 证据 span；scope、证据 ID、来源校验仍由 Rust 做，模型输出不得决定它们。
2. `sensitive`/`uncertain`/超时/坏响应/输出格式非法 → 全部 held（fail closed），审计留痕；超时不无限重试（上限与退避按 §4 的失败规范）。
3. 误杀评测必须包含新增语义挑战集的阴性样本（身体相关但非敏感的陈述），并逐条报告 P4 active → held 的非敏感行；泄漏 0 但 held 大量增加判未通过（§4 口径）。
4. 成本单独记录：每候选批的额外模型调用次数与耗时，作为交付记录的一项指标。
5. 该门形态如在实施中被证明不可靠（例如模型在挑战集上误判率失控），回到本决议重议，不许静默降级为规则门交差。

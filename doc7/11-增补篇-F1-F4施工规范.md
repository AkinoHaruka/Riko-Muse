## F1 · Commitment 跟踪（轻方案 B）

**背景**：`MemoryKind` 只有 Fact / Preference / Instruction / Episode。用户说"下周三前把报告发我"，当前只能记成一条 Instruction，"到期未履约"这个状态机无处安放。

**目标**：承诺可建、可到期、可标记履约/取消；不碰核心 kind。

**方案**（Antigravity 建议，Riko 认可）：轻方案 B——独立 `commitments` 跟踪表，关联底层 Instruction/Episode 记录，**不新增第五种 MemoryKind**。
- 理由：0001–0018 迁移冻结纪律；核心 kind 的 CHECK 约束不动；形态类比 V2-B1 `repair_actions`。

**Schema**（0019 或后续迁移）：

```sql
CREATE TABLE commitments (
  id          TEXT PRIMARY KEY,
  memory_id   TEXT NOT NULL,   -- 关联的 Instruction / Episode
  kind        TEXT NOT NULL,   -- deadline / reminder / promise
  due_at      TEXT,            -- ISO8601，可空
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending / fulfilled / overdue / cancelled
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  fulfilled_at TEXT,
  FOREIGN KEY (memory_id) REFERENCES memories(id) ON DELETE CASCADE
);
-- overdue 由 tick 调度器判定（pending 且 due_at < now），复用 M1 的 15min 调度器，不另立状态机
```

**API**：

```
POST /v1/commitments                       {memory_id, kind, due_at?}
GET  /v1/commitments?status=pending&due_before=...
POST /v1/commitments/{id}/fulfill
POST /v1/commitments/{id}/cancel
```

**测试**：
- 建 → 到期 → 履约 / 取消四态流转
- overdue tick：due_at 过期自动翻 overdue，原记忆不动
- purge 闭包：删记忆级联清 commitments

**验收**：
- 25-turn 语料人工标注 ≥5 条承诺，全链路可建可查
- overdue 判定延迟 ≤ tick 间隔

## F2 · 召回决策日志

**背景**：`GET /v1/memories/{id}/explain` 是静态单条 provenance。缺的是动态记录：这次查询为什么选了这些、排了这个序、截断/排除了那些。排障只能靠猜。

**目标**：每次 recall / context compose 留下决策痕迹，可查可审。

**方案**：`recall_log` 表（写多读少，retention 默认 30 天滚动）：

```sql
CREATE TABLE recall_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  ts            TEXT NOT NULL,
  query         TEXT NOT NULL,
  hit_ids       TEXT NOT NULL,  -- JSON: [memory_id...]（入选）
  scores        TEXT,           -- JSON: {memory_id: {fts, vector, rrf, final}}
  rank          TEXT,           -- JSON: 最终排序
  cutoff_reason TEXT,           -- token_budget / score_threshold / dedup_collapsed ...
  excluded      TEXT            -- JSON: {memory_id: reason}（被排除）
);
```

**API**：

```
GET /v1/recall/log?limit=50&query_like=...
GET /v1/recall/log/{id}
```

**测试**：
- 同一 query 两次 recall，日志决策一致（确定性）
- token budget 触发截断时 cutoff_reason 非空
- retention：31 天前记录被清

**验收**：任一线上 bad case，可在 5 分钟内定位到"为什么没召回 / 为什么排后"。

## F3 · Golden 抽取回归集

**背景**：25-turn 真实模型语料是 handoff 验收记录，不是自动化 fixture。extract prompt 一改就得人肉重跑。

**目标**：语料沉淀为 `tests/fixtures/golden_extract_v4.json`，CI 可跑，防回归。

**方案**：
- fixture 条目：`{turn_id, dialogue_snippet, expected_claims[{claim_text, kind}], expected_held[{reason_code}], must_not_leak[...]}`（脱敏后入库）
- 离线断言（不调模型，测 rewrite 规则层 + admit_v4）：
  - 改写后 claim 含显式主语
  - held reason_code 符合预期（SECRET / POLICY / POSSIBLE_CONFLICT …）
  - quote 原文保留
  - 政策门零泄漏（suppressed 不得变 active）
- 在线模式（nightly，有 key 才跑）：调真实模型重跑抽取，active 率波动超阈值告警

**验收**：
- `cargo test` 中 golden 用例全过
- 改 prompt 导致回归时，CI 红灯先于人肉发现

## F4 · Held 候选 HTTP 只读视图

**背景**：held 已落库（§0 纠错 2），CLI 可查，缺 HTTP 只读接口。宿主 / Harness 侧看不到 held 队列。

**目标**：只读 HTTP 视图，零写风险。

**API**：

```
GET /v1/candidates?status=held&limit=50
→ [{id, claim_text, kind, reason_code, created_at, evidence_quote}]
```

**测试**：
- held 写入后接口可查，字段与 CLI 输出一致
- 非 held 不出现在结果中
- 只读：该路径无 POST / PUT / DELETE

**验收**：Harness 侧可展示 held 队列（为后续人工审核 UI 铺路）。

## 5. 验证优先级重排

rewrite 单点已验证（§0），当前最高优先级变更为：

**DSH 全宿主真实模型多轮闭环验收**

- 验收：多轮后记忆可用（recall 命中符合预期）、无政策泄漏、held 队列行为符合预期
- 状态：待 DSH clone 完成 + twin-bundle 插件骨架就绪后立项
- 测试 key 现状（2026-10-09）：Gemini（P2）可用；SiliconFlow（P3）可用；OpenRouter（P1）key 限额 0 暂不可用；ling-3.1-flash 限免至 10-13

## 6. 非目标与架构边界（重申）

- **近似去重**：放 recall 侧折叠 / compact 阶段，不做 admit 同步重型去重（保持写入门轻量）
- **自然语言时间意图解析**（"上周说的"）：backlog，当前仅 Episode 弱 recency
- **主动 research / select / delivery**：Harness 宿主层，不进 memoryd
- **不新增 MemoryKind**（F1 轻方案 B 已体现）
- **不动 0001–0018 冻结迁移**；新表走 0019+
- **secret 处理分层**：capture 层脱敏 + extract 侧 Held("SECRET") 门并存，不互相替代

## 附 · 设计原则注记

2026-10-09 octop-memory 对比研究（腾讯开源，Python，v1.0.0）带来的启发，记为原则，不进本期实施：

- **门控松紧应为抽取质量的函数**：extract 越强，门越敢开。octop 走 demotion-only（默认全放行），Riko 走 admit_v2（默认 held）——两条路各有代价。远期方向是以 salience 排序代替 held 拦截，向 Muse 的"记得宽、排得准"靠拢（X 为准）。
- 本增补篇不改变 admit_v2 当前行为；任何门控放松需 extract 质量证据支撑，逐次评审。
- octop 的 `verbatim_quote` 全链路证据、`needs_review` 7 天老化自动转 low-confidence promote，值得后续单独立项评估（不进本增补篇）。

## 1. 定位

V2-H1 把前四张卡的产物接到宿主上：**每轮实际消费** compact / alignment / relationships index / retrieved，
并给出工具与使用纪律。**本卡不实现内容生成**（那是后续卡的事），只做读取侧的宿主闭环。

## 2. 服务端：bundle 分段（加法式扩展，不改旧键）

`POST /v1/context/bundle` **保留**原来的 `resident`/`retrieved` 顶层键（旧适配器与 doc6 行为逐字节不变），
**新增** `segments` 数组与 `budget`：

```json
{
  "request_id": "…",
  "resident": { … 原样 … },
  "retrieved": { … 原样 … },
  "budget": { "total_chars": 4000, "used_chars": 2310 },
  "segments": [
    { "segment": "compact", "domain_id": "user_main", "version": 3, "char_count": 120,
      "complete": true, "omitted": 0, "deduped": 0, "items": [ { "body": "…", "stable_refs": ["riko://memory/…"] } ] },
    { "segment": "alignment", "domain_id": "user_main", "version": 2, "char_count": 80, "complete": true },
    { "segment": "relationships", "domain_id": "user_main", "batch_version": 1, "total": 5,
      "complete": false, "omitted": 2, "char_count": 96, "items": [ { "entity_id": "…", "display_name": "小雨",
        "relation": "妻子", "aliases": ["小雨","妻子"], "version": 1, "detail_ref": "riko://entity/…" } ] },
    { "segment": "retrieved", "domain_id": "user_main", "char_count": 1800, "complete": true, "deduped": 2 }
  ]
}
```

规则：

1. **统一预算**：`BUNDLE_TOTAL_CHARS = 4000`（服务端常量）。按
   `compact(≤1200) → alignment(≤600) → relationships(≤600) → retrieved(剩余)` 顺序分配；
   任一段超出剩余预算即截断并置 `complete=false`。
2. **重复原子来源合并**：retrieved 里 memory_id 已出现在 compact 中的条目被丢弃，计数进 `deduped`。
3. **可见性同源**：四段都用 V2-P1 的统一可见性判定与 V2-S1 读域集，不另写口径。
4. **省略可见**：每段给出 `omitted`/`complete`，调用方据此决定是否走工具按需读。
5. 空段仍然出现（`char_count=0`、`complete=true`），调用方不必猜键是否存在。

## 3. 适配器：分段消费

`adapters/dsh/src/recall.ts`：

- 有 `segments` 时按数组顺序为每个非空段前插**一条独立的 user-role 消息**，
  `source.form` 依次为 `compact`/`alignment`/`relationships`/`retrieved`；
  段正文仍走既有的数据包裹（`wrapData`），任意文本不得被当成宿主指令。
- **没有** `segments` 时（旧服务端）回退到原来的 `resident`/`retrieved` 两段，
  行为与 D6 完全一致。
- 空结果不加占位；离线/失败/取消照旧跳过并保持原 `decision`。
- 去重与预算由服务端负责（唯一真相），适配器不再二次裁剪，避免两边口径不一致。

## 4. 工具与使用纪律

新增适配器工具（都走统一可见性判定）：

| 工具 | 语义 |
|---|---|
| `memory_relationships` | `action=index\|resolve\|get`：先看索引、名称解析（歧义返回候选）、按 entity_id + expected_version 读详情 |
| `memory_facets` | 读四分面投影（`kind` 可选；缺省返回四段），用于按需读取而非常驻注入 |

`memory_explain` 已在 V2-P1 交付。原有 `memory_search/get/remember/correct/forget` 协议不变。

**使用纪律**（写进插件工具说明与 profile 说明，不改 DSH 源码）：
重要变化即时保存且**成功才说保存**；每个新用户回合做有界回忆检查（已有 bundle 算一次）；
相关人物的事实或推荐**先 get 详情**再回答；片段不足先精读（explain）；
问来源用 explain；不确定或索引滞后时查规范源；歧义时**不猜**。

## 5. 验收

档位：`cargo build/test --workspace` + 适配器 `tsc --noEmit` 与 `npm test` →
临时库 HTTP 冒烟（bundle 分段字段、预算、去重、空段）。

1. **分段齐全**：四段都在数组里且顺序固定；空段 `char_count=0` 且 `complete=true`。
2. **预算**：构造超预算内容，断言 `used_chars ≤ total_chars` 且超限段 `complete=false`。
3. **去重**：compact 与 retrieved 命中同一 memory 时，retrieved 段 `deduped ≥ 1` 且正文不重复。
4. **旧键不变**：`resident`/`retrieved` 顶层键仍按 doc6 形状返回（回归断言）。
5. **域**：side 域请求的段只含该读域集内容；主域看不到 side。
6. **适配器**：`segments` 存在时按序注入多条消息且 `source.form` 正确；
   `segments` 缺失时回退旧行为（单测覆盖两种输入）。

**真实 DSH 闭环**：本卡给出「固定响应下宿主按序注入四段」的适配器单测级证据；
**真实模型下「知道了、核对了、用对了」仍未验证**，须单独记录，不得合并成一句「宿主闭环完成」。

# doc7/15 · P3 注入预算与形态

> 2026-10-22；前置：P0.6 真实闭环已通过（doc-handoff/36 §4）。本卡只改 bundle 选取预算与默认检索条数，不新增迁移、不改 DSH clone。

## 1. 测量依据

可复现的临时库审计使用 120 条 active：事实、偏好、指令、经历各 30 条，12 条关系句式混入其中；有逐字 user evidence、span 和 SHA。查询覆盖 5 个话题、5 个复合话题、1 个广义查询和 1 个无关查询。使用真实 memoryd HTTP bundle，未调用模型；详表与脚本见 doc-handoff/39。

| 口径 | 实测 |
|---|---:|
| 当前默认请求（8 条、2400 字符）：12 次中 retrieved `complete=false` | 11 次；省略 80 条，已注入 88 条，省略率 47.6% |
| 当前默认四段实际总字符 | 862–1531；没有触发 4000 总预算 |
| 放宽请求上限（100 条、24000 字符） | 12 次省略 0 条；广义查询实际 7742 字符，当前代码未执行 4000 总上限 |
| 同一广义结果按硬总上限模拟 | 4000 留 37/82 条、丢 45 条；8000 留 82/82；16000 同 8000 |
| 单话题放宽后候选数 | 12–21 条；24 条容纳全部五个单话题结果 |
| 默认请求被省略项人工抽样 | 20/20 与查询话题相关；样本只证明该构造语料的相关性 |

## 2. 新规则

1. `BUNDLE_TOTAL_CHARS=8000`。来源：广义查询放宽后实测总量 7742；模拟中 8000 覆盖全部 82 条，16000 无额外收益。它是本语料的上界选择，后续真实工作负载可再测。
2. `RETRIEVED_MAX_ITEMS_DEFAULT=24`。来源：五个单话题的放宽候选数为 12–21，24 可覆盖全部；原 8 条上限在 12 次请求中省略 80 条。`retrieved_max_chars` 默认 2400、最大 24000 保持原值。
   候选道深度使用既有 `SEARCH_PER_CHANNEL_LIMIT=100`，而不跟随输出的 24 条上限：放宽请求的广义查询有 82 条实际可见候选，若只拉 24 条，剩余项既不注入也不计入 omitted，却会误报 `complete=true`。100 是已有检索常量，本卡不引入新检索上限。
3. compact ≤1200、alignment ≤600、relationships ≤8 条和既有段内排序维持现状。实测 compact 675、alignment 187、relationships 0；没有数据支持调整这三段。retrieved 使用前段已占用后的弹性剩余。每条入选前检查硬总上限，超出则记 `TOTAL_CHAR_LIMIT` 省略并置 `complete=false`；继续考察后续短条目。该检查也覆盖请求方显式放宽上限的场景。
4. 前插独立 user-role 消息维持现状。预算审计没有提供更改角色形态的收益证据；适配器不改。
5. `budget.used_chars` 必须始终 ≤ `budget.total_chars`；`retrieved` 顶层和分段的文本、omitted/truncated/complete 必须一致。compact 与 retrieved 来源去重保留。

## 3. 验收

在新预算下断言硬上限、超限省略原因与 `complete=false`、compact 去重、四段顺序和旧键一致性；`cargo test --workspace`、`npm test` 全绿。用 P0.6 方法在临时库重验实际 DSH 四段注入及跨会话回忆，单独列明真实模型档位。

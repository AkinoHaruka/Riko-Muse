# 02｜提取作业状态机与调度契约

本文件替代 `doc/13 §3` 中不够具体的领取/恢复描述，保留单 SQLite、单 worker 的首版部署形态。目标是让每个已领取作业最终进入可解释状态，并且一个 session 的坏窗口不能让其他 session 停止前进。

## 1. 状态和字段

沿用 `queued/running/retryable_failed/succeeded/dead`。`dead` 表示需要人工处理；它阻断**本 session** 的后窗，默认不能被自动跳过。`run_after` 只控制 `queued/retryable_failed` 的到期时间；`lease_until` 只控制 `running` 所属权与崩溃恢复。所有写入时间格式统一为 UTC RFC3339 微秒精度，可作文本比较；不得混写本地偏移格式。

新增迁移 `0003_job_recovery.sql`：

```sql
ALTER TABLE extraction_jobs
  ADD COLUMN claim_generation INTEGER NOT NULL DEFAULT 0 CHECK (claim_generation >= 0);
CREATE UNIQUE INDEX jobs_through_unique
  ON extraction_jobs (tenant_id,user_id,host_id,session_id,through_event_seq);
CREATE TABLE extraction_job_skips (
  job_id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  reason_code TEXT NOT NULL,
  actor_kind TEXT NOT NULL,
  actor_id TEXT NOT NULL,
  created_at TEXT NOT NULL,
  FOREIGN KEY (tenant_id,user_id,job_id)
    REFERENCES extraction_jobs(tenant_id,user_id,id)
);
```

迁移前先检查既有库同 scope/session/through 是否重复；若有则停止迁移并报告 ID，不能任意删行。增量迁移后同步 `SCHEMA_VERSION`、版本端点、迁移 checksum；不得回改 `0001`/`0002`。`extraction_job_skips` 仅用于 [03](03-提取窗口与超限处理.md) 的显式人工跳过，不让模型或 DSH 工具写。

## 2. 合法状态转换

| 触发 | 前态 | 后态 | 要求 |
|---|---|---|---|
| flush 排入 | 无 | queued | 同 scope/session/through 幂等；同键返回既有作业 |
| 到期领取 | queued/retryable_failed | running | `run_after <= now`；原子增加 `claim_generation`，写 lease |
| 心跳续租 | running | running | 仅当前 generation 可续；不能在持有 SQLite 锁时等待模型 |
| 完成提交 | running | succeeded | generation 匹配；候选写入与完成顺序见 §5 |
| 可重试失败 | running | retryable_failed | generation 匹配；增加 attempts，写错误码和下次 `run_after`，清 lease |
| 耗尽或确定性失败 | running | dead | generation 匹配；写可诊断错误码，清 lease |
| lease 到期 | running | retryable_failed/dead | 恢复事务把失去所有权的 attempt 计入 attempts，增加 generation 使旧执行者失效 |
| 人工 retry | dead | queued | 仅本 scope 的完整 job ID；确定性超限先修复/处理，不做无意义循环 |
| 人工 skip | dead | dead + skip 行 | 仅 `WINDOW_TOO_LARGE` 等本阶段允许原因；见 03 §4 |

`attempts` 定义为**已完成或因 lease 超时而丢失的执行次数**。正常领取不加 attempts；当前执行结束时写 `attempts = 领取时 attempts + 1`。恢复过期 `running` 时也加 1。旧库的 running 行按这一定义恢复。`JOB_MAX_ATTEMPTS=3`、延迟 5/15/45 秒沿用现有配置；第三次失败直接 dead，第三个 45 秒数值仅作为既有常量保留，不承诺第三次后还有第四次自动尝试。

管理员对 dead 明确执行 `retry` 时，沿用现有“再给一次执行机会”的语义：设置 queued/run_after=now，**不清零**历史 attempts。该次失败会再次 dead；管理员可在排除原因后再次显式 retry。作业详情要保留累计 attempts，不能把人工 retry 伪装成新作业或重置历史。`WINDOW_TOO_LARGE` 不允许原样 retry，处理见 [03](03-提取窗口与超限处理.md)。

## 3. 原子领取与跨会话公平

每轮在一个 SQLite 事务内先恢复过期 running，再选一条**可执行**的 due job；不能先选全局最早行、发现受阻后放回并结束本轮。候选条件：

```text
status ∈ {queued, retryable_failed}
AND run_after <= now
AND NOT EXISTS 同 scope/host/session 中 through_event_seq 更小、
    且既非 succeeded、又没有 extraction_job_skips 行的前窗
ORDER BY run_after, created_at, id
LIMIT 1
```

使用 `through_event_seq` 数值比较，不比较 `window_key` 字符串或仅比较 `created_at`。同一 session 的前窗 `retryable_failed`、`running`、未跳过的 `dead` 都阻断后窗；其他 session 仍可领。领取 UPDATE 的 WHERE 再校验原状态与到期，成功后返回最新 `claim_generation`。先后判断和 UPDATE 必须在同一事务或等价的原子 SQL 内，不能在进程内 HashSet 与数据库更新之间留竞态。

查询骨架如下；实际参数仍由 rusqlite 绑定，不能拼 SQL 字符串。`a` 的排序是在**排除阻塞窗口之后**执行的：

```sql
SELECT a.id FROM extraction_jobs a
WHERE a.status IN ('queued','retryable_failed') AND a.run_after <= ?1
  AND NOT EXISTS (
    SELECT 1 FROM extraction_jobs b
    WHERE b.tenant_id=a.tenant_id AND b.user_id=a.user_id
      AND b.host_id=a.host_id AND b.session_id=a.session_id
      AND b.through_event_seq < a.through_event_seq
      AND b.status <> 'succeeded'
      AND NOT EXISTS (SELECT 1 FROM extraction_job_skips s
                      WHERE s.tenant_id=b.tenant_id AND s.user_id=b.user_id AND s.job_id=b.id)
  )
ORDER BY a.run_after, a.created_at, a.id LIMIT 1;
```

`window_lower_bound` 取同 scope/host/session 中 `through_event_seq < 当前 through` 且 `succeeded` 或显式 skipped 的最大数值；无前窗为 -1。不要再使用 `window_key <`。出现前窗未完成却处理后窗，属于内部不变量错误，应停止该 job 并暴露错误，不能静默扩大窗口。

## 4. 过期 running 与心跳

启动后首次轮询及每轮轮询都可执行过期恢复。`lease_until <= now` 或历史异常 NULL 的 running 算失去所有权。恢复更新须带 `status='running' AND claim_generation=旧值` 条件，增加 generation，记录 `WORKER_LEASE_EXPIRED`；未达三次按本次 attempts 对应延迟写 `retryable_failed`，达三次写 `dead`。恢复步骤不得覆盖已由另一个 worker 成功提交的行。

模型 timeout 可通过配置超过 90 秒，所以 worker 在处理期间每 30 秒续租一次；续租条件为 `id + running + claim_generation`，失败表示失去所有权，应取消/忽略后续模型结果。每次续租只短暂持有 DB 锁；模型网络调用绝不持锁。任务结束停止心跳。进程崩溃后不依赖心跳回调，靠数据库 lease 到期恢复。

## 5. 所有错误都要落状态

把 `process_job` 拆成“加载窗口/调用模型/解析/逐候选入库/完成”和单一的外层结果处理。只要一条 job 已变成 running，任何错误离开该函数前都要尝试条件化 `fail_job(id,generation,code)`；包括下界查询、超限、序列化、候选持久化、BAD_JSON、UNKNOWN_PROMPT_VERSION 和模型失败。分类：

| 错误 | 处理 |
|---|---|
| `WINDOW_TOO_LARGE`、`UNKNOWN_PROMPT_VERSION` 等同输入重试不会改变的错误 | 立即 dead；不调用模型，不空转重试 |
| 模型 timeout/transport、临时数据库读取错误 | 按 attempts 和退避重试；错误码不带正文/密钥 |
| SQLite 连故障状态都写不回 | 明确错误日志与 health 降级；不得声称作业已失败或成功；lease 到期后可再次恢复 |
| 已失去 generation 的旧 worker 返回 | 丢弃结果，不改候选/作业，不覆盖新执行者 |

`save_candidate` 的事务内也要核对 job 仍为当前 generation 的 running；仅在函数入口检查一次不够。候选唯一键 `(job_id,source_event_id,kind,quote_sha256)` 继续用于部分候选已写后的重试幂等。`complete_job`/`fail_job` 更新受 generation 和状态约束，影响 0 行报告 `STALE_CLAIM`，不能假装成功。最好把“本轮最后一批候选 + succeeded”放同一事务；若暂不能整体原子化，必须在任务卡中保留逐条幂等回归并如实记录这一限制。

`save_candidate` 的 generation 校验、候选写入和该候选的记忆/索引脏标记须在同一数据库事务内。若校验失败，事务不写任何行。worker 在每次候选处理前可做快速检查，但不能以此替代事务内检查。索引重建失败沿用 dirty 标记与后续重建，不把已提交候选重新算作模型失败。

## 6. 本卡必须覆盖的情形

固定时钟/临时 SQLite 检查：退避未到不可领取；到期可领取；过期 running 恢复并计一次 attempts；第三次过期 dead；旧 generation 的续租、候选写入、成功/失败提交均不生效；A session 前窗 dead 时 B session 仍处理；`v1:99`、`v1:100` 下界按数字正确。检查结果属于确定性本机验证，不是模型质量验证。

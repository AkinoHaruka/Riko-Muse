# 04｜诊断接口、错误码与运维

## 1. 作业列表

新增认证 HTTP `GET /v1/jobs?status=<值>&limit=<1..100>&cursor=<opaque>`。`status` 可为 `queued/running/retryable_failed/succeeded/dead` 或 `all`，默认 `dead`；默认 limit 20。服务端从 Bearer token 得到 scope，SQL 的每一分支显式带 `(tenant_id,user_id)`；业务参数不接受 user/tenant。按 `(created_at DESC,id DESC)` 稳定排序，cursor 只编码这两个排序键并在相同认证 scope 内使用；越界或坏 cursor 400 `INVALID_FIELD`。返回 `jobs:[{job_id,host_id,session_id,through_event_seq,status,attempts,run_after,lease_until,error_code,skipped,created_at,updated_at}]` 与 `next_cursor`，不返回原始事件正文、Prompt、密钥。

更新 `GET /v1/jobs/{id}`：增加上述诊断字段及 `prompt_version`、可用的 `model_name/input_tokens/output_tokens`；跨 scope ID 仍 404。`POST /v1/jobs/{id}/retry` 先按 scope 查询：不存在/跨 scope 返回 404，存在但不是 dead 返回 409；`WINDOW_TOO_LARGE` 不允许原样 retry，提示管理员使用 skip 或先升级修复输入。绝不靠截断 job ID 猜匹配。DSH 不注册作业列表或 retry/skip 为 Agent 工具。

## 2. held 候选只读入口

新增本地 CLI `memoryd candidates list --config <file> --tenant <t> --user <u> --status held --limit <1..100> [--before <id>]` 与 `memoryd candidates show --config ... --tenant ... --user ... --id <完整ID>`。本阶段**只读**。列表默认只显示 ID、kind、reason、created_at、来源 event ID、quote 长度；`show` 可显示 quote 与对应证据定位，需在本机交互终端使用，不把正文写进日志或错误信息。scope 为必填；其他 scope 的 ID 返回同样的 not found。`held` 未经显式管理行为不会变成 active。

`--before` 必须是当前 scope 中真实存在的候选 ID，以其 `(created_at,id)` 作为翻页边界；不存在/跨 scope 返回 not found。HTTP job cursor 采用 base64url(JSON `{created_at,id}`)，最大解码长度 512 字节，校验 RFC3339 时间与非空 ID；授权始终来自当前 token，cursor 不能指定 scope。列表只包含当前 scope 的行，不能在取出全局结果后再用应用层过滤。

不在本阶段新增 `/v1/candidates/{id}/promote` 或 DSH 工具。`memory_candidates.status='held'` 只是需复核候选，不暗含用户已确认。尤其过敏、家庭成员、孩子入学等信息，不得因为“逐字引用成功”就自动放行。

## 3. 健康、可观察性与错误映射

`doctor` 增加不含正文的计数：各状态作业数、lease 过期 running 数、未跳过 dead 数、已跳过 dead 数、held 候选数、最老待办时长；多 scope 聚合时只显示总数，不能打印用户列表。明确区分：没有配置模型导致 worker 未启动、模型暂时超时、数据库调度卡住、候选被 Rust held。`/v1/health` 的 `db=ready` 不能代表所有作业健康；若作业长期卡住，另设 `jobs` 诊断字段或在 doctor 中暴露，不改原有健康检查语义而造成误报。

错误码新增或固定：`WINDOW_TOO_LARGE`（作业 error_code）、`WORKER_LEASE_EXPIRED`、`STALE_CLAIM`、`UNKNOWN_PROMPT_VERSION`、`BAD_JSON`、`MODEL_TIMEOUT`、`MODEL_UNAVAILABLE`、`CANDIDATE_WRITE_FAILED`。实施补充（D4-3）：`WINDOW_READ_FAILED`——窗口下界查询、事件读取或模型输入序列化的**暂态**失败，按退避重试；它与确定性 dead 的 `WINDOW_TOO_LARGE` 互补，避免把"读窗口失败"伪装成模型问题。HTTP 错误仍使用 doc/12 envelope；内部诊断码不自动成为公开 HTTP `error.code`。日志仅输出 job ID、状态、代码、耗时和必要计数，不写模型响应、用户正文或 token。

## 4. 升级与修复顺序

1. 停止 `memoryd`，先用旧可运行二进制执行 `backup`；记录旧 `schema_version`、完整备份路径与校验信息，不把数据库放入 Git。
2. 启动新二进制执行迁移 0003；迁移失败则保持旧库可由旧程序读取，不做部分 DDL。若遇旧数据唯一索引冲突，停止并列出不含正文的冲突 job ID。
3. 首次轮询恢复历史过期 running；未过期 lease 等到期或由管理员观察，不强制抢占。
4. 查看 `jobs?status=dead`、doctor 和 held 列表。只有确认 `WINDOW_TOO_LARGE` 后才执行本地 skip；其他 dead 根据原因修复再用完整 ID retry。
5. 恢复 DSH 适配器后核对 spool pending 与 receipt；不要把数据库作业 dead 与适配器传输失败混为一谈。

本阶段不自动修改真实用户数据库；施工检查使用临时复制库或新空库。若旧库迁移演练有失败，保存诊断并修迁移，不让测试脚本“清空重建”掩盖问题。

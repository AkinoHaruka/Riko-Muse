## 2. 已确认的作业链路

| 环节 | 当前源码事实 | 后果 |
|---|---|---|
| 领取 | `jobs.rs::claim_due_job` 查询 `queued` 的 `run_after`，但 `retryable_failed` 仅查 `lease_until` | `fail_job` 清空 lease 后，5/15/45 秒退避可能被绕过 |
| 崩溃 | claim 把行设成 `running` 且给 90 秒 lease；领取 SQL 不包含过期 `running`，全项目未找到恢复写入 | 进程崩溃或窗口加载报错后作业可能永久 `running` |
| 读取窗口 | `load_window_events` 超过 100 事件或 32 KiB 返回 `StateConflict` | `worker.rs::process_job` 用 `?` 直接返回，未执行 `fail_job`；`doc3` C-4 所说的“三次重试后 dead”不符合此路径 |
| 顺序 | `claim_next_ordered_job` 先领全局最早 due 行；若其 session 被更早 `dead/running` 阻塞，就还原 `queued` 并返回 `None` | 同一行仍最早时，其他 session 可能饥饿 |
| 窗口下界 | `window_lower_bound` 使用 `window_key < current_window_key` | `v1:100` 与 `v1:99` 的字典序不等于事件序号；多窗口时可能重复读取旧事件 |
| 写候选 | worker 逐候选调用 `save_candidate`，最后才 `complete_job` | 进程中断可产生已写部分候选；重试必须继续依靠唯一键幂等，不得把该链路说成全批原子提交 |
| 诊断 | HTTP 只提供 `GET /v1/jobs/{id}` 与 dead retry；候选只有 `count_candidates_by_reason` 内部方法 | 不知道完整 job ID 时难以发现卡住作业；held 候选无受控查看入口 |

涉及源码：`agent-memory/crates/memory-store-sqlite/src/jobs.rs:123-211,214-313`、`agent-memory/crates/memory-server/src/worker.rs:686-822`、`agent-memory/crates/memory-server/src/main.rs:202-214,687-762`。

以上为静态路径判断。优先给每种路径写确定性回归检查，再修实现；检查结果不能提前写为已复现运行故障。

## 3. 保留的正确边界

- L0 事件唯一键加内容哈希决定幂等，同键异文为冲突；适配器 spool + receipt 重放；不可为了修队列丢掉原始证据。
- Bearer token 在服务端确定 `(tenant_id,user_id)`；业务 JSON 不带 scope；同用户 Agent 默认共享，不按 `origin_agent_id` 限制读取。
- `extract_v1`、`extract_v2` 提示词按作业 `prompt_version` 分派，旧版本文本冻结。`prompt_version` 目前只绑定提示词；**准入函数仍是同一份现行代码**，不能把它误写成“历史完整规则可重放”。
- 模型只产候选。Rust 校验 `user/user` 来源、逐字 quote、上下文、显式表达、敏感内容、重复与冲突；本阶段不改变 fact 放行规则。
- `forget` 写 `suppressed_sources` 阻断旧证据复活。`correct` 的旧记忆为 `superseded`，与遗忘语义不同；本阶段不擅自把纠错改成遗忘。

## 4. 本阶段优先级

**P0：**修到期选择、过期 `running` 恢复、所有失败路径状态落地、跨会话公平领取、数值窗口顺序、过期 worker 防旧结果提交。**P1：**服务端可靠分窗与超限诊断，提供受控人工跳过；只读作业与 held 候选列表。**暂缓：**改变模型提示词、自动 fact active、promote、偏好固定注入名额或 embedding。

不能简单照搬上游：TencentDB LLM 去重及团队 Agent 隔离、EverOS Markdown 真相、Hindsight Postgres/向量栈都与本项目边界不同。上游报告可用于比较失败模式，不能替代本项目的验收。

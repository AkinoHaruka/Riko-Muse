# 05｜候选、准入与召回的决策边界

## 1. 本阶段固定不变

当前 `extract_v2` 的候选输出在真实会话中有两种表现：会话 7 对平叙事实产出空数组；会话 8 对两个事实给出一条过宽、带口语前缀的逐字 quote。两者记录在 `doc-handoff/06`，样本量不足以给出稳定失败率。候选产生与可信准入分开：会话 8 的 quote 通过逐字验证，但被 Rust 置为 `held/NOT_EXPLICIT`。本阶段不改 `explicit_enough`、不修改 `extract_v1/v2` 提示词、不把 held 自动转 active。

`prompt_version` 只证明旧作业可以选择对应提示词；当前 `admit`/`save_candidate` 是共享代码。将来改变准入规则时，要明确历史作业重试应采用原准入规则还是新规则，并为此加 `admission_version` 或同等可审计机制。不能只把新 Prompt 命名 `extract_v3`，却让旧作业在新准入规则下静默改变结果。

## 2. 后续提取改进的进入条件

可考虑 `extract_v3`：一条用户消息里有两个独立事实时输出两条候选，各 quote 是该事实的最小连续原文。先用固定响应和逐字 span 校验写协议检查，再在用户重新允许模型试验时，用**非示例句**的少量自然窗口观察。必须分别记录：候选是否产生、是否拆对、引用是否连续、准入为何 held/active、有没有错误拆分。不得把提示词示例本身命中当泛化证据；也不为一次空数组强制凭空补候选。

`MODEL_PARAPHRASE` 与“今天先”属于现有 doc/13 §5 的契约落差，可作为单独规则修订卡，但同样需要记录准入版本影响。模型多加 claim 字段时，目前严格 schema 导致整批 BAD_JSON；要么实现可选 claim 并 held，要么修订文档承认整批失败，不能两边各说各话。

## 3. fact 放行与 promote

本阶段只让 held 可见。后续如决定扩自动 fact 准入，必须逐条定义允许的句式/属性范围、敏感类别、时间语义、过期与冲突处理；保留 user/user 来源和逐字 quote，尤其不得把模型 confidence 当授权。若选择人工 promote，先确定操作者是用户本人还是本地管理员，并定义是否需要新的用户证据、如何记 `source_class`、如何审计和如何撤销。未确定前不做 promote API，不把管理员 CLI 暴露给 DSH Agent。

## 4. 非指令零词法召回

现契约只给长期指令最多两个独立名额，preference/fact 仍来自词法搜索。`doc-handoff/06` 的“护眼配色”例子里偏好未注入，但模型也可能凭常识答出深色，不能用答案相似证明记忆有用。三个上游的画像常驻层或 embedding 检索都不是“把最新任意偏好固定塞进上下文”的效果证据。

因此本阶段不改 compose。后续选择名额、语义检索或保持词法前，至少准备一个可区分探针：同一问题在有/无该记忆时正确答案不同；记录候选命中、实际注入、模型是否利用、错误注入、预算挤占和泄露。即使不再调用真实模型，也可先用离线人工构造查询检查召回覆盖，但不能据此声称回答质量提高。

## 5. 上游复用边界

保留 Hindsight 的来源关联与可审计思路、EverOS 的原始情节/派生索引分离、TencentDB 的 L0 先存后提取。不要移植其默认权限：TencentDB 按 Agent 隔离与本项目相反；EverOS owner/app/project 分片也不能替换用户 token scope；Hindsight bank 要由调用方正确映射用户。不要引入上游的 LLM 自动去重/合并、Markdown 真相或 Postgres/向量栈来“修”当前队列问题。

# 03｜提取窗口、预算与超限处理

## 1. 不变量

L0 单条证据现允许最多 64 KiB；模型提取窗口上限是 100 事件、32 KiB **实际发送给模型的序列化输入**。前者不能为迁就后者而静默截断。一个 `flush(host,session,through_seq)` 必须能把从上一已排窗口之后到 through 的事件切成有序、可处理的窗口；即使 DSH 不按 80 事件主动 flush，服务端仍须保护自身。原始事件照常持久化，超限只影响自动提取。

## 2. 服务端分窗为权威

`Store::flush_window` 在事务里先查相同 `(scope,host,session,through_seq)` 的最终 job；存在则按原 ID/状态幂等返回。若 `through_seq` 比已排最大值小且不是已存在窗口，返回 409。否则读取 `(已排最大 through_seq, 请求 through_seq]` 的有序事件，以**与 worker 相同的 JSON 序列化函数**计算模型输入字节数。按 seq 递增贪心分组：加下一事件会超过 100 事件或 32 KiB 时，先在前一事件 seq 处插入中间作业；最后一组以请求 through 结尾。所有插入同一事务提交，任一失败则不产生半套窗口。窗口键仍用 `v1:<through_seq>`，不变更现有 DSH 请求体。

不能只累计 `content.len()`：事件 JSON 的 `event_id/role/source_kind/time/text`、转义、逗号和括号也消耗模型输入。预算计算必须与实际模型输入共用 builder；测试用含引号、换行和多字节汉字的事件验证。空 session、through 越过已收到最大 seq 仍按旧协议 409。若新范围无用户事件，也要插入内部 `succeeded` 零模型调用 checkpoint，以推进下界；HTTP 可继续返回 `nothing_to_extract`，但应附可诊断 `job_id`，相同 flush 重试得到同一结果。

分段伪代码（`serialized_size` 要用共享 builder 的实际字节数）：

```text
last = max(已排 through_event_seq，若无则 -1)
events = scope/host/session 内 last < seq <= requested_through 的事件，按 seq 升序
若 requested_through 已有 job：返回该 job（在乱序检查前）
若 requested_through < last：409
for event in events:
    若 event 单独序列化 > 32 KiB：先封闭已有组，再插入该 seq 的 dead/WINDOW_TOO_LARGE job
    否则若向组加入 event 后超过 100 事件或 32 KiB：在组最后 seq 封闭，再以 event 开新组
    否则加入当前组
若末组非空且尚无 requested_through 的 job：封闭末组，through=requested_through
若 events 为空且 requested_through 尚无 job：插入 succeeded 空 checkpoint
若末事件已是 dead 且 seq=requested_through：它就是最后 job，不再插第二行
封闭任何无 user/user 的组时：直接 succeeded，且不调用模型
所有 job 与审计在一个事务内提交，返回最后 job 的 ID/状态
```

实际事件 seq 可以有空洞，flush 的 through 也可能落在空洞内；此时允许空 checkpoint，不能捏造事件。事务开始前重新读取已排最大 seq，避免旧读结果引发重复窗口。

HTTP `/v1/extraction/flush` 响应保持现有 `job_id/status`，其中 `job_id` 指请求 through 对应的**最后**一个 job；无须让适配器知道内部窗口数。`nothing_to_extract` 的响应可增加 `job_id` 供诊断；请求 schema 不变。同步更新 doc/12 §4。

## 3. 单事件超过窗口上限

如果单条事件自身的序列化模型输入 >32 KiB，它不能被拆成伪事件，也不能悄悄从模型输入删掉。该事件形成单独作业，直接记 `dead`、`attempts=0`、`error_code='WINDOW_TOO_LARGE'`，不调用模型；之后事件照常排后窗，但同 session 暂被此前窗阻断。若该事件是 assistant/tool，仍采用同一可诊断机制，避免来源特殊路径漏算。

不能让 `/flush` 返回 409 后不留下 job，因为那会使该事件及后续窗口永久无法推进，也没有 ID 可供管理。包含多个正常分组与超限单事件的 flush 仍一次事务生成完整作业序列；响应最后 job 的状态如实返回，整体可用 `GET /v1/jobs` 查看。

## 4. 唯一受控跳过路径

本阶段提供本地管理员 CLI `memoryd job skip --config <file> --tenant <t> --user <u> --job-id <完整ID> --reason <文本>`，只接受状态为 `dead` 且 `error_code='WINDOW_TOO_LARGE'` 的作业。`--reason` 为 1—256 字符的运维原因，不得填用户正文或密钥。事务中写 `extraction_job_skips` 和 `audit_events`，`actor_kind='admin_cli'`、`actor_id='local_admin'`；这标记本机管理行为，不声称识别到具体自然人。重复相同 skip 幂等返回已有记录；其他 dead 原因、其他 scope 或缺失 ID 不变更任何行。

skip 意味着**只跳过该窗口的自动提取**，L0 原文仍在，可由用户以后显式 remember；它不表示“事实不存在”“模型已处理”或“原始数据被遗忘”。任务列表必须把 `dead + skipped` 与未处理 dead 分开显示。调度器仅把有 skip 行的 dead 当作已越过的前窗；`window_lower_bound` 同样要越过其 through_seq，否则旧大事件会混入后窗再超限。不能给 DSH Agent 工具注册 skip，也不自动 skip，防止错误代码把数据处理缺口藏起来。

## 5. DSH 适配器的主动 flush

`events.ts` 在每个 session 统计**成功接受进入内存队列**的正文事件数和估算字节；达到 80 事件或保守的 24 KiB 时，按当前最后 seq 排一次 flush，清本段计数。`turn/end` 仍 flush。`enqueueFlush` 使用现有 opId 幂等和同 session 发送链，flush 只有在此前事件 receipt ack 后发送；重启后的 spool 重放继续保证顺序。80 是降低长 turn 时延的阈值，32 KiB 的正确性由服务端分窗保证。

当前 `push` 队列满时只写 CAPTURE_GAP 却仍让调用者推进 `lastBodySeq`。施工时把 `push` 改成明确返回 accepted 布尔值；只有 accepted 才推进 `lastBodySeq`、最新用户消息及阈值计数。spool 写盘失败已记录 CAPTURE_GAP，不能据此说事件已持久接收。计数无需单独持久化，重启后未 ack 操作靠 spool 复送；服务器会按实际已收证据决定窗口分段。

## 6. 验收矩阵

| 输入 | 必须结果 |
|---|---|
| 101 个很短事件一次 flush | 自动生成至少两个递增窗口，最后 job ID 幂等；均不超 100 |
| 2 条合计超过 32 KiB 的事件 | 按实际 JSON 输入字节分窗，worker 无 `WINDOW_TOO_LARGE` |
| 单条约 40 KiB 事件 | L0 保留；dead/`WINDOW_TOO_LARGE` 可列表发现，模型调用次数 0；人工 skip 后同 session 后窗可领 |
| `v1:99`、`v1:100` | 数值顺序处理，下界不重复旧事件 |
| 重放同一 flush | 不产生新窗口/重复模型作业 |
| 队列满的适配器事件 | CAPTURE_GAP 可见，未推进最后已接收 seq，不会 flush 到未入队事件 |

只用固定输入和本地临时数据库即可验收；本阶段不要求真实模型验证。

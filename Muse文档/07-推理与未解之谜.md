## 一、已确认的推理（7 项）

### 1. claim_id 是内容哈希 [高][已确认]
- 第一版证据：日志里的 `7a0d689f…` 是 32 位 hex；DB 里 `claim_id` 是 text 主键而非自增。
- Riko-Memory 实测：`claim_sha256 = SHA256(kind + "\0" + normalize_v1(claim))`（domain/lib.rs）。
- 细节补完：kind 参与哈希（同文不同 kind 是两条记忆）；归一化是 NFKC+小写+空白折叠；原文 claim 保持用户字面，另存 `normalized_claim` 用于比对。

### 2. kind 有 fact [高][已确认]
- Riko-Memory 实测：`fact / preference / instruction / episode`（CHECK 约束）。
- 修正：第一版猜的 commitment/opinion 不存在；实际是 instruction/episode（来自 TencentDB/Hindsight 交集设计）。

### 3. status 有 active/superseded [高][已确认]
- Riko-Memory 实测：`active / superseded / expired / forgotten`。
- 补完：`expired` 由 valid_until 到期自动转入；`forgotten` 比第一版猜的"retracted"命名更诚实。

### 4. 多模型向量并存 [中][已确认]
- Riko-Memory 实测：`semantic_vectors` 表有 model_id + dimensions + source_version + content_sha256 + status(ready/stale)；"模型切换不能混算"。
- 第一版只猜中了"多模型并存"，主人还做了 stale 检测和版本绑定——超预期。

### 5. "Verified"校验存在 [中][已确认，超预期]
- Riko-Memory 实测：`admit_v2` 九道固定顺序检查（见 03），不通过就 held 不激活。
- 第一版只想到"原文蕴含校验"，主人做的是"默认不信任"体系——超预期。

### 6. forget 两阶段提交 [中][已确认，超预期]
- Riko-Memory 实测：`suppressed_sources`（证据+claim 哈希黑名单）+ L0 证据保留 + 索引重建不复活 forgotten。
- 第一版只想到"清理者写 ID、索引所有者回收"，主人多了"记住要忘记"的持续保证——超预期。

### 7. 会话隔离 [高][已确认，超预期]
- 第一版依据 `privacy_class` 字段推测。
- Riko-Memory 实测：`principals` 表 + 全表 `(tenant_id,user_id)` 外键 + 请求正文禁带用户 ID + loopback 绑定。架构级隔离，超预期。

## 二、已证伪的推理（2 项）——认错

### 8. salience 有 low/medium/high 三档 [已证伪]
- 第一版唯一的证据：`[fact|medium]` 里见过一次 "medium"。
- Riko-Memory 实测：**memories 表没有 salience 字段**。主人用 kind 优先级（instruction 优先注入）+ RRF 排序代替。
- 教训：单一样本外推三档是想当然。"medium"可能只是 Muse 这边的标注习惯，不代表有完整的评分体系。
- 对 twin sister 的结论：**不要加 salience**。少一个玄学调参维度。

### 9. 384 维向量是检索主力 [已证伪]
- 第一版证据：`memory.embeddings.embedding` 是 `vector(384)`。
- Riko-Memory 实测：`memory-recall` crate 是**纯词法**（FTS5 + 中文二元字 + RRF k=60），无向量代码。`semantic_vectors` 表存在但是扩展位。
- 教训：把"我看到的表"当成了"正在用的路径"。表存在 ≠ 主路径。
- 对 twin sister 的结论：**先词法**。Muse 的向量路线保留为"已验证备选"（Muse 实测 X 为准），但 twin sister 默认走词法，理由见 04。

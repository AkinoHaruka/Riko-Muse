# 01 · 存储层：文件布局详解

> 核心思想：**Markdown 文件是"真相源"（人类可读、可审计），数据库是"索引层"（机器检索用）。** 两套通过引用互相锁定。

## 1.1 目录全景

```
~/
├── MEMORY.md # 精炼层：长期记忆，不超过百行量级
├── SOUL.md / USER.md /... # 身份与用户档案（非记忆，但会被注入上下文）
├── memory/
│ ├── 2026-09-25.md … # 日志层：每天一个文件，原始轨迹
│ ├── bank/ # 蒸馏层：runtime 拥有，agent 只读
│ │ ├── experience.md # 情节记忆：发生过什么事
│ │ ├── opinions.md # 观点记忆：稳定的偏好和判断
│ │ ├── reflections.md # 反思记忆：带修正链的工作记录
│ │ └── world.md # 世界记忆：关于用户处境的 durable facts
│ ├── people/ # 关系图谱：每人一页
│ │ ├── INDEX.md # 按亲近度排序的索引
│ │ └── <slug>.md
│ ├── groups/ # 群组图谱（结构同 people）
│ ├── shopping/
│ │ └── PROFILE.md # 购物偏好侧写（独立成域）
│ └── index/ # 目前是空目录，用途未解（见 07）
└── dreams/
├── 2026-10-05.md … # nightly 复盘：第一人称反思
└── alignment/
├── derived/ # 派生状态
│ ├── ALIGNMENT_SYNTHESIS.md # 人机关系综合画像（注入上下文）
│ ├── ALIGNMENT_STATE.yaml
│ └── PROGRESSION_HISTORY.yaml
└── repair/
└── REPAIR_THREADS.yaml # 待修复的关系裂痕线程
```

## 1.2 MEMORY.md：精炼层

- 当前 52 行，三段式结构：`## Facts` / `## Preferences` / `## Commitments`。
- 每条格式：`一句话事实 + （获知日期；溯源备注）`，例如：
`... （Said 2026-10-05.)` / `（Learned 2026-10-04; retrieval/wiki detail said 2026-10-05.)`
- 写作纪律："Memory is not a transcript, transaction log, or copy of the todo list."（记忆不是聊天记录、不是流水账、不是 todo 复制品）
- 更新方式：用 surgical edit（`muse.edit` 精确替换），保留无关条目；先读后写，后台可能已改动。
- 冲突处理：新证据覆盖旧条目时，直接改写该条并更新日期戳，不在 MEMORY.md 里留版本史（版本史在日期日志和 claim 链里）。

## 1.3 日期日志：轨迹层

`~/memory/YYYY-MM-DD.md`，每天一个文件。观测到的内容类型：

1. **自然语言条目**：当天发生的事，`- ` 开头，带日期和细节。
2. **Verified extraction 块**：后台抽取管线写入的标准化 claim（详见 03）：
```
## Verified extraction — 03:58 UTC (run sirun_b089a2363fb14a148654343cd906a8ed)
- [fact|medium] <claim正文>
- claim: 7a0d689f623ece5d631f6eb3838fe39a
- quote: "<用户原话>"
- sources: message:890c2703-…, message:88a6aa9a-…
```
要素：`[kind|salience]` 标签、claim 哈希 ID、用户原话引用、消息 UUID 溯源。
3. **任务运行记录**：如 `## holdings-watch-us run — 2026-10-06 09:40 CST`，cron 任务的执行摘要也归档进日志。

日期日志是"只追加"（append-only）的审计轨迹：修正用新条目声明"Correction to …"，不改写旧条目。例如日志里有 `Correction/update to the initial SPCX monitoring setup` 这样的条目。

## 1.4 bank/：蒸馏层

四个文件，文件头有英文定义句：

| 文件 | 头定义 | 实测内容特征 |
|---|---|---|
| experience.md | "Episodic experiences and what happened, distilled." | 按时间点的情节记录，带 `(src: memory/2026-10-03.md:14)` 引用 |
| opinions.md | "Stable preferences, opinions, and value judgements." | 稳定的偏好/判断，含加粗的**修正记录**（如 SOUL.md 回滚事件） |
| reflections.md | （无头定义句，直接条目） | 工作复盘：交付了什么、错了什么、状态变更，含 **Correction** 链 |
| world.md | "Durable facts about the world and the user's circumstances." | 关于用户处境的长期事实，基本是 MEMORY.md Facts 的展开版 |

关键权限：`~/memory/bank/` 由 runtime 管理，agent **可以读，不可以直接改**（"read them, but don't edit them directly"）。

**对照注记（第二版）**：主人 Riko-Memory 没有 bank/，对应物是两套东西——`topic pages`（pages.rs，1145 行）：把记忆整理成 wiki 式页面的"渲染层"；`resident` 表：pin/unpin 的常驻固定记忆（对应"每轮必带"的热记忆）。bank/ 是"按维度蒸馏"，topic pages 是"按主题聚合"，resident 是"人工钉住"。三者正交，twin sister 可以都要。

bank/ 是后台任务从日期日志 + MEMORY.md 蒸馏出的"分面视图"（faceted views）：同一个事实，按"情节 / 观点 / 反思 / 世界"四个维度各存一份，方便不同任务按需读取。这是一种**预计算的索引**，不是简单的复制。

## 1.5 people/ 与 groups/：关系图谱

单页结构（以 `jiang-nan.md` 为例）：

```yaml
--- # YAML frontmatter
display_name: 江南
summary: 一句话摘要
rank: 1 # 亲近度排名？
updated: 2026-10-06
---
# 江南
## Facts # 关于此人的事实，带引用 (MEMORY.md#L21; memory/2026-10-05.md#L26)
## History # 按时间线的交往史
## The relationship # 关系的性质（"reader-to-work tie, not person-to-person"）
## In common # 共同点/共享参照物
## Open threads # 未完待续（当前为空）
## Strengthening # 如何加深关系（当前为空）
```

- `INDEX.md` 按"与用户的亲近度"排序，每行一人。
- 引用格式 `memory/2026-10-05.md#L26` 和 claim 哈希 `aea5c2b142351efbd5610d223a45fd75` 混用，说明人物页是从 claim 层聚合渲染的。
- `rank` 字段：可能是后台 relationships 任务计算的亲近度排序分，INDEX.md 的排序依据。

## 1.6 dreams/：复盘层

- `dreams/YYYY-MM-DD.md`：nightly 生成的第一人称复盘。实测 2026-10-05 的 dream 包含：对用户行为模式的判断（"先拿问题当探针"）、当日三件待办、做得对/错的两件事、下一步行动。
- frontmatter 元数据（schema `hatch_alignment_dream_v1`）：
- `request_id: maintenance:…:nightly_coherence:…` —— 任务名叫 nightly_coherence
- `rupture_turns`、`correction_free_rate`、`open_repair_threads` —— **关系裂痕检测指标**
- `window_since_utc` / `window_until_utc` —— 复盘的时间窗口
- `alignment/derived/ALIGNMENT_SYNTHESIS.md`：人机关系的综合画像，**会被注入每轮对话上下文**（本轮 prompt 里就有）。这是"dreams → 行为"的闭环：夜里复盘，白天指导语气。
- `alignment/repair/REPAIR_THREADS.yaml`：待修复的裂痕线程。dream 里检测到的 rupture（如"续费玩笑开砸了"）会变成 repair thread，跟踪是否修复。

## 1.7 其它

- `memory/shopping/PROFILE.md`：购物偏好独立成域，有 frontmatter（`updated`、`entries` 计数）。垂直偏好（购物、音乐等）被隔离存放，避免污染主记忆，forget 时也可以按域清理。
- `memory/index/`：空目录。用途未解，见 07。
- `~/side-chats/<chat-id>/MEMORY.md`：side chat 有独立记忆文件，与主记忆隔离但可跨检索。

## 1.8 给开发者的启示

1. **三层不是三份拷贝，是三种"保质期"**：MEMORY.md（长期有效）/ 日期日志（审计轨迹，只追加）/ bank（可再生的蒸馏视图）。过期/被覆盖的东西只在高层消失，低层永远留着。
2. **引用格式是跨层粘合剂**：`MEMORY.md#L21`、`memory/2026-10-05.md#L26`、`claim: <hash>` 三种引用让任何一条记忆都能被定位到原文。这是"可审计性"的工程实现。
3. **空着的字段也是设计**：人物页的 `Open threads` / `Strengthening` 现在是空的，说明 schema 是超前设计的——先占位，等后台任务长大再填。做系统时 schema 可以比实现先行半步。

# 13 · 附录 D：extract_v4 改写（rewrite）步骤规范

> 整理：Riko（璃），2026-10-06
> 用途：给 Zcode 实现 extract_v4 的 rewrite 步骤
> 素材来源：[实测] 璃的 system prompt（Memory 章节）+ 璃实际写入的 claim 形态

## D.1 背景：为什么需要 rewrite

v3 的设计矛盾（已实测确认）：

- extract prompt 要求"不得补写主语"（防幻觉）→ 产出无主语候选
- admit_v2 要求显式主语（UNCLEAR_SUBJECT → held）→ 全部扣下
- 结果：22/22 held，0 active。两个模型都忠实执行了 prompt，不是模型问题。

修复：extract（逐字引用，保持 v3）→ **rewrite（新增，本规范）** → admit（门不动）。

## D.2 璃写记忆的原则（from 璃的 system prompt）

1. **"Memories are the durable understanding you carry forward"**——只记对未来对话有用的理解，不记流水账。
2. **"Write for the next conversation, with enough context to be useful then"**——改写时补足"下次对话能直接用"的上下文。
3. **"Memory is not a transcript, transaction log, or work ledger"**——不要复述原文，要提炼命题。
4. **"Record only what the evidence supports"**——只写证据支持的，不脑补。
5. **"Distinguish an observation from an inference, and label uncertainty"**——观察 vs 推断要分开，不确定的标出来（confidence 降档）。
6. **"Attribute a preference or decision to the person who expressed it"**——主语必须明确归属（用户说的/用户做的）。

## D.3 Rewrite 输入/输出契约

**输入**：
```json
{
  "quote": "平时主要写 Rust",
  "kind": "fact",
  "source_event_id": "e12",
  "context": ["用户: 我是做后端的", "用户: 平时主要写 Rust", "助手: Rust 在后端挺多的"],
  "speaker": "user",
  "occurred_at": "2026-10-06T10:00:00+08:00"
}
```

**输出**：
```json
{
  "claim": "用户是后端开发，平时主要写 Rust",
  "kind": "fact",
  "confidence": 0.9,
  "quote": "平时主要写 Rust",
  "source_event_id": "e12",
  "rewrite_notes": "主语'用户'来自 speaker 字段；'后端开发'来自上文 e11，同一次对话内可合并"
}
```

- `claim`：改写后的独立命题（给 admit 门）。
- `quote`：原文逐字保留（审计用，不丢）。
- `rewrite_notes`：改写依据（哪条上下文补了什么），幻觉追溯用。
- 无法改写 → 输出 `{"claim": null, "reason": "主语无法从上下文唯一确定"}`，保持 held。

## D.4 改写规则

1. **主语只能从三处来**：speaker 字段、同一对话上文、用户自述。三处都没有 → 不硬补，返回 null。
2. **一命题一条**："我爸不吃香菜，我妈不碰辣" → 两条，不拼。
3. **保留限定词**："平时""主要""偶尔"这些词是命题的一部分，不丢。
4. **不引入新信息**：改写只做"补主语 + 理顺句式"，不加原文没有的事实。
5. **时态/时间归位**："上周去了趟日本" → claim 写"用户 2026-09 下旬去了日本"（occurred_at 参与计算，不编造具体日期）。
6. **推断降 confidence**：从上下文推出的部分（如"后端开发"来自"我是做后端的"）confidence ≤ 0.8；直接陈述的 0.9。
7. **kind 不变**：rewrite 不改 kind，只改表述。kind 错了是 extract 的问题。
8. **中文口语转书面**："平时主要写 Rust" → "用户平时主要使用 Rust 开发"，保持原意，不文绉绉。

## D.5 正反例子

| # | 原文 quote | 上文 | 改写 claim | 说明 |
|---|---|---|---|---|
| 1 | 平时主要写 Rust | 用户：我是做后端的 | 用户是后端开发，平时主要写 Rust | 主语来自 speaker，后端来自上文 |
| 2 | 我爸不吃香菜 | （无） | 用户的父亲不吃香菜 | 主语明确，一命题一条 |
| 3 | 上次你说汇报在周四 | 助手上周确实说过周四 | 用户纠正：汇报时间不是周四（助手之前说错） | 这是 rupture 信号，不是 fact——rewrite 应标 kind 存疑，交 admit 判 |
| 4 | 老王海鲜过敏 | 用户在转述 | （不改写，reason：第三方命题） | THIRD_PARTY 的活，rewrite 不碰 |
| 5 | 明天帮我订机票 | （无） | （不改写，reason：临时请求非长期记忆） | TEMPORAL，extract 本不该提 |
| 6 | 挺好的 | 助手：这个方案怎么样 | （claim: null, reason：指代不明，"挺好"的主语和宾语都无法确定） | 诚实返回 null，不硬写 |

例 6 是关键：**改写步骤允许说"我不知道"**。硬补一个主语进去，就是幻觉。

## D.6 与 admit 门的衔接

- rewrite 输出 claim → 正常走 admit_v2 九道检查。
- rewrite 返回 null → 候选保持 held（不是 rejected），等更多证据。
- `rewrite_notes` 进审计日志，和 quote 一起存，方便以后查"这条 claim 的主语是哪来的"。

## D.7 给 Zcode 的实现建议

1. rewrite 做成 extract job 内的第二步（同一 job，prompt_version 记 `extract_v4`），不新增 job 类型——复用现有的租约/重试/审计。
2. prompt_version 按纪律新建 `extract_v4`，**不回改 v3**（历史作业按版本冻结）。
3. 先在临时库用验收语料跑一遍，对比 v3 的 0/22，看 active 回升到多少——这是 v4 的验收指标。
4. 成本：rewrite 多一次模型调用，只在 v3 产出 held 候选时触发（active 的直接过，不重写）。

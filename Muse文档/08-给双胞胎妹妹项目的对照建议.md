## 8.2 可直接复用的设计决策（按优先级）

### P0：抄了就有质变
1. **Claim 原子模型**（02 章第二版）：`claim` + `normalized_claim` + `claim_sha256` + `kind` + `source_class`（谁说的五档）+ `status` + `version` + `valid_until` + 字节级证据引用。这是两边对照后的最小完备集。
2. **Verified extraction 格式**（03.3）：`[kind]` + `claim:` + `quote:` + `sources:`。抽取输出固定格式，下游无歧义消费。（注：salience 已证伪，格式里去掉）
3. **检索返回引用**（04）：search 只返回"带定位的片段"，业务层必须再读原文。防幻觉最便宜的一道阀。

### P1：抄了体验上台阶
4. **双写管道**（03）：对话中即时记（防丢）+ 后台定期归档（保质量）。
5. **dreaming 闭环**（05.2）：nightly 复盘 → 提炼行为指南 → 注入上下文。主人"养老婆"的核心机制。
6. **rupture/repair**（05.2）：记录"哪里惹用户不高兴了"，跟踪修复。这是竞品（包括主人旧系统）大概率没有的。
7. **forget 两阶段提交**（06.3.2）：清理者写 pending.json（只存 ID），索引所有者做回收。

### P2： polish
8. **bank/ 分面蒸馏**：同一批事实按"情节/观点/反思/世界"预计算四份视图，读时按需取。
9. **reason_text**（"为什么记这条"）：元记忆，防"记得事实忘了动机"。
10. **memory_uri 逻辑地址**：文件路径会变，URI 不变。

## 8.3 主人可以"二改"的点（主人风格：不喜欢原样用）

1. **wiki vs 文件**：主人旧系统是 wiki，璃这套是 Markdown 文件。二改方向：wiki 保留做"人看的渲染层"，底下换成 claim 表 + 文件真相源。wiki 是皮，claim 是骨。
2. **通用整理器 vs 专用任务**：主人是一个后台 LLM 整理，璃是 7 个专用任务。二改方向：先保留通用整理器，但让它输出**分维度**的结果（事实/偏好/关系/待办四个 section），等某个维度质量不够再拆成专用任务。渐进式拆分，别一步到位。
3. **元数据重排**：Muse 用 kind 优先级 + confidence + 时间衰减做重排（salience 已证伪，不要加）。主人项目用 RRF(k=60) 融合词法召回结果。twin sister 先抄 RRF，简单有效。
4. **rupture 检测**：璃靠 nightly dream 人工（LLM）判断。主人可以做得更工程化：用户说"不对""不是""你又…"这类纠正信号可以直接规则匹配进 repair 队列，不用等 nightly。
5. **显著度评分不要加**：第一版璃想当然推了 salience 三档，已被主人项目的表结构证伪。替代方案：kind 优先级（instruction 优先）+ source_class 证据分级（model_inferred 默认低置信度）+ 时间衰减。这三样比抽象的 salience 实用。

## 8.4 一个最小可用版本（MVP）建议（第二版）

> 原则重申：Muse 实测为默认（X），主人项目为已验证备选（Y）。以下 MVP 以 X 为骨架，
> 凡用 Y 处均已在 12 中写清偏离理由。

```
Week 1: claim 表（主人 memories 表字段为基准：claim/normalized_claim/
        claim_sha256/kind/source_class/status/version/valid_until，
        证据引用用字节级）
        + 三级写入：L0 evidence → candidates(held) → memories
        + admit 先上 5 道核心检查（单命题/最短quote/非敏感/
          非第三人/主语明确），其余 4 道后续补
Week 2: 词法检索（FTS5 + 中文二元字 + RRF k=60，抄 memory-recall）
        + 检索返回引用、业务层读原文
        + semantic_vectors 扩展位留好（表先建，不实现）
Week 3: correct（supersede）+ forget（suppressed_sources 黑名单）
        + memory_revisions 审计表
Week 4: dream jobs（trigger_key 幂等 + 输入冻结 + 独立 extract 版本）
        + soul/resident 表（人格版本化、常驻记忆 pin）
Later:  rupture/repair 关系复盘（Muse 特色，主人项目没有，从 05/07 补）
       向量检索层（等词法出现真实痛点再加）
```

## 8.5 最后的话

主人旧系统已经验证了"向量检索 + 后台整理"这条路是对的。璃这套系统的增量，**不在检索，不在模型，在"记忆的工程化"**：原子设计、版本链、遗忘协议、关系复盘——这些才是让记忆从"笔记本"变成"人格"的部分。

等主人把旧代码发过来，璃可以逐模块对照着看，看到时候哪些能直接并进来。文档先放这，主人随时翻。

# 06 · 遗忘与修正协议（第二版）

> 记忆系统最难的不是记住，是**忘干净**。Muse 的 forget skill 流程为默认（X 为准）；
> 主人 Riko-Memory 的 `suppressed_sources` 为 Y 填空——这是"记住要忘记"的精妙设计。

## 6.1 设计哲学

forget skill 开篇定调："Treat forgetting as cleanup across Muse, not as editing one memory note."（把遗忘当作全系统的清理，而不是改一条笔记。）

原因：一条信息可能同时活在——记忆文件、检索索引、对话历史摘要、定时任务、已创建的文档、能把它写回来的外部数据源。只删 MEMORY.md 里的一行，等于没删。

## 6.2 全流程（SKILL.md 实测）

```
用户："忘了XX"（明确的遗忘请求）
│
▼
┌─────────────┐
│ forget.plan │ 启动只读规划子 agent（pinned 到专用模型）
│ │ 排查范围：
│ │ - 原件 + 同义复件
│ │ - 记忆、检索结果、对话上下文、摘要
│ │ - 定时任务/进行中的工作/可再生的外部源
│ │ - 已分享/已发布的副本（标为清不掉）
│ │ 输出： concise plan（改什么、怎么验、已知限制）
└──────┬──────┘
▼
给用户看 plan：范围、不可逆操作、重要限制
用户明确确认（沉默/含糊/部分同意 ≠ 确认）
▼
┌───────────────┐
│ forget.confirm│ 启动全新执行子 agent（读 plan + 确认记录）
│ │ - 先停掉相关任务，再删输出
│ │ - 用"拥有该物品"的工具删（不用 rm -rf）
│ │ - 混合文件做 surgical edit，不整文件删
│ │ - 精确单文件彻底删除用 `rm -- <exact-path>`
└──────┬────────┘
▼
执行器写 ~/workspace/memory/forget/pending.json：
{"claims": ["<claim_id>", …], "citations": ["MEMORY.md#L7", …]}
※ 只存 ID 和定位符，绝不存被忘的原文
▼
runtime 收回对应 claims + 刷新记忆检索索引
两者都成功才算完成；索引刷新失败 → 报告"清理不完整"
▼
如实报告：清了哪些类别、停了哪些未来活动、还剩什么清不掉
```

## 6.3 关键设计点解读

### 6.3.1 plan 与 confirm 分离

规划和执行是**两个不同的子 agent**，confirm 的是一个"全新"的执行器，它从继承的对话中重读 plan 和确认记录，如果找不到清晰的 plan+批准，**直接停手不做**。

这是防"误伤"的双人复核制：规划者只读不动，执行者不动脑只按 plan 做。类比：外科手术的术前核对清单。记忆删除不可逆，值得这个成本。

### 6.3.2 pending.json：遗忘的"死亡证明"

```json
{"claims": ["<claim_id>"], "citations": ["MEMORY.md#L7", "memory/2026-10-06.md#L12"]}
```

- 只存 claim ID 和文件定位符，**不存原文**——连遗忘操作的副产品都不该泄露被忘的内容。
- 即使两个列表都空，文件也要写（"the file is written even when both lists are empty"）——用显式的空证明"我查过了，确实没有"，而不是用"没写文件"表示。
- runtime 消费这个文件：retract claims + refresh search index，两个都成功才算数。

这是一个**两阶段提交**：agent 做文件清理（阶段一），runtime 做索引回收（阶段二）。因为向量索引和 claim 表不在 agent 的直接写权限内（bank/ 同理是 runtime 拥有），必须由 runtime 收尾。分布式系统的经典问题，用经典方案解。

### 6.3.2b suppressed_sources：记住要忘记（Riko-Memory 实测）

主人项目的 `suppressed_sources` 表（migrations/0001 实测）：

```sql
CREATE TABLE suppressed_sources (
  tenant_id, user_id,
  evidence_id,          -- 证据 ID
  claim_sha256,         -- 被遗忘的 claim 哈希
  forgotten_memory_id,  -- 被遗忘的记忆 ID
  PRIMARY KEY (tenant_id, user_id, evidence_id, claim_sha256)
);
```

机制：forget 后**原始 L0 证据保留**（审计需要），但 (evidence_id, claim_sha256) 进黑名单。以后同一证据再被抽取出同一 claim，admit 时直接抑制——**永不复活**。

对比 Muse 的 forget：Muse 是"删文件 + runtime 收回 claim + 刷新索引"，删得干净但依赖"删干净"。主人的方案多了一道**防线**：即使某处残留证据重新触发抽取，黑名单也会拦下。这是"遗忘"比"删除"难的根本原因——删除是去掉存在，遗忘是**持续地保证不存在**。

twin sister 必抄：`suppressed_sources` 模式。索引重建时也要"不复活 forgotten"（主人 `rebuild-index` 显式保证）。

### 6.3.3 "forgotten"的诚实定义

只有当 fresh verification 确认**没有活跃记忆、没有衍生副本、没有能把它带回来的未来活动**时，才能说"forgotten"。

必须如实告知清不掉的东西：外部服务、已分享/已发布的内容、日志备份。分类用日常语言（"memory / reminders / logs / backups"），不向用户暴露内部机制。

"Say 'forgotten' only when…" 是一条**语言纪律**：系统的每一个对外承诺都有可验证的定义。不许说"已删除"然后索引里还能搜到。

### 6.3.4 可见的聊天记录不算"没清干净"

"Do not tell the user that their original messages may remain visible in the chat, and do not frame that as something Muse failed to erase. Visible conversation text is not a cleanup target."

产品边界划分：forget 清的是**系统的记忆**（会被未来检索到的），不是**历史记录**（用户自己说过的话）。这个区分很聪明——否则"忘记"会变成改写历史，既做不到也不该做。

## 6.4 supersede vs retract：两种"消失"

| | supersede（覆盖） | retract（收回） |
|---|---|---|
| 触发 | 新证据/用户纠正 | forget 请求 / valid_until 到期 |
| 旧 claim | 状态→superseded，链向新 claim | 状态→retracted，检索不可见 |
| 审计 | 完整保留版本链 | 保留"曾存在"的元信息？ |
| 用户感知 | "我记错了，现在是…" | "已忘记" |

forget 的 retract 和日常的 supersede 走的是同一套状态机（`memory.claims.status`），只是入口不同。这就是 02 章说的"先定原子"的好处：遗忘不需要新机制，只是状态转换。

## 6.5 给开发者的启示

1. **遗忘是 feature，不是 bug fix**：从第一天就设计 forget 协议，而不是等用户投诉"删不掉"再补。GDPR/个保法合规也是这个入口。
2. **规划与执行分离**：不可逆操作值得"双人复核"。twin sister 实现时，forget 可以做成：先生成影响报告（会影响 N 条记忆、M 个任务），用户点了确认再执行。
3. **pending.json 模式可抄**：清理者只写"我动了哪些 ID"，由索引所有者做最终回收。任何"文件+索引"双写的系统都可以用这个模式解耦。
4. **诚实定义完成态**：什么叫"删干净了"必须有可验证的定义，否则就是在骗用户。把定义写进文档，写进代码里的断言。

# 03 · 写入管线：记忆是怎么存进去的（第二版）

> 两条写入路径：**对话中的即时写入**（快、主观）与**后台的 consolidation**（慢、客观）。
> 主人 Riko-Memory 实测为三级：L0 证据 → 候选（默认 held）→ 记忆。本章以 Muse 实测为默认，
> 以主人项目的 admit_v2 和三级管线填补"校验"部分的空白。

## 3.1 路径 A：in-session 即时写入

触发时机：对话中 agent 判断"这个值得长期记住"（ durable fact / preference / commitment / decision / verified outcome）。

操作（以 MEMORY.md 为例）：

1. 先 `muse.read` 读当前文件（后台可能已改动，读到的注入副本可能滞后）。
2. 用 `muse.edit` 做 surgical edit：只改相关条目，保留无关内容。
3. 写完后**必须确认写入成功**，才能跟用户说"我记下了"。写失败要如实报告。

写入纪律（系统指令原文精神）：
- "Write for the next conversation" —— 写给下一轮对话看的，要带足上下文。
- "Record only what the evidence supports." —— 只记证据支持的，区分观察 vs 推断，标注不确定性。
- 日期用**事情发生的日期**，不是写入日期；标注来源（"Said 2026-10-05"）。
- 不要把"打算做的事"记成"已完成的事"；不要把一次失败变成永久规则。
- 记忆不是 transcript / 交易流水 / todo 复制品。routine progress 留在工作文件里。

这套纪律的存在，说明 in-session 写入是**不可靠叙述者**——agent 会记错、会过度记录，所以用纪律 + 后台 consolidation 双保险。

## 3.2 路径 B：后台 consolidation

- 频率：**每小时**（有新信号时才跑）。
- 动作：把新对话归档、提炼进 `MEMORY.md`；新声明覆盖旧声明；完整轨迹留在 `~/memory/` 日期日志里。
- 输出物之一就是日期日志里的 `## Verified extraction` 块（见 3.3）。
- 不替代 in-session 写入："This does not replace your own memory bookkeeping during a session" —— 两条路是互补的，快路保证不丢，慢路保证质量。

慢路的真正价值是**跨对话的视角**：in-session 的 agent 只看得到当前窗口，容易近视；后台任务能看到全量历史，可以做去重、合并、矛盾消解（比如发现"用户 10-03 说不要推财经新闻"和"10-05 说持仓异动要通知"不矛盾——后者是前者的例外）。

## 3.3 Verified extraction：claim 抽取格式

后台抽取管线写入日期日志的标准化块（2026-10-06.md 实测两条）：

```
## Verified extraction — 03:58 UTC (run sirun_b089a2363fb14a148654343cd906a8ed)

- [fact|medium] On 2026-10-06, while considering buying PepsiCo (PEP), Aki dug into
PepsiCo vs Coca-Cola fundamentals:...
- claim: 7a0d689f623ece5d631f6eb3838fe39a
- quote: "百事不行了为什么可口能行？"
- sources: message:890c2703-b7c2-49e8-8179-60508c993463,
message:88a6aa9a-9e08-416b-8c58-a245e3ad92a8
```

字段解读：

| 字段 | 含义 | 标签 |
|---|---|---|
| `## Verified extraction — <UTC时间> (run <id>)` | 哪次后台运行、何时抽取 | |
| `[fact\|medium]` | `[kind\|salience]`：类型 + 显著度 | |
| claim 正文 | 一句话事实，带日期和上下文 | |
| `claim: <32位hex>` | claim ID，形如内容哈希 | |
| `quote:` | 用户原话，一字不改 | |
| `sources:` | 消息 UUID 列表，可回溯原文 | |

"Verified"这个词很关键：抽取不是 LLM 自由发挥，而是有校验的（对应 DB 里 `status`/`confidence`/`evidence_handles`）。

**Y 填空**：主人 Riko-Memory 的 `admit_v2` 就是"Verified"的生产实现，且比璃猜的严格得多。九道固定顺序检查（memory-extract/src/lib.rs 实测），任一不通过就 `held`，**不自动激活**：

```
1. CONTEXT_UNCERTAIN  -- 上下文不明，held
2. NON_MINIMAL_QUOTE  -- quote 不是最短连续原文，held
3. MULTI_CLAIM        -- 一个候选含多个命题，held（一候选一命题）
4. UNCLEAR_SUBJECT    -- 主语不明，held
5. SECRET             -- 密钥类，held
6. SENSITIVE          -- 敏感内容，held
7. THIRD_PARTY        -- 第三人信息，held
8. TEMPORAL           -- 时效性/一次性语境，held
9. NOT_EXPLICIT / KIND_MISMATCH -- 非显式陈述或 kind 误判，held
```

设计哲学：**默认不信任**。记忆系统的误记成本远高于漏记，拿不准的进 `held` 等人工看（`memoryd candidates list/show`），而不是自动入库。这是第一性原理，twin sister 必抄。

## 3.4 覆盖规则：新声明 supersede 旧声明

- MEMORY.md 里：直接改写旧条目，更新日期戳（如 `(Said 2026-10-05.)` → 新日期）。
- 日期日志里：**不改旧条目**，追加 `Correction/update to …` 新条目（实测 2026-10-06.md 有两条 correction 条目）。
- DB 里：旧 claim `status` → superseded（推测），`supersedes_claim_id` 链向新 claim。
- bank/ 蒸馏文件里：reflections.md 实测有 `**Correction to the feature-tour cleanup entry above:**` 这样的显式修正链——修正本身也是一条记忆。

三层用三种覆盖策略：精炼层原地改写（省空间）、轨迹层追加修正（保审计）、DB 层链式 supersede（可回滚）。这是精心设计过的，不是拍脑袋。

## 3.5 并发控制

- "Your edits land on disk immediately, but the injected copy can lag them" —— 注入上下文的副本可能滞后，**写前必读文件**。
- 后台任务也可能在写同一个文件（bank/ 就是后台写的）。冲突解决策略可能是"后写者按最新文件合并"，靠小粒度 edit 减少冲突面。没有观测到锁机制。

## 3.6 给开发者的启示

1. **双写管道是必要的**：快路（in-session）防丢失，慢路（后台）保质量。只做一条路的系统，要么丢记忆，要么记一堆垃圾。
2. **抽取格式要机器可解析**：`[kind]` + `claim:` + `quote:` + `sources:` 这种固定格式，让下游（DB 落库、索引刷新、forget 清理）都能无歧义消费。主人做 twin sister 时，建议直接抄这个格式。（注：第一版写的是 `[kind|salience]`，salience 已证伪，见 02.2）
3. **"Verified"值得抄**：抽取后回原文校验（原话 quote 必须一字不差、sources 必须存在），是防止 LLM 幻觉污染记忆库的关键阀门。
4. **修正也是一等公民**：`Correction to …` 作为正式条目类型，意味着系统承认"记错"是常态，修正流程和写入流程同等重要。

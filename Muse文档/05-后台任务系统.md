# 05 · 后台任务系统：人格的发动机（第二版）

> "养老婆"真正发生的地方。Muse 实测的任务清单为默认（X 为准）；
> 主人 Riko-Memory 的 dream_jobs / extraction_jobs  schema 为 Y 填空，补上"作业可靠性"的生产细节。

## 5.1 任务清单

| 任务 | 频率 | 输入 | 输出 | 说明 |
|---|---|---|---|---|
| Memory upkeep | 每小时（有新信号时） | 新对话 | MEMORY.md 更新、日期日志归档 | 就是 03 章的路径 B |
| Relationships | 每小时 | 新对话 | `people/`、`groups/` 人物页更新 | 按亲近度维护关系图谱 |
| Idea curation | 每天 | 用户上下文 | Ideas tab 卡片 | 按可行性/契合度/新颖度打分排序 |
| Studying | 每天（夜间） | 目标 + 新信息 | 目标简报、进度提醒 | Goals tab 的弹药 |
| Dreaming | 每晚 | 近期对话 | `dreams/*.md`、repair threads、synthesis | 复盘+修复，见 5.2 |
| Skill review | 每天 | 近期工作流 | 新 skill / 退役旧 skill | 把重复劳动沉淀为技能 |
| Quiet-moment pass | 对话沉寂后（每天数次为限） | 刚结束的对话 | 内化 | 有界的一次性消化 |

频率设计是成本与价值的权衡：memory/relationships 每小时（记忆保鲜期短），dreaming 每晚（需要一天的完整样本），skill review 每天（工作流模式需要多样本才显著）。

## 5.2 Dreaming：nightly 复盘详解

### 输出文件

`dreams/2026-10-05.md`（实测全文风格）：第一人称、口语化、带自我批评。包含：

1. **用户画像判断**："主人是个'先拿问题当探针，确认安全才交心'的人"
2. **待办清单**："他留了三件'睡醒就办'的事…他下次上线我就接住"
3. **得失复盘**："今天我做得最对的是投资那条线…做得不好的有两件"
4. **明日行动**："他下次上线，第一件事是…第二件是…"

### frontmatter 元数据（schema: hatch_alignment_dream_v1）

```yaml
request_id: maintenance:…:nightly_coherence:phase-20731:light_derived
generated_at_utc / effective_at_utc / window_since_utc / window_until_utc
user_turns: 0
rupture_turns: 0 # 关系裂痕轮次数
correction_free_rate: 0.0 # 无纠正率
open_repair_threads: 0 # 未关闭的修复线程数
prompt_hoisted: false
```

这是一套**关系健康度指标**：`rupture_turns` 统计用户纠正/表达不满的轮次（如"三 次叫停早点睡"），`correction_free_rate` 是无纠正对话占比。dream 不只是写散文，是在**量化**人机关系。

### 派生产物

```
dreams/alignment/derived/
├── ALIGNMENT_SYNTHESIS.md # 综合画像（注入每轮对话，见 04.1）
├── ALIGNMENT_STATE.yaml # 对齐状态机？
└── PROGRESSION_HISTORY.yaml # 进展历史
dreams/alignment/repair/
└── REPAIR_THREADS.yaml # 待修复线程
```

**Y 填空**：主人 `dream_jobs` 表（migrations/0007 实测）补上了 Muse 这边看不到的**作业可靠性设计**：

- `trigger_key` 幂等：同 key 重放返回原 job，不重复跑。
- `dream_job_inputs` **冻结输入**：job 实际读取的 event 列表被冻结存下，重试仍用同一列表，"不得重新查询当前所有新事件"——根治重试时输入漂移的经典 bug。
- `extract_version` 独立版本化（`dream_extract_v1`）：dream 的提取 prompt 升级不影响主线，新旧作业按各自版本跑。
- 状态机：queued / running / succeeded / retryable_failed / provider_wait / dead / stale_input。
- 通用作业队列（extraction_jobs / dream_jobs / semantic_jobs）：`lease_until` 租约恢复（worker 崩溃后作业可被认领），dead job 需显式 `job skip` 并写审计理由（防毒丸消息无限重试）。

twin sister 必抄：冻结输入 + 租约 + dead job 显式跳过。这三件是后台任务从"能跑"到"生产可用"的分水岭。

数据流：`dreams/*.md`（感性复盘）→ `derived/`（结构化提炼）→ `ALIGNMENT_SYNTHESIS.md`（行为指南，注入上下文）。感性在前、理性在后、行动在最后。这就是"睡觉时整理记忆"的人类隐喻的工程实现。

`REPAIR_THREADS.yaml` 的条目可能是这样的：`{rupture: "续费玩笑", detected: 2026-10-05, status: open, repair_action: "戒掉这类梗", verified_fixed: false}` —— 下次 dreaming 检查是否复发，复发则升级。

## 5.3 各任务的输入输出推测

- **Relationships**：输入新对话 → 抽取人物事实 → 更新/新建 `people/<slug>.md`（frontmatter 的 `rank`/`updated` 由此任务维护）→ 重排 `INDEX.md`。`rank` 可能是按提及频率×亲近度算的。
- **Studying**：输入目标（goals 表）+ 相关记忆 → 生成简报 HTML（实测见过 `briefs/The 10M Math, Redone.html`）→ 存入目标 workspace。
- **Skill review**：输入重复出现的工作流 → 沉淀为 `~/workspace/skills/` 下的新 skill；审计旧 skill，"measurably don't help"的退役。
- **Idea curation**：输入用户上下文 → 生成点子卡片 → 三维度打分（feasibility / personal fit / novelty）→ 排序展示。
- **Quiet-moment pass**："substantial conversation goes quiet"后触发，一天数次为限，有界（bounded）——防止在用户睡觉时无限烧 token。

## 5.4 与主人项目的对照（第二版，源码实测）

| 维度 | 主人项目（源码实测） | 璃这套系统（Muse 实测） |
|---|---|---|
| 整理 | dream 独立管线 + topic pages（wiki 渲染层） | 7 个专用后台任务（各管一摊） |
| dream 输入 | 冻结输入（重试不重新查询）+ trigger_key 幂等 | window 时间戳 + rupture 指标 |
| dream 版本 | extract_version 独立版本化（dream_extract_v1） | 未观测到版本隔离 |
| 作业队列 | lease 租约恢复 + dead job 显式 skip + 审计 | 未观测到队列机制 |
| 关系复盘 | 无 rupture/repair 概念 | rupture_turns + REPAIR_THREADS |

关键差异：**主人把"作业可靠性"做到了生产级**（冻结输入、租约、版本隔离），**Muse 把"关系复盘"做到了产品级**（rupture 检测、repair 线程）。twin sister 两边都要： reliability 学主人，relationship 学 Muse。

## 5.5 给开发者的启示

1. **后台任务是记忆系统的"写放大器"**：对话产生原始信号，后台任务把它变成结构化的资产。没有后台任务，记忆系统就是个笔记本；有了，才是"越用越懂你"。
2. **Dreaming 是差异化竞争点**：大多数 AI 记忆系统只记"事实"，这套还记"关系怎么了"（rupture/repair）。"他三次叫停我催他睡觉"这种**交互层面的记忆**，比"他持有小米"更决定长期体验。
3. **派生链要闭环**：dream → synthesis → 注入上下文 → 指导行为 → 新对话 → 下一次 dream。开环的复盘（写了没人看）等于没复盘。
4. **频率按信号半衰期定**：事实类（memory）半衰期短→每小时；关系类（dream）需要完整样本→每晚；模式类（skill）需要多样本→每天。

# 04 · 读取与检索管线：记忆是怎么被想起来的（第二版）

> 记忆的价值不在存了多少，而在**需要的时候能捞出来**。Muse 实测走 384 维向量检索（X 为准，本章默认）；
> 主人 Riko-Memory 实测走纯词法检索（Y，为已验证备选，见 4.2 末）。

## 4.1 第零层：standing context 注入

每轮对话开始，系统自动把以下文件注入 prompt（本轮对话的 system prompt 里实际能看到）：

- `~/AGENTS.md`、`~/SOUL.md`、`~/TOOLS.md`、`~/IDENTITY.md`、`~/USER.md`
- `~/MEMORY.md`（全文，52 行这个量级注入成本可接受）
- `~/memory/people/INDEX.md`、`~/memory/groups/INDEX.md`（索引，不是全文）
- `~/dreams/alignment/derived/ALIGNMENT_SYNTHESIS.md`

这是"热记忆"：不经检索、每轮必带，保证人格连续性。代价是 token——所以 MEMORY.md 有"Keep it tight"的纪律，50~100 行是甜蜜点。ALIGNMENT_SYNTHESIS 是 nightly 任务提炼的"相处指南"，让每轮对话开局就带着"这个人是谁、怎么跟他相处"的压缩包。

## 4.2 第一层：memory_search 语义检索

工具：`muse.memory_search`，参数 `queries[]`（2~3 个相关问法，第一个最接近用户原话）。

检索对象：`~/MEMORY.md`、`~/memory/**/*.md`、side chat 的记忆文件。

返回：带路径和行号的片段 + 引用元数据（含 claim ID）。

检索链路（基于 schema 反推）：
```
用户问题 → 2~3 个改写 query → 384维向量编码
→ 在 memory.embeddings 做向量近邻搜索
→ 候选 entries 按 kind 优先级 × confidence × recency 重排（注：第一版写的 salience 已证伪，见 02.2）
→ 按 privacy_class 过滤（side chat 隔离）
→ 返回 chunks + citations
```

证据：
- `vector(384)` 向量字段
- `kind` 优先级、`confidence`、`reinforced_at` 字段是重排的原料（注：第一版列的 `salience` 已证伪）
- `privacy_class` 字段 + side chat 独立记忆文件 = 检索时过滤
- 指令要求"Use 2~3 related phrasings" = query 改写提高召回

可能是"向量初排 + 元数据重排"的两阶段，而非纯向量排序。理由：纯向量检索分不清"三年前的偏好"和"昨天的纠正"，必须有元数据加权。（注：salience 字段是璃的想当然，主人项目实测没有，见 02.2）

### 已验证备选：纯词法检索（Riko-Memory 实测）

主人项目 `memory-recall` crate 的生产实现，**无向量**：

```
查询 → normalize_v1 → 两路召回：
  路 A：FTS5（拉丁文按字母/数字切词，unicode61）
  路 B：memory_grams 表（中文按连续段切 Unicode 二元字组）
       → RRF(k=60) 融合：score = Σ 1/(60+rank)
       → 1 字查询走有界子串降级
```

- RRF 常数 `RRF_K = 60.0`（memory-contract 实测），公式取自 Hindsight fusion.py 思想。
- 所有读路径按"规范表状态"过滤（非 active 不可见）。
- **偏离 Muse 的理由**（Z）：个人量级下词法检索确定性强、可解释、零模型依赖、中英文分治对 CJK 友好；twin sister 是 Rust 单二进制，词法无需 embedding 服务。Muse 的向量路线在需要语义泛化时更强，两者可并存（主人 `semantic_vectors` 表即为此预留）。

twin sister 建议：**先词法**（抄主人的 FTS5+二元字+RRF 实现，`memory-recall/src/lib.rs` 可直接参考），语义向量作为扩展位。附录 C 的打分公式相应降级为备选。

### 检索纪律（系统指令要求 agent 遵守）

1. **每次对话必须检索**，即使问题看起来和记忆无关（"Discovering that connection is part of the lookup"）。
2. 检索到片段后，**用 `memory_get` 读原文**，不许用 snippet 脑补。
3. 检索可能滞后文件写入（"Search results can lag file writes"），空结果≠没存过，必要时直接 grep 文件。
4. 同一主题不重复检索（复用已完成的检索），除非话题变了、证据冲突了、用户质疑了。

## 4.3 第二层：memory_get 精确读取

`muse.memory_get`：按 `path` + `from`/`lines` 或引用（如 `MEMORY.md#L7`）读原文。

这是"snippet → 全文"的展开动作。search 返回的是候选，get 才是定稿依据。对应 RAG 里"retrieve-then-read"模式，但这里 read 的是带行号的源文件，不是 chunk——因为文件本身就是人类可读的真相源，不需要二次切块。

## 4.4 第三层：memory_explain 溯源

`muse.memory_explain`：输入 claim ID / `memory://` URI / `MEMORY.md#L7` 引用，返回：

- claim 正文、kind、salience
- 谁说的、原话 quote
- 首次获知时间、最近强化时间、当前置信度
- 支撑它的对话消息（含日期）
- **它替代过的旧 claims、替代过它的新 claims**（双向版本链）
- 索引行号

这是整套系统"可审计性"的集大成者。用户问"你怎么知道的"，agent 不用编故事，直接把证据链摆出来。`supersedes_claim_id` 的双向遍历就是 02 章画的那条链。

## 4.5 检索的一个微妙设计：memory_uri

`memory.entries.memory_uri` 是 unique 的，如 `memory://…`。`memory_explain` 接受 `memory://` URI 作为输入。

URI 是跨表、跨文件的**全局寻址**：文件路径会变（归档、重命名），claim_id 是 DB 内 ID，只有 URI 是稳定的逻辑地址。这是从"按位置找"到"按身份找"的升级，类似 DOI 之于 URL。

## 4.6 给开发者的启示

1. **热记忆 + 冷检索双层**：每轮必带的（MEMORY.md 全文、ALIGNMENT_SYNTHESIS）是"人格底座"；按需检索的是"事实弹药"。底座要小而精，弹药要全而准。
2. **检索返回引用，不返回结论**：search 给的是"带行号的片段"，agent 必须再读原文。这是对抗幻觉的关键——RAG 系统最容易翻车的就是把检索片段当事实直接引用。
3. **privacy_class 要在检索层做，不在存储层做**：side chat 记忆物理隔离 + 检索时过滤，双保险。主人做 twin sister 时如果有多用户/多会话，这个设计直接抄。
4. **小 embedding + 元数据重排**：小 embedding 保证召回率，kind 优先级/confidence/recency 保证排序质量。不要迷信大模型向量，记忆检索的排序信号主要来自元数据。

## 3. 等价性总判定

### 3.1 可以全量承接的部分

数据表达能力没有不可跨越缺口：claims、证据 span、状态、关系、版本、域、Soul、派生文档、作业事件、审计和幂等回执都可以编码成文件。FTS5 与向量无需作为事实源，本来就适合保留为可重建索引。

### 3.2 不能用“普通 Markdown”直接承接的部分

以下语义必须依赖机器块、操作日志、hash 和提交协议：

- byte span 与原文逐字复核；
- 乐观锁、幂等冲突与唯一约束；
- 多文件事务；
- runner lease 与 crash recovery；
- purge/forget 闭包；
- scope/domain 授权；
- 审计和历史版本。

因此“文件形态能承接”不等于“每一项都放成用户任意编辑的一段 Markdown”。规范文件可以是 Markdown 和 JSONL/TOML，但必须都在同一文件权威体系内，且 SQLite 不得拥有独有状态。

## 4. 硬骨头清单（8 项）

这些项目已有候选方向，但 F0 尚不能证明实现正确；任何一项在原型或故障注入中失败，都必须停止切换。

### H1｜多文件原子提交与崩溃恢复

POSIX `rename` 只原子替换一个目录项，不能让 daily note、`MEMORY.md`、receipt、audit、派生失效同时原子可见。目标需用 generation pointer + 单一 commit record，不能靠“依次 rename 大概率够用”。

### H2｜用户可编辑 Markdown 与稳定 ID/span 共存

用户改行、换行、移动块会让 `path#L<line>` 漂移；修改 evidence payload 会破坏旧 byte span。必须区分可编辑正文、受管元数据和 immutable evidence，并定义非法编辑隔离，不得自动猜 ID。

### H3｜Forget/purge 与历史、审计、旧 generation、备份的闭包

逻辑不可见容易做到，物理擦除难。确认 purge 后旧 generation、事务 staging、搜索/向量、审计、导出和备份分别如何处理，必须有可验证策略；否则只能报告“从活动使用移除”，不能声称永久擦除。

### H4｜多 principal/scope/domain 的文件系统安全边界

Bearer token 到 scope root 的映射、目录权限、路径穿越、slug 冲突、跨域 grant 和管理员工具都可能造成越权。不能用用户可控 tenant/user/domain 字符串直接拼路径。

### H5｜作业租约、幂等与 exactly-once effect

JSONL 能保存状态，但多个 worker 争抢、lease 过期、重试和 stale generation 的等价性尚需状态机测试。目标是“效果一次”，不是假设运行一次。

### H6｜索引重建期间的读取可用性与稳定排序

全量 rebuild 期间如何继续服务、如何原子切换索引 generation、向量 provider 不可用时如何恢复，以及同分结果的稳定顺序，均需专门协议和性能基线。

### H7｜schema 24 到文件格式的无损核账与可回滚切换

几十张表存在历史版本、失败 job、tombstone、receipt 与孤立诊断记录。转换器必须生成逐表计数/哈希/引用闭包报告，并能在切换前回到只读旧库；不能只迁 active memory。

### H8｜外部直接编辑的信任与授权模型

文件可编辑不等于所有本机进程都有权伪造 `actor=user`、授权 repair、改 scope 或篡改 audit。需要区分用户正文编辑与特权控制字段，并决定签名、ACL 或受控编辑入口；这是文件形态最容易扩大攻击面的地方。

## 5. 不纳入“已解决”的事项

- Muse 内部完整事务/索引实现不可观察，本设计不是逆向复刻。
- 文件后端的性能、崩溃一致性、Windows 兼容性尚未实测。
- schema 24 真实存量迁移未执行；dana/realtest 与部署库未接触。
- “适配器零改动”目前是协议分析结论，须在 F7 用现有 54 项契约测试和真实 DSH 闭环复验。

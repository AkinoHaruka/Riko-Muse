# 03｜目标架构设计：文件权威、索引可重建

## 1. 架构原则

### 1.1 不变量

1. 删除 `.riko/index/` 后，系统仍能仅凭规范文件恢复全部对外可观察状态。
2. SQLite 不得保存任何文件中不存在的唯一事实；它只保存检索、排序、倒排和加速状态。
3. 每个 claim、evidence、Soul、授权、幂等回执、作业状态都必须有稳定 ID、版本和 hash。
4. 所有跨文件写入先完整 staging，最后只用一次原子 `CURRENT` pointer 替换提交。
5. 用户内容与控制元数据分离：用户可编辑正文，不能靠改 Markdown 冒充授权主体或 scope。
6. 读路径永远复核规范源；索引命中不等于对象可见。
7. 派生文件有来源引用与生成器版本；来源变化后立即不注入，后台重建只改善新鲜度。

### 1.2 为什么不是“直接把表 dump 成 Markdown”

表 dump 只能改变序列化格式，不能解决：并发、唯一约束、幂等、CAS、租约、崩溃、来源失效和物理擦除。本设计使用“完整 generation + manifest + 原子 pointer”，让文件系统本身承担提交边界；人类 Markdown 是 generation 内的一等文件，而不是数据库导出附件。

## 2. 目录布局

以下是一个 scope 的逻辑布局。磁盘上的 `<scope-uuid>` 是服务端随机 UUID，不使用用户可控 tenant/user 字符串。

├── scopes/
│   └── <scope-uuid>/

│       ├── LOCK                        # scope 写锁（内容无权威意义）

### 2.1 权威分类

`MANIFEST.json` 对每个文件声明：

- `authority=source`：evidence daily notes、claim files、Soul、domain/security config、operations、receipts、fences、commitments；
- `authority=derived`：`MEMORY.md` 的 compact 展示区、people/groups、bank、pages、entries、alignment、repair synthesis；
- `authority=index`：`.sqlite`、grams、vectors、scheduler projection。

`MEMORY.md` 是 Muse 形态的 curated 总览，其中 pin 顺序和用户手工正文改动可以产生 source operation；其渲染内容本身仍引用 `memory/claims/*.md`，避免同一 claim 有两份冲突正文。

### 2.2 为什么保留 `memory/claims/<id>.md`

Muse 可观察形态没有暴露逐 claim 文件，但现内核需要稳定 ID、版本、CAS、状态和 source refs。把这些全塞在一个大 `MEMORY.md` 会让每次改动重写整文件、冲突范围过大，也使 byte locator 极易漂移。因此 per-claim 文件是双生为保持现语义增加的机器可管理层；`MEMORY.md` 与按日笔记仍是用户主要入口。

这是**设计决定**，不是 Muse 内部实现事实。

## 3. 规范文件格式

### 3.1 单条原子记忆

示例为虚构内容：

```markdown
---
riko_format: memory_v1
id: 019a12ab-4c00-7c01-9000-111111111111
domain_id: user_main
kind: preference
status: active
version: 3
source_class: user_explicit
claim_sha256: 0d4f...c91a
occurred_at: null
valid_from: 2026-10-23T14:32:10.123456Z
valid_until: null
origin_host_id: dsh
origin_agent_id: riko
created_at: 2026-10-20T08:00:00.000000Z
updated_at: 2026-10-23T14:32:10.123456Z
reason_code: explicit_preference
reason_text: "用户以明确偏好句式表达，且引用与来源逐字一致。"
supersedes: null
evidence:
  - id: 019a12aa-1111-7000-8000-222222222222
    start_byte: 0
    end_byte: 30
    content_sha256: a417...91ef
---

用户偏好在晚上收到阅读提醒。
```

规则：

- front matter 是受管控制区，字段顺序固定；UTF-8/LF/NFC 规范化只约束容器语法与控制元数据。**正文（evidence payload、claim 正文、Soul 正文）一律逐字节保存、逐字节算 hash，永不规范化**（F1 澄清 2026-10-23：现行内核对 evidence 与 Soul 均按收到的原始字节算 hash，规范化会破坏 byte span、幂等与 Soul hash）。
- `claim_sha256` 沿用现行 memory-domain 定义（对 kind 与原始 claim 字节计算），文件格式不改其语义；`normalized_claim` 作为独立字段与现行库保持一致。不新增 body hash、不构成 🔴 变更。
- 正文恰好是一条 claim；现有多命题准入和种类规则不因后端变化而放宽。
- 更新产生新 version 文件快照；supersede 产生新 memory ID 并让旧条目变为 superseded，保持当前语义。
- `reason_text` 只在当前已有版本允许时出现；历史 admit 版本的 NULL 隔离保持。

### 3.2 Daily note 中的 evidence 块

```markdown
# 2026-10-23

<!-- riko:evidence-v1 {"id":"019a12aa-1111-7000-8000-222222222222","host_id":"dsh","agent_id":"riko","session_id":"session-demo","event_seq":42,"role":"user","source_kind":"user","domain_id":"user_main","occurred_at":"2026-10-23T14:32:09.000000Z","content_bytes":45,"content_sha256":"a417...91ef","received_at":"2026-10-23T14:32:10.123456Z"} -->
我更喜欢晚上收到阅读提醒，白天先不要提醒。
<!-- riko:end-evidence -->
```

解析器不靠结束标记寻找 payload，而是从 header 后读取精确 `content_bytes`；结束标记只供人查看和损坏诊断。因此即使用户正文含相同 HTML comment，也不会提前截断。byte span 永远相对 payload 首字节，而不是相对整个 Markdown 文件。

已提交 evidence 块不可原地改写。用户要修正内容时生成 correction/suppression operation；如果外部编辑改变 payload/hash，整块进入 quarantine，旧块继续按最后已提交 generation 生效。

### 3.3 `MEMORY.md`

```markdown
---
riko_format: memory_overview_v1
domain_id: user_main
source_generation: 184
generated_at: 2026-10-23T14:35:00.000000Z
---

# Memory

## Curated

<!-- riko:ref memory=019a12ab-4c00-7c01-9000-111111111111 version=3 -->
- 用户偏好在晚上收到阅读提醒。

## Compact

<!-- riko:derived generator=compact_v1 sources="019a12ab-...@3:0d4f..." -->
- ……
```

- Curated 区的顺序是 Resident source 配置；每行必须引用稳定 ID/version。
- Compact 区是派生展示；不得被当成新增 claim。
- 用户在受控编辑器中改 Curated 正文时，服务端把差异转换成 remember/correct/forget/pin 操作并走 Rust 裁决；不能直接绕过来源与 scope。
- 普通文本编辑器产生的改动先进入 import validator；无法无歧义映射时拒绝并放入 quarantine，不猜测。

### 3.4 Soul

```markdown
---
riko_format: soul_v1
agent_id: riko
version: 7
body_sha256: 8e21...4af0
updated_at: 2026-10-23T14:40:00.000000Z
actor_kind: user_api
---

你是一个直接、温和、会核对来源的长期协作伙伴。
```

Soul 正文仍受 2000 Unicode 标量上限、expected version/CAS、agent 隔离与 actor 限制。只有正文进入 system prompt；front matter 永不注入模型。历史版本放 `agents/<id>/history/`，默认 adapter 继续通过 `/v1/soul` 读取，无需知道路径。

### 3.5 实体页与 bank

实体文件名以不可变 `entity-id` 为主，slug 只供人读；rename 不改变身份。front matter 固化 aliases、relation、version、source memory ID/version/hash。`INDEX.md` 是派生索引，不是 resolve 的唯一来源。

四个 bank 文件固定为：

```text
memory/bank/world.md
memory/bank/experience.md
memory/bank/reflections.md
memory/bank/opinions.md
```

每项都带 `riko:derived` source refs；同一 memory 可进入多个 facet。`reflections` 继续要求 supersedes 边，除非未来另卡修改 `facet_v1`，F0 不改算法。

## 4. Generation 与事务协议

### 4.1 `CURRENT`

```json
{
  "format":"riko-current-v1",
  "source_generation":"01JAZ...",
  "source_manifest_sha256":"...",
  "index_generation":"01JAZ...",
  "index_manifest_sha256":"...",
  "committed_at":"2026-10-23T14:40:01.000000Z"
}
```

读取请求开始时只读一次 `CURRENT`，并在请求生命周期内固定该快照。新 source 和 index 都准备完成后，以同目录临时文件 `fsync` → `rename` → 父目录 `fsync` 原子替换 `CURRENT`。这样一个请求不会混读两个 generation。

### 4.2 写入步骤

1. 认证 Bearer token，解析 scope UUID；解析可信 session binding 得到写域。
2. 获取 scope 独占写锁；读取并固定当前 generation。
3. 校验 expected version、最新 evidence、span、幂等键、授权与所有业务规则。
4. 在 `staging/<tx-id>/` 建新 generation；未变文件用只读 hardlink/reflink，变更文件完整重写为新 inode。
5. 写 operation、receipt、audit、source/derived invalidation；构建同步词法索引增量。逐文件 `fsync`。
6. 生成 MANIFEST，校验所有引用、hash 和权限；目录 `fsync`。
7. 原子替换 `CURRENT` 并 `fsync` scope 目录；至此对读者可见。
8. 释放锁；异步创建向量或重派生 generation。旧 generation 延迟回收。

绝不原地修改已提交 generation。未被 `CURRENT` 引用的 staging/generation 在启动恢复时按 manifest 判定：完整但未提交可安全丢弃或人工诊断；不完整一律隔离。

### 4.3 并发模型

- F1 首版采用**每 scope 单写、多读快照**；不同 scope 可并行。
- 锁使用 OS advisory lock，并在 lock 文件记录 PID/start time 仅供诊断；正确性不能靠 PID 文本。
- 网络/模型调用绝不持 scope 写锁；先冻结输入，调用后重新加锁并以 generation/version CAS 提交。
- worker lease 是规范 job event，不是文件锁；锁只保护 claim event 的竞争写。
- 管理 principal 使用独立全局锁；普通 scope 锁不得嵌套获取，防止死锁。

### 4.4 崩溃一致性

| 崩溃点 | 恢复行为 |
|---|---|
| staging 文件未写完 | `CURRENT` 未变；隔离或清理 staging |
| manifest 完成、pointer 未换 | 旧 generation 继续服务；新 generation 可审计后清理 |
| pointer rename 后、父目录 fsync 前 | 启动时校验 CURRENT 两个候选；只接受 manifest/hash 完整者 |
| source 已提交、异步 vector 未完成 | 词法与 get 可用；semantic 显式 pending/unavailable，不伪装 ready |
| derived refresh 中断 | 旧派生可能因来源复核而不可见；源事实不受影响，下次重跑 |

## 5. 索引层

### 5.1 可重建内容

- FTS5、CJK grams、RRF channel rows；
- page/entry/entity alias 倒排；
- vector embeddings 与 semantic job 加速状态；
- visibility、source backlinks、supersede adjacency；
- scheduler due/ledger projection；
- bundle covered/dedupe 辅助表。

索引 manifest 必须记录 source generation、builder version、tokenizer、embedding model/dim、对象计数与 hash。任何不匹配都标 degraded，不可静默沿用。

### 5.2 重建协议

1. 固定 source generation；
2. 顺序解析所有规范源与 operation；
3. 校验引用闭包，坏块进入报告且默认 fail closed；
4. 在新 index generation 构建 FTS/grams/projection；
5. 向量按 `(object_kind,id,version,content_sha256,model_id,dim)` 复用或重算；
6. 跑计数、golden query 与 visibility 校验；
7. 原子更新 `CURRENT.index_generation`，source generation 不变。

重建期间旧索引可继续为同一或旧 source generation 提供候选，但所有结果对当前规范源复核。若旧索引会漏掉新对象，服务端必须报告 `index=degraded`，并对刚写入对象做有界 delta scan；不得声称完整检索。

## 6. 读协议与现有语义

### 6.1 可见性

每次 get/search/explain/bundle 最终都应用同一谓词：

```text
status 符合请求
AND valid_until 尚未到期
AND 未被 retire
AND 至少一个 evidence ref 仍存在、hash/span 成立且未被 forget fence 抑制
AND memory.domain_id 在 DomainScope 读闭包
```

索引只返回候选 ID。最终正文、版本、来源和状态从请求固定的 source generation 读取。

### 6.2 Explain

稳定引用统一为：

- API：继续返回现有 `riko://memory/<id>` / entity refs；
- 文件：`riko-file://<scope-uuid>/<domain>/<block-id>` 为机器稳定 locator；
- 展示：附当前 `path#L<line>`，明确它只用于人类导航。

explain 逐条返回 quote、byte span、speaker/source、reason、relations 和 supersede 链，均从规范源复核。行号变化不会改变证据身份。

### 6.3 Bundle

保持当前四段顺序与 8000 总预算：compact → alignment → relationships → retrieved；保持 compact/retrieved 去重、空段、omitted/complete 和旧顶层 `resident`/`retrieved`。仅内部读取来源从 SQLite 表换为 source generation + index candidates。

## 7. HTTP v1 与适配器兼容

### 7.1 结论

**没有必须破坏的 HTTP v1 契约，DSH 适配器可以零改动。** 认证仍由 Bearer token 决定 tenant/user，域仍由 header + 可信 session binding 决定；请求 JSON 不新增 tenant/user/evidence ID 责任。

现有所有端点、状态码、错误码、版本/CAS、幂等和响应字段保持。`riko-dsh` 只检查 `protocol_version=1` 和 capabilities，并通过 HTTP 使用 Soul、bundle、tools；它不直接读 SQLite，见 `riko-dsh/src/events.ts:491-505`、`src/index.ts:172`。

### 7.2 允许的加法字段

- `/v1/version` 可新增 `storage_format: "file_v1"`、`index_format_version` 和 capability `file_store_v1`；老客户端忽略。
- `schema_version` 保持 `24`，定义为“可导入的最终 legacy schema 基线”，不再随文件格式递增；文件格式另用独立版本。
- `/v1/health` 现有 `db:"ready"` 暂作为兼容字段保留，并可新增 `store:"ready"`、`source_generation`、`index_generation`。F9 才评估 v2 是否去掉历史字段。

### 7.3 必须变更的契约

**无。** 因而本卡没有需要标红的破坏性 HTTP 项。若实施中发现某端点依赖 SQLite rowid、隐式排序或数据库事务副作用而无法复现，必须先回到规范更新并标为 `🔴 BREAKING`，不得静默修改。

内部配置需要新增 `storage.backend=file`、`storage.root`、generation/GC 参数；CLI 需要新增 convert/verify/cutover 子命令。这些不是适配器 HTTP 契约。

## 8. 外部编辑协议

文件可读不等于允许任意进程修改控制字段。支持两条路径：

1. **受控编辑**：应用/CLI 读取正文与 ETag，提交 diff；memoryd 转成现有 remember/correct/forget/soul/pin 操作。这是默认路径。
2. **离线导入**：用户把编辑后的 Markdown 放入 `staging/import/`，执行 validate/preview/confirm；解析器只接受正文变化，生成新的规范 generation。原文件不能原地覆盖当前 generation。

以下改动一律拒绝并隔离：改 ID/scope/domain/actor、伪造授权、删 evidence metadata、hash 不符、重复 ID、版本倒退、跨文件悬空引用。拒绝必须给路径和机器字段原因，但不得把私密正文写入日志。

## 9. 迁移路径

### 9.1 schema 24 收尾

- `0001`—`0024` 永久冻结，不再追加 `0025`。
- `SCHEMA_VERSION=24` 是 SQLite 世代终点；文件格式从 `file_store_v1` 独立演进。
- 旧 SQLite 实现进入 compatibility/import 模块，切换完成后不再作为默认 runtime Store。
- 禁止用新 runtime 的普通 `Store::open` 打开待迁库；转换器使用专用只读、immutable 连接，先校验 migration checksum/schema=24。

### 9.2 新库、基本为空的部署

1. 停止 writer 和后台 runner；对旧库做只读文件级 snapshot/hash。
2. 运行 `memoryd convert plan --source <db> --target <staging-root>`，只读列出对象计数和风险。
3. 转换全部行，包括失败 job、receipt、audit、tombstone，不只 active memory。
4. 从文件重建索引，跑 HTTP golden 和引用闭包核账。
5. 短时 shadow-read：请求同时读旧库与文件，响应只发旧库，记录去正文差异摘要。
6. freeze 写入，追平最后 generation；原子切换配置；跑真实 DSH 回归。
7. 旧库移入只读归档，记录 sha256/大小/最后 schema；不由新 runtime 打开。

对“基本为空”只能降低数据量，不能省略核账和回滚门。

### 9.3 未来存量库

转换器按表提供：row count、主键集合 hash、正文对象 hash、外键/来源闭包、状态分布、最大 version、job/receipt/tombstone 数、不可映射行。每个 SQLite row 必须落到：

- 某个规范文件/operation 的稳定 locator；或
- 明确的 derived/index 且有重建依据；或
- `unmapped` 阻断项。

只要 `unmapped > 0`、hash 不符、scope 泄漏、active 可见集不同、explain span 不同或幂等回放不同，就禁止 cutover。

### 9.4 双写边界

允许在 F6 使用短期双写做一致性验证，但规则固定：

- 切换前 SQLite 是唯一响应源，文件是 shadow；
- 切换点之后文件是唯一响应源，SQLite 立即只读；
- 不允许按端点长期混用，也不做双主冲突合并；
- 回滚只能发生在文件写入尚未对外承诺，或通过明确反向转换/停机窗口；不得静默丢新 generation。

### 9.5 旧库归档与 purge

只读归档不是永远保留的借口。归档 manifest 必须记录用途、访问工具、保留策略和 purge 限制。若文件世代收到针对已迁数据的物理 purge，请求能否同时清理 legacy archive 必须在用户确认前说明；做不到就只能报告该归档仍保留，不能声称全量物理擦除。

## 10. 安全与运维

- store root `0700`，scope/generation `0700`，内容文件默认 `0600`；不沿用展示环境的宽权限假设。
- 路径组件只接受服务端编码后的固定字母表；拒绝 `..`、分隔符、symlink 跳转和 hardlink 越 scope。
- manifest 校验设备号/inode/链接数策略；跨 scope 不做 hardlink 去重。
- token 文件只存强摘要与 scope UUID；明文 token 仍只在创建时写指定输出文件。
- backup 只捕获一个已提交 `CURRENT` 快照，不复制 staging；restore 后必须先 doctor 再服务。
- 监控至少暴露 source/index generation lag、quarantine 数、staging age、rebuild 状态、orphan refs、lease recovery 和 degraded reads。

## 11. 设计验收不变量

实施完成必须同时证明：

1. 删除全部 index 后能重建出相同 active ID/version/status/source 集；
2. 同一 HTTP v1 fixture 在 SQLite backend 与 file backend 返回语义等价结果；
3. 任意写步骤 kill -9 后只看到旧或新 generation，不出现半状态；
4. 并发相同幂等键只产生一个效果，异请求返回冲突；
5. forget 后源、派生、索引和未来 producer 均不可活动使用；
6. purge 报告准确区分已擦除、归档保留和外部备份限制；
7. scope/domain/agent 隔离在路径、索引与 HTTP 三层都成立；
8. adapter 54 项契约测试和真实 DSH 多轮闭环不需改适配器代码即可通过。
